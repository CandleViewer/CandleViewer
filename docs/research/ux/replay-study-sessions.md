## Method note (agent-delivery adaptation, owner decision 2026-09-25)

The ticket calls for structured sessions with the owner and the two account managers, a 2-second screenshot test and one keyboard-only session. Delivery is a solo agent with one human owner, so — as `e16-recorder-mental-model.md` and `e30-d01-session-protocol.md` did — the sessions are replaced by (1) the heuristic evaluation of §3 against the catalogue, the contracts and the shipped replay code, (2) the teardown of §2 from public documentation fetched 2026-10-21 (no exchange host contacted; a claim not backed by a fetched page is labelled "(heuristic, unsourced observation)"), and (3) the protocol of §6 and the checklist of §6.7 for the owner. Severity uses Nielsen's scale: **S4** catastrophe (a trader can act on stale prices or lose a protection), **S3** major, **S2** minor, **S1** cosmetic. A default that differs from a contract or from the shipped code is recorded as a contradiction (§7.1), never silently.

### 2.2 What CandleViewer copies and what it must avoid (heuristic, each with its source)

1. **Copy:** a status line that says what to do next and how far the segment has played (ATAS [AT-1]) → the transport carries a one-line state ("Seeking to 13:52:04…", "Gap 13:52–13:55 — recorder was offline", "End of range"); H1.
2. **Copy:** "Go to real time is not an exit" vs "Jump to real-time chart" ending replay (ATAS [AT-1] vs TradingView [TV-1]) → CandleViewer's `R` must say which it is: "Leave replay and return to live data", confirmed (SCR-097), with what happens to simulated positions (F6); H5.
3. **Copy:** the first-available-day jump (TradingView [TV-2]) and the automatic jump to the first available bar → US-RPL-001's "earliest available timestamp offered with the reason" and US-RPL-007's "jump to earliest"; H9.
4. **Copy:** one shared clock across charts (TradingView "All charts", Sierra "All Charts in Chartbook" [TV-1, SC-1]) and the lesson that per-chart empty-period skipping breaks sync (Sierra [SC-1]) → the gap policy is a session property, never per pane (F9); H4.
5. **Copy:** stepwise speed keys (Bookmap `.` / `,` [BM-2]) → next / previous preset keys, missing from the keymap today (F14, G2); H7.
6. **Avoid:** trading executed on real-time data while the chart replays (TradingView [TV-1]) — the exact "act on stale prices" hazard this ticket names; CandleViewer's fills come from the paper matcher against the replayed book (`24` §12, §13.7), nothing can reach an exchange (F23, F24), and no exchange-bound order surface exists on `/replay` at all — the lock does not depend on the paper-fills toggle (F27, G12); ATAS's own rule is the positive precedent [AT-1] (§3.6); H5.
7. **Avoid:** idealised fills (ATAS "immediately in full" [AT-1]; Sierra's bid/ask sizes always 1 [SC-1]) → the queue-position, latency and partial-fill model of `24` §12.1 stays, and SCR-099 states its assumptions (F25); H2.
8. **Avoid:** an undocumented replay indicator (Sierra [SC-1]) and a symbol-only indicator (TradingView [TV-1]) → word + glyph + date + frame on every pane (F2, F4); H1.
9. **Avoid:** a free numeric speed field as the primary control (Sierra, up to 100000 [SC-1]) → presets anchored to budgets, a custom value within the API range as the secondary path (§4); H6.
10. **Avoid:** empty windows during replay (ATAS [AT-1]) and a mandatory restart (Bookmap [BM-1]) → the terminal's panels stay, fed by the replay clock (SCR-097), with the per-pane opt-out of §3.6; H3, H7.

## 3. Heuristic evaluation

**Relationship to DEMO / LIVE (both session kinds).** Environment and execution mode are two axes (`24` §1.2), and the sources disagree on the first: `24` §1.2 and `23` §11 say a paper fill during a replay of live-recorded data is `environment = "live"`, `execution_mode = "replay"`, while `24` §13.7 says the environment "stays the paper account's `demo`" and the shipped session service accepts only a demo account the user holds as `paper_account_id` (`sessions_service.py`; C3 — the r1 draft of this memo cited `24` §2 for `environment = demo`, which it does not say). The env badge is the status row's first chip and the CMP-074 band is global (E11-D02 §10), so the design defines what both read on `/replay`, **never the workspace environment**: (1) **with a paper account** the badge reads `DEMO` — the paper account's environment, the one the fills are attributed to — beside the chip (`DEMO · REPLAY 13:38:04`); (2) **with no paper account** (a session the service allows and a trader can open from a LIVE workspace) the badge position reads `NO ACCOUNT` (accessible name "No account attached — replay of recorded data; nothing can be placed") and the transport header states "no account attached" — not "VIEW ONLY", which would re-create F1's overload against the Viewer role's read-only SCR-097 variant (`14` §12.2) and SCR-124's "view as (read-only impersonation)". In both kinds the CMP-074 band position follows the same rule — `DEMO`, or `REPLAY · no account attached` as a text-first state with no environment hue (a `15` CMP-074 amendment, G13; the owner decides the wording, Q13) — and leaving replay restores the workspace band through the `R` confirm, which names the environment being returned to (F6). **LIVE therefore never appears inside replay chrome by rule:** for the paper-account kind the demo-only gate makes it impossible by construction; for the no-account kind the rule is the design's own, D02 draws both frames (A4) and the no-account-in-a-LIVE-workspace frame is in the 2-second test (§6.4).

### 3.5 Recorder emptiness as the normal case (heuristic)

Replay depth equals recorder depth (`14` §0.5.3). The shipped facts make partial and empty windows the **first-weeks default**, not an edge case: recording starts only on chart-open, a manual add or an open position (ADR-0015; E16-D01 F4), `retention_days` defaults to 30, `GET /market/data-coverage` is capped server-side to the last 90 days (`24` §13.3.1, #2216), covered intervals merge across ≤1000 ms, a window with no covered interval is refused with `no_data_recorded` (422), and a partly covered window is accepted with every uncovered span seeded into `coverage_gaps` (INV-B12-d) and a `ReplayGap` marker placed before the events of its instant. The engine's per-session `GapPolicy` is `skip` or `stop` — exactly SCR-097's "[Skip gap] [Stop here]".

### 3.6 Live panes beside replay (US-RPL-005; heuristic)

The precedents split three ways: ATAS empties every non-selected window [AT-1], Bookmap cannot show live at all [BM-1], Sierra lets other chartbooks' windows stay live [SC-1], and TradingView keeps the trading panel and quotes on real-time data during replay [TV-1] — the last is the hazard. **PROPOSED default: no live pane** (SCR-097's `[ ] keep live panes` unchecked); **opt-in per pane** (US-RPL-005's scenario) and **only for read-only panes** — the watchlist, a second-symbol chart, the tape — persisted with the session (US-RPL-009 restores the pane configuration); **the order-entry surfaces are replay-locked unconditionally**: on `/replay` the ticket, the DOM ladder's click-trading and the positions grid bind **exclusively to `session.paper_account_id`** — the server-validated demo account (`24` §13.7: an `exchange_accounts` row with `env = 'demo'` that the user holds) — or to no account at all, whatever the paper-fills toggle says; the header's account selector and the trade-group targets are not rendered and there is no fan-out (one paper account, one leg); with paper fills on they act on the paper matcher inside the replay frame (§3.7), with paper fills off they are read-only with the reason at the point of action, never hidden (`14` §0.5 item 5, E17-D01 D13 — the pattern of the >25× disable) — and they are never eligible for the live opt-in, so US-RPL-005's "live" badge never sits on a trading-capable pane (its scenario needs none). The reason is the TradingView hazard itself [TV-1]: a real-account ticket beside replaying panes places an ordinary live order on stale prices that no server can tell from any other live order — it is not a replay-origin order, so RP-E01's structural isolation (`23` §11, `24` §8, `24` §13.7) does not cover it (F24) — and the UI rule is the only guard, which is why it depends on no toggle (F27, G12; C-2.11's separate chrome). Q6 asks the owner which read-only panes may opt in, not whether the lock holds. Two edges `23` §11 itself raises — its example is "a live DOM beside a replayed chart" — go to Q6 with a leaning: a read-only DOM may opt in for another symbol only, and **same-symbol live panes are refused**: two "nows" of one symbol on one page defeat the date carrier (F4). ATAS states the whole rule outright — "Real-time quotes and your real positions are not shown in this ATAS window. To trade live, exit Replay or open a second copy of ATAS" [AT-1] — the positive precedent for A8. An opted-out pane shows **no** replay frame or chip, its normal env badge and its feed chip. The remaining problem is lexical: "live" means the environment (`14` §0.5.1), the healthy feed (E17-D01's chip vocabulary) and, in US-RPL-005, "not replaying" — F1 asks the owner to settle the word for the opted-out pane (Q3); until then the memo proposes the chip's accessible name "Real-time — not replay".

### 3.7 Paper trading in replay (US-RPL-006; heuristic)

**PROPOSED: the real ticket (SCR-060 as E30-D02 specifies it) in a distinct state, not a separate surface.** Rehearsal is the point (US-RPL-006 "rehearse execution"), so the keys (E30-D01 SC-1), the arm model and the bracket must be the ones the trader uses live; a second ticket would double the design and implementation cost and train the wrong hands. The distinct state has five carriers: the pane sits inside the replay frame with its chip; the submit label carries "simulated" (SCR-097 checklist "paper-trading controls drawn with 'simulated' labelling"); the arm pill reads `ARMED (REPLAY · DEMO)` with the paper account's label and its second line "REPLAY · simulated fills" — a CMP-229 replay state the catalogue lacks (G15), because the indicator is global-scope (E30-D02 D15) and an arm must never cross the replay boundary. The arm is a **server object**, not a pill state: `22` `POST /settings/arm` returns an `arm_token` bound to the login session (`ttl_seconds` 30–3600, default 300), sent as `X-Arm-Token` on a live account's risk-increasing order mutations; arming "needs a fresh step-up while a live account is within the caller's reach: for the Owner whenever one exists" (`403 step_up_required`, class `live_enablement`); "a token records whether it was issued under that step-up; one issued without it never satisfies a live mutation"; and "disarming, session end, kill-switch engagement or a risk-cap breach invalidates it immediately". So entering `/replay` drops the workspace's arm with its reason (E17-D01 D12's auto-disarm pattern) and the `R` confirm drops the replay arm — each a `POST /settings/arm {armed: false}`, server-invalidated (C-2.12, C-2.21) — and the boundary is anchored on the token's own rule: a replay arm minted **without** the live step-up can never satisfy a live mutation, which is "an arm never crosses the boundary" enforced synchronously, with the pill as its mirror (F34). The cost the contract sets today is Q15: the Owner, for whom the step-up applies whenever any live account exists, would answer a step-up to arm a rehearsal ticket and again at every TTL expiry inside a 2 h study, which breaks US-RPL-006's rehearsal; the leaning is a demo-/replay-scoped arm request (`scope: "demo"` or `replay_session_id` on the request) that skips the live step-up and mints a live-incapable token, keeping the TTL and E30-D02 D15's `mm:ss` expiry cue — contract-first in `22` by E30-S04 (#1088); research PRs never edit `22`. ### 3.8 Scrub latency honesty (heuristic)

The budgets disagree (C2): SCR-097 "seek ≤1 s to any point within the loaded window", US-RPL-004 "≤2 s", `24` §13.7 "≤2 s for any point in a recorded day", `30` §6.3 exit 8 "within 1 s for a 200-depth symbol", and the ticket's "1 s p95 / 2 s ceiling". ADR-0035 (proposed) measured 8.6 s p95 at the 300 s snapshot interval as first written and **0.41 s p95** with 60 s snapshots and collapsed deltas (synthetic 200-depth, laptop), and the control endpoint says a seek "is never cheaper than a snapshot interval (60 s)". Nielsen's limits [NN-1] frame the perception: 0.1 s "reacting instantaneously", 1 s "flow of thought … uninterrupted", 10 s "keeping the user's attention". The design therefore has **three rungs**, each with a text carrier (F17, F18):

| Elapsed       | What the trader sees                                                                                                                                                                                                                                                                                                                                                                                      | Why                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| drag, <0.1 s  | the thumb's time readout moves with the pointer (local); the panes keep their last frame; one `seek` is sent on release, never per pixel                                                                                                                                                                                                                                                                  | instant feedback without a round trip; the control endpoint is rate-limited                            |
| 0.1 s – 1 s   | the transport's state line "Seeking to 13:52:04…"; the chip's clock shows the target; nothing animates                                                                                                                                                                                                                                                                                                    | the flow stays uninterrupted; eased bars would mark instants that never happened (E11-D06 D20's logic) |
| 1 s – 2 s     | the same line gains the cause and the elapsed time: "Rebuilding the book from the 13:51:00 snapshot · 1.4 s"                                                                                                                                                                                                                                                                                              | the budget's p95 is 1 s; past it the trader must know why                                              |
| >2 s (breach) | the cause line stays, the controls stay live, Pause — or `Esc` while the transport or the scrubber thumb has focus (§3.2: in the ticket `Esc` clears the ticket, on the chart it cancels a drawing) — cancels the seek (B12: `CANCEL` from `buffering` returns to `paused`, cursor unchanged) and the state line then reads "Seek cancelled — try again" with the unchanged time; at 10 s a cancel button | the ceiling; never a spinner alone; never a frozen transport                                           |

Every pane flips **together**: a seek produces one `snap` with reason `replay_seek` per subscribed topic (`23` §11), so the design must not stagger panes. The observed tolerance is measured in T3 (§6.3) and is not claimed.

**Every backward move is a seek (F33).** The contract has no reverse step — `step_events` / `step_ms` are `minimum: 1` — and INV-B12-b lets only `SEEK` move the cursor back; `24` §13.7 calls `reposition` "the only way the cursor moves back" and bounds a seek at ≤2 s for any point in a recorded day, and `22`'s control description says a seek "is never cheaper than a snapshot interval (60 s)". So `←`, `Shift+←` and the #1 task — stepping back through a trade (T3) — are seeks with a book rebuild each, under the rungs above: repeated back-steps coalesce into one `seek` per 250 ms or on key-up (never one per keypress), the rungs are shown for each, the panes are never staggered, and T3 logs back-step latency separately from pointer seeks (§6.3). E26-T03 / E26-T05 decide a bounded reverse buffer or a denser snapshot cadence (G14). One more honesty rule: a `CANCEL` the chart held while `buffering` replays on its next entry into `buffering` (`24` §13.7), so the seek after a cancelled seek can cancel itself — the state line says "Seek cancelled — try again" rather than staying silent (C5).
