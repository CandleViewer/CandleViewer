## 4. The decision

### 4.1 The rule, written before the run (RULED BQ-06)

Reject any strategy whose AT-tree build at 500 is over 100 ms or whose drag cost at 500 is over 2 ms. Among the
survivors, keep the ones that leave every drawing reachable by keyboard: a strategy that makes a drawing unreachable
fails WCAG 2.1.1 whatever its speed. If more than one is left, the tie-break decides. Exactly one strategy is
recommended, with the reason.

### 4.2 The recommendation

**Recommended: (c) visible, selected and focused drawings only.** The harness's reason: survivors of the gates at 500: (b), (c); reachable by keys alone at 500: (b), (c); the gates do not separate them, so the tie-break decides, and it is accessibility, not cost (BQ-06): the strategy that gives each drawing its own named, focusable node (setsize and posinset, pressed state) wins; (b) gives 0 per-drawing nodes and nests a second application role, so it loses although it is cheaper at 500 ((b) 78 nodes, AT p95 6.68 ms, drag p95 0.085 ms; (c) 209 nodes, AT p95 10.72 ms, drag p95 0.995 ms).

Both (b) and (c) pass the gates, (c) with a comfortable margin at 500, so the rule reaches its last step and the
tie-break decides. The tie-break is accessibility, not cost (RULED BQ-06): (c) gives every drawing in the window a real,
named, focusable node (4.1.2 per object); object navigation, the readers' element lists and their virtual cursors work
on it without depending on `aria-activedescendant`, whose reader support is uneven `(heuristic)`; it keeps `D02`'s drawn
pattern (one roving group, `aria-setsize` / `aria-posinset`, `D02`:325) and answers F-04 as written (`D10`:854). (b)
nests a second `role="application"` inside the chart wrapper's (`E06-D03`:103), a browse-mode trap and a finding in
itself (FK-04). (a) fails the drag gate at 500.

### 5.2 The rule (what the surrogate set holds)

1. **Window = the drawings whose bounds intersect the visible range, plus every selected drawing, plus the focused
   one.** The visible range is the time range of `viewportChanged`; the price range is added once the engine reports it
   (GK-02). A hidden drawing is not in the window.
2. **`aria-setsize` is the full count of the pane's drawings; `aria-posinset` is the rank in the full time-then-price
   order** (`D02`:428). "Item 3 of 12" stays true when the window drops items.
3. **The focused surrogate never leaves the window.** If the viewport moves away from it, it stays until focus moves.
4. **A window change never moves focus.** A resize, a pan or a zoom keeps `document.activeElement` (the rule the engine
   already tests for a resize, `ENG/README.md`:565, BQ-157). Surrogates are added and removed around it; when a drawing
   moves, the existing nodes are not re-ordered (that would move the focused node) and `aria-posinset` is updated
   instead.
5. **The set is fed from the engine's own visible-window query and `viewportChanged`; it is never recomputed**
   (`T Tech`). Today the query returns `null` (`ENG/src/api/chart.ts`:312); §15.1 states what E11-S13 must give.
6. **Reachability.** A drawing outside the window is reached by the tree (`D02`:376) or by moving the plot stop's cursor
   until it enters the window; both paths are keyboard paths. Harness: 500 of 500 drawings reached by PageDown in (c), the focused surrogate stayed through pan +300, pan -600, zoom to 40 bars and a plot resize with focus kept: true.

## 6. The keyboard creation flow, by anchor class (RULED BQ-08)

The flow is parameterised by anchor count (`D02`:266); the registry (`D02` §2.2) is the index. Tools are table rows; a

### 6.1 Common to every class

- Arming moves focus to the plot stop (`D02`:388). The pending anchor starts at the data cursor, else the last close.
- `←` / `→` move a bar, `↑` / `↓` a tick, `Shift` ×10, `Ctrl+↑` / `Ctrl+↓` cycle the snap (`D02`:388).

  the tool is disarmed (`D10`:530, VC-16).
- No creation needs a drag (`D02`:266). No pointer event is needed for any row below (`T AC2`).
