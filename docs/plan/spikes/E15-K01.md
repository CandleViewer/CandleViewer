## 0. Read first: what this run is and is not

- **The panes are stand-ins.** The engine has no candle, indicator or drawings layer yet (`layers/index.ts` is a
  placeholder; E18/E19 and E14-T03 open, none `blocked_by` of this ticket). The harness draws the instanced
  work those layers will issue on real WebGL2 (§2.1), imports nothing from the engine package or `apps/web`,
  and mirrors (does not import) the bench's percentile, admissibility, seeded generator and B3/B4 GL load
  (BQ-02 ruling; harness README). Every number is a stand-in number; GK-1 re-measures with the real layers.
- **The plot is 1600 × 900 CSS px at a pixel ratio of 1** (results `params.plotArea`), split into the N
  panes. "16 panes under 16 ms" is a fill-rate-sensitive result: a pixel ratio of 2 draws four times the
  pixels, and a larger plot more, so a high-DPR or larger display can cross where this host did not (OL-1
  measures at the reference machine's own size and ratio).
- **The host is below the reference class.** Intel Core Ultra 7 366H, 16 logical CPUs, 15 GB, kernel
  6.18.33.2-microsoft-standard-WSL2, Node v22.14.0, Chromium 156.0.8078.4 (Playwright 1.64.1, headless), build
  `d29f49a62a`. Its two GPUs (an NVIDIA RTX PRO 500 Blackwell laptop GPU, "dGPU", and the Intel integrated GPU,
  "iGPU") are reached through WSL2's translation layers (Mesa d3d12 under ANGLE's GL backend), not the
  reference path (ANGLE on D3D11, Windows). SwiftShader is the bench's pinned CI flag set (software GL). Load
  average before each job: median 1.52, max 7.13 (other work shared the host; start 0.32, end 8.91).
  Under the #220 evidence rule (`KR`) **a budget met here is conservative evidence; a budget missed here is
  inconclusive** and is re-measured on the reference machine (owner legs, §10).
- **No reference number is claimed.** The ticket's three devices (reference Electron, reference Chromium, a
  low-power iGPU at 4x CPU) are owner legs; their cells ship `owner-leg-pending` (§10). The host's iGPU at 4x CPU
  is reported as a stand-in for the weak device and turns out not to be weak (§3.2).
- **Method.** Playwright drives headless Chromium; each job in a fresh browser context, in a seeded shuffled
  order (`--seed 371`). Frame time = every pane submitted, every context flushed, then a 1x1 `readPixels`
  (GPU completion inside the number; `gl.finish()` does not wait in Chromium). Per rep: nearest-rank p95 over a
  10 s window after a 2 s warm-up (≈ 600 frames at 60 Hz; n stated where under 600); per cell: the median of
  three rep p95s. Below 100 frames the figure is labelled **max** (BQ-14). The ≥ 600-frame target is
  unreachable for cells slower than about 17 ms per frame (two GPU cells, n = 499 and n = 521) and for every
  SwiftShader cell (n = 29–368).
- **Wall time.** Main pass 2,414 s (40 min 14 s; 55 cells × 3 reps = 165 runs, three 70 s trigger runs, 24
  sync jobs) plus a supplementary `--resume` pass of 95 s for the SwiftShader probe windows (§2.3): 2,509 s
  measured, inside the 45-minute budget. The results hold 57 cells / 167 runs: the main pass's 55 and the
  probe pass's two one-rep cells. No cell failed or hung.

## 2. The harness and the method (throwaway)

### 2.1 The stand-in scene

Each pane draws the 100k-bar seeded series (seed 20260928, generated in `lib.mjs`), panning one bar per frame
at 6 px per bar, with one program (an instanced segment quad) and one buffer per draw slot. The plot is a fixed
1600 × 900 CSS px at a device pixel ratio of 1 (`page.html`, `page.mjs`), tiled into the N panes; fill-rate
cost scales with the pixel ratio squared and the plot's area, so the figures hold for this size only (§0):

| Density         | Draws per pane | What it stands in for                                                                                                 | At 16 panes (draws, KB uploaded per frame) |
| --------------- | -------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| bare            | 3              | grid, wicks, bodies                                                                                                   | 48, 35                                     |
| indicators      | 20             | bare + the R1 set: 7 overlay lines, 4 sub-panes (volume + MA, RSI, MACD + signal + histogram, Stochastic + ATR + OBV) | 320, 311.75                                |
| drawings        | 21             | indicators + 200 trend lines, all transformed and submitted every frame (no culling: conservative)                    | 336, 361.75                                |
| orderflow-proxy | 8              | `load.mjs`: 8 × 2,500 instanced quads and a heatmap column every 100 ms — an **estimate** for footprint / DOM panes   | 32 at N = 4                                |

Topologies (BQ-05): **worker-shared** (one render worker, one OffscreenCanvas and context, a viewport and scissor
per pane — the default), **worker** (one worker, one context per pane) and **inline** (main thread, one context
per pane).

### 2.2 What else was measured

The context-count probe (20 contexts on the main thread, 20 in a worker), the warm-up of every cell (settle,
§9 T4; the first frame), three 70 s runs for the trigger as ruled (§9 T5), and the sync fan-out (§8).

### 3.3 Marginal cost of one pane

Least-squares slope per leg (§3.2): **0.17 ms (bare), 0.22 ms (indicators), 0.29 ms (drawings)** per pane on
the default topology (dGPU); 0.46 ms on the iGPU; 1.02 ms (dGPU) and 0.90 ms (iGPU at 4x) on the main thread;
the order-flow proxy's slope is flat over N ≤ 4 (−0.05). Adjacent-N slopes on the default topology run
−0.58 … +1.36 ms (pass A −0.45 … +1.36, pass B −0.58 … +1.06; results `curves[].marginalMsPerPane`): the step between neighbours is inside rep-to-rep noise
(§3.5), so the least-squares figure is the one to use. The per-pane costs of the stand-in densities differ by
about 0.1 ms; the GPU round trip, not the draw count, dominates this host's numbers.

### 3.4 Topology and the live-context limit (BQ-05)

The context probe created 20 WebGL2 contexts: on the main thread the first four were lost as contexts 17–20
were created (16 live), on every device; **in a worker, 16 of 20 were lost (4 live)**, on every device. The
per-pane-context worker leg lost 2 contexts at N = 6 and 12 at N = 16 (invalid cells). So one context per pane
cannot be the worker topology above four panes in this Chromium (156, headless, on this host; to be confirmed
in Electron on OL-2): the multi-pane render worker needs **one shared context with a viewport and scissor per
pane** (the default measured here), or several workers. That is a constraint for E15-T02 (#403), a row for the
`26` §16 owner (§12) and a case for E11-Q07 (#519, the engine's GPU, driver and runtime matrix charter) to
confirm on other runtimes (FK-1); the engine's `host/mount.ts` already notes a browser live-context budget of
about 16, which holds for the main thread only.

## 5. The rule, written before the run (BQ-06, BQ-10, BQ-12, BQ-14) — every value PROPOSED

Fixed as the `RULE` block at the top of `E15-K01-harness/run.mjs` before the full run started; the results
file records it under `rule`. Git cannot show that order (`run.mjs` was first committed with the results);
the evidence is this section and the run's own `rule` record, which the run wrote from the block it applied
and which matches `run.mjs` value for value. The changes made after the run are listed, none of them a
threshold: D-6 (the outlier reading, the only change to how the rule reads) and D-8 (offline re-analysis of
stored data and probe guards added after the r1 lenses).

1. **Per cell** (leg, density, N): p95 frame time per rep, nearest rank over the 10 s window after a 2 s
   warm-up; the cell's figure is the **median of the rep p95s**. Fewer than three reps: not admissible. A cell
   where any context was lost is **invalid** and leaves the curve. Below 100 frames the figure is labelled max.
2. **Crossings**: the first measured N whose p95 is over 16.6 ms (budget #1; C-14.2's < 16 ms reported
   beside it), 18.2 ms (US-LAY-001) and 33.3 ms (the floor); the interpolated crossing is linear between the
   neighbouring measured N and labelled interpolated.
3. **Marginal cost** per pane: the slope between adjacent measured N, and the least-squares slope and
   intercept per leg.
4. **Ceiling**: `recommendedMaxPanes` (leg, density) = the largest measured N such that every measured
   N' ≤ N has p95 × 1.2 ≤ 16.6 ms (p95 ≤ 13.83 ms), capped at 16 (SCR-020); 0 when N = 1 fails. A ceiling at
   the largest measured N below 16 is a lower bound. `recommendedProfile` = `reduced` below 4, else `full`.
5. **AC1**: |A − B| / min(A, B) ≤ 10 % per configuration, on the drawings density of the default topology.
6. **AC4**: any valid 6-pane drawings cell over 33.3 ms is named a roadmap exit-criterion risk.
7. **Sync (BQ-12)**: main thread when the main-thread p95 per frame at 16 panes, unthrottled, is ≤ 0.5 ms.
8. **The probe** (`frameProbe.ts` `classify`): the same budget, headroom, cap and four-pane floor, fitted
   on a 120-frame window at one pane and one at four; the harness applies a mirror (`lib.mjs`) and the app's
   unit test checks the app's `classify` reaches the same answers on the measured windows.
9. **The runtime trigger (E15-D12 BQ-10, RULED; calibrated here)**: p95 over a rolling 60 s above 18.2 ms,
   visible and focused only, 10 s warm-up, single frames over 200 ms dropped. Calibration checks:
   - **T1** no healthy cell (unthrottled, GPU device, p95 × 1.2 ≤ 16.6) fires the trigger (cell-window form);
   - **T2** per leg, the first N over 18.2 ms against the ceiling: the trigger must sit above the ceiling;
   - **T3** the 200 ms outlier rule stays if frames over 200 ms are under 1 % of the healthy frames;
   - **T4** the 10 s warm-up stays if every valid GPU cell settles within 10 s (settle = the end of the last
     1 s bucket, before warm-up + 5 s, whose p95 is over 1.25 × the cell's window p95); else it rises to the
     measured settle, rounded up;
   - **T5** three long runs of 70 s apply the rule exactly as ruled (a healthy 16-pane dGPU run must not fire);
   - **18.2 ms stays** (it is the product promise, never tuned to the data); a weak leg that never crosses it
     is reported, not "fixed".
     The probe's own warm-up = max(30 frames, the measured settle × 60 frames).

## 6. The capability probe (`apps/web/src/lib/capability/`; BQ-10)

- **`frameProbe.ts`** (pure): `classify(windows)` → `{ p95FrameMs, recommendedMaxPanes, recommendedProfile,
paneCount, sampleCount }` (a fitted slope ≤ 0 is noise: the top window's p95 is charged to its panes instead

  starved of frames); `warmWindow`; `percentile` (the bench's nearest rank); `describeMeasurement` (the

  `reducedTrigger(frames)` → `{ fired, p95FrameMs, frameCount }`, the E15-D12 trigger as calibrated (§9); its
  window is full when the kept frames span 60 s and, each counted as at least 1/60 s, cover half of it (a long
  hidden gap does not make a full window).
  Constants: `FRAME_BUDGET_MS` 16.6, `HEADROOM` 1.2, `HARD_CAP_PANES` 16, `FULL_MIN_PANES` 4,
  `WARMUP_MS` **7,000** of clock time (§9 T4: was 30 frames; D-9), `WINDOW_FRAMES` 120 or `WINDOW_MAX_MS`

  then four; at each it drops a 7 s warm-up on the caller's clock `now` (7 s at any refresh rate, where the
  run's 420 frames would be 2.9 s at 144 Hz) and collects 120 frames or 13 s (window time = the summed frame
  times, each at least 1/60 s), so it takes 18 s at 60 Hz and **at most 40 s plus four frames on any device**

  `capability.profile_measured {p95FrameMs, recommendedProfile, paneCount}` once; a store that is full or
  blocked (it throws on read or write) loses only the memory: the probe still measures, reports and resolves.

- **No sniffing.** `test/lib/capability/noSniff.test.ts` greps every source file of the module for the user

  against an example it must catch (AC2's grep; the DoD's "grep assertion in CI": it runs in
  `unit-frontend`). Frame time is the only signal the BQ-10 ruling allows.
- **Privacy** (`T` Security notes): stored and reported values are aggregate timing and a pane count; no
  identifier, no renderer string; nothing is sent by this module (the caller's analytics seam carries the event,
  D12 C-11's rule: a bucketed frame time, never a raw device profile beside a user id).
- **Tests** (98, all passing): fast / borderline / slow / one-pane-fails / noisy with one 200 ms GC spike that

## 8. Sync propagation threading (BQ-12; for E15-T03 #436)

One `sync {groupId, timeRange, crosshair}` per frame to N panes (three binary searches over 100k bar times per
pane), on the host's iGPU device; main-thread ms per frame, 360 frames per rep after 60 dropped, three reps:

| CPU |   N | fan-out on the main thread: main p95 | posted once, fanned out in the worker: main p95 / worker p95 (worker unthrottled at 4x, FK-2) |
| --- | --: | -----------------------------------: | --------------------------------------------------------------------------------------------: |
| 1x  |   6 |                                 0.09 |                                                                                  0.06 / 0.035 |
| 1x  |  16 |                                0.095 |                                                                                  0.06 / 0.045 |
| 4x  |   6 |                                0.735 |                                                                                  0.48 / 0.035 |
| 4x  |  16 |                                0.745 |                                                                                   0.50 / 0.04 |

**Recommendation: keep sync propagation on the main thread** (rule §5.7: 0.095 ms at 16 panes ≤ 0.5 ms; 0.6 %
of 16.6 ms). Moving it to the worker saves 0.035 ms per frame unthrottled and 0.25 ms at 4x CPU, because posting
the one message costs most of what the fan-out costs; at most one `sync` per frame (`26` §6) keeps it there.
At 4x CPU the main-thread fan-out misses the 0.5 ms rule (0.735 / 0.745 ms at 6 / 16 panes), while the
posted-once variant's main-thread cost meets it (0.48 ms at 6 panes) or touches it (0.50 ms at 16; the rule is
≤ 0.5). Its worker column at 4x (0.035 / 0.04 ms) is unthrottled (CDP's throttle does not reach a worker,
FK-2) and not comparable. The rule is fixed unthrottled (§5.7), so the recommendation stands; the weak-device
direction favours the worker, and OL-3 re-checks it at 4x on a true weak device. To be linked from #436 at
merge (§13).
