## 0. Read first: what this run is and is not

- **Client portion only.** Backend latency is out of scope (E29 owns the 50 ms; the span `exchange.place_order`
  is where it is measured). The submit posts to a loopback stub. **Budget #4 end to end on Bybit demo
  (`06` row 4) is PENDING E29-K01 (#843)** (section 8).
- **The ticket is a stand-in.** SCR-060 and `packages/order-ticket-core` are not on `main`. The reducer is a
  pure stand-in for `size()` + `validate()` (scaled-bigint parsing, as Decimal parsing would be). The real
  parts are the keymap path (`KeymapHost`, dispatcher, registry), the `<Chart>` binding over the engine and
  the Electron shell. The spike page does not boot the SCR-010 shell.
- **The single-key buy is a stand-in.** `B` is `ticket.side_buy` (sets the side, not arm-gated), so no
  single-key arm-gated "buy market" exists. `Ctrl+Enter` (`ticket.submit`) is measured as is; the extra key
  exists only on the spike branch.
- **The host is below the reference class** (section 2). A budget met here is conservative evidence; a budget
  missed here is inconclusive (the E15-K01 evidence rule) and goes to a reference-machine owner leg.

## 1. Method

1. Pin `main` (sha TBD) and the fixture capture; fix the seed. Section 4 is written before any run.
2. The harness builds the web app with `CV_SPIKE_E30_K01=1` and drives Electron through Playwright
   `_electron` against the loopback stub (`apps/desktop/e2e/perf/`), egress guard on, name resolution
   failing for every non-loopback host. Headless Chromium is an optional cross-check.
3. The spike page mounts the real `KeymapHost` (armed through `setArmPort`, confirm skipped: BQ 6), the real
   `<Chart>` (engine in `worker` and in `inline` RunMode), a stand-in ticket and a WS client. The recorded
   BTCUSDT capture is replayed through the stub's gateway at a rate scaled to the 350 KiB/s of `23` section
   16.3 (the scale is in the results: BQ 8).
4. Matrix: 3 reducer placements x 2 RunModes x 2 runs; per cell 1 000 samples per trigger after 50 warm-up
   samples, paced at 20 Hz. Each run is a fresh Electron profile.
5. Time is attributed on the worst cell of each budget with Electron `contentTracing` (`CV_K01_TRACE=1`):
   reconciliation, layout, reducer.
6. The decision table (section 6) is filled from the results, then the acceptance scenarios are applied
   (section 7).

## 3. Measures

| Measure               | Start                           | End                                                           | Input method (BQ 7)                                           |
| --------------------- | ------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------- |
| `recompute_end_a`     | input event `timeStamp`         | the reducer returns (worker placement: the reply arrives)     | `dispatchEvent`                                               |
| `recompute_end_b`     | the same                        | first `requestAnimationFrame` after the derived fields commit | `dispatchEvent`                                               |
| `click_to_fetch`      | `click` `timeStamp`             | mark immediately before `fetch()` in one transport port       | Playwright `page.mouse` (trusted)                             |
| `hotkey_to_fetch`     | `keydown` `timeStamp`           | the same mark                                                 | Playwright `page.keyboard`: `Ctrl+Enter` and the stand-in key |
| `ws_orders_to_render` | WebSocket `message` `timeStamp` | first rAF after the commit                                    | stub frame; information only                                  |

- Triggers for recompute: a price keystroke, a quantity keystroke, a sizing-mode switch.
- `fetch()` is wrapped directly, not through `apiFetch`/`csrfFetch`, because the CSRF recovery can retry once
  and put a second `fetch()` into a sample (`apps/web/src/lib/http/csrfFetch.ts`). The POST's Resource Timing
  `fetchStart` is recorded as a cross-check row `<kind>_resource_timing`.
- The end-B figure is read in the rAF callback, before paint: paint completion comes from the trace (step 5).

## 4. Budgets and thresholds (PROPOSED; fixed before the run)

| Measure               | Budget           | Owner                                                                |
| --------------------- | ---------------- | -------------------------------------------------------------------- |
| Recompute, end B      | 8 ms p95         | SCR-060 Performance (`14` line 1474)                                 |
| Recompute, end A      | 8 ms p95         | E30-T01: `size()` + `validate()` (E30.json, Performance notes)       |
| Click to `fetch()`    | 50 ms p95        | US-DOM-007 (`11` line 2108); BQ 3                                    |
| Hotkey to `fetch()`   | 50 ms p95        | US-ORD-006 NFR (`11` line 3020); BQ 3                                |
| WS `orders` to render | information only | `23` section 16.3 tick to pixel < 40 ms p95; `06` row 3 < 100 ms p95 |

- Sampling (BQ 11): 1 000 per cell, warm-up discarded, p50 / p95 / p99 and the worst 1 % (mean of the slowest
  1 %), nearest rank. Two runs must agree within 15 % at p95 or the cell is rejected as noisy.
- Verdicts: only a reference-class host can FAIL; a below-class host that meets a budget reads PASS and one
  that misses it INCONCLUSIVE; a noisy cell is never decided; the calibration widens nothing.
- BQ 3 caveat to record in section 7: `06` budget #4's own arithmetic (50 ms backend + 250 ms Bybit demo REST,
  plus 20 to 50 ms Tailscale RTT) leaves 0 ms for the client. The 50 ms gesture-to-`fetch()` figure is adopted
  for PASS/FAIL here; a `06` section 5.2 amendment is a separate docs PR and K01 edits no `06`.
- BQ 4: SCR-060 says click to ack <= 500 ms p95, `06` budget #4 says < 300 ms on demo (500 ms is the live
  figure). `06` owns it; routing the `14` text fix to its owner is a follow-up, not this spike.
