## 4. Determinism is a hard requirement

Same hardware class, fixed driver and fixed Chromium is a **requirement**: an option that cannot meet it is dropped, not scored down. The reason is the gate itself: the median of 5 runs on headless Chromium over a fixed dataset, failing on a regression above 5 % (`CON`:620). A gate that cannot reproduce itself is worse than no gate. The normative threshold is 5 % (`CON`:620 = C-9.1 #16, C-13.9, `06-performance-and-load-standard.md` §7.4), cited here as a premise. `ADR13`:60 and the `EB` header say 10 %. This PR edits neither: the ADR-0013 corrections are the orchestrator's amendment PR, and the stub header rides E03-T14.

Consequences, stated once:

- O7 cannot replace the GPU gate for B7 or for frame-time targets. It stays the recorded lane. The matrix numbers "are comparable only with a baseline from the same runner class" (`PEM`:19-20).
- O4 is dropped on this rule: instance class and driver can differ between starts. A pinned machine type could change that; it is UNVERIFIED.
- O5's hardware class is not stated; it is UNVERIFIED until the plan page names it.
- O2 adds a cold start per job and shared-host neighbours; whether the 5 % gate tolerates that is a question for a measurement we cannot run without a GPU.
- A baseline moves only by an approved commit that states the cause (`ADR13`:60).

## 5. Who may run on the runner (trigger policy)

Trigger policy often removes more risk than the isolation layer, and it costs nothing, so it is a criterion in its own right.

**Visibility.** The repository is public (API setting, read 2026-11-01). `docs/ci-runbook.md`:156 says "this public repository"; `ADR13` rule 6 (`ADR13`:62) says "private and single-org" and is stale on this point. Correcting it is part of the orchestrator's ADR-0013 amendment PR, not this spike's (C-4.9). Every option below is evaluated under public visibility.

Trigger-policy options, applicable to any isolation layer:

| ID  | Policy                                                       | Who can start a run on the runner                       | Under a public repository                                                                                                                                                                                                                                                                                                                                                                 |
| --- | ------------------------------------------------------------ | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | Dispatch and schedule only (today's `perf-*` line)           | Maintainers, and the clock                              | Safe default; no per-PR number                                                                                                                                                                                                                                                                                                                                                            |
| P2  | `pull_request` from same-repository branches, path-filtered  | Any account that can push a branch to this repository   | Depends on who holds write access; fork PRs must stay excluded; PR code reaches the runner before any review                                                                                                                                                                                                                                                                              |
| P3  | `merge_group` only (`ADR13` Amendment 3 rule 6, `ADR13`:113) | Whoever enqueues a PR; enqueueing is the trust decision | The run executes in the base repository, holds only the declared permissions and receives no repository secret (rule 6). By the enqueue rule of `ADR13` rule 6 (`ADR13`:113), a PR is enqueued only after its approvals and green checks. P3 narrows who can start a run; it does not replace the isolation layer, since a `merge_group` run still executes reviewed code on our hardware |
| P4  | P1 plus P3                                                   | Maintainers, the clock, and enqueued PRs                | The stage 1 form of §7                                                                                                                                                                                                                                                                                                                                                                    |

Fork PRs never reach a self-hosted runner under any option. First-time-contributor approval gates are not a substitute for P3 on a public repository.

Isolation options under public visibility (O1 to O7 of §2):

- O1 to O3 and O6 (hardware we own): admit only through P1, P3 or P4; P2 is not recommended while the repository is public.
- O4 and O5 (fresh machines per job): P2 is workable because nothing persists, but the determinism rule of §4 drops O4 and leaves O5 UNVERIFIED.
- O7 (GitHub-hosted, software rendering): any policy, including per-PR runs on `pull_request`, since the machine is fresh and GitHub-managed.

Today's `perf-*` workflows already hold the line "dispatch only: never on a PR" (`perf-ws-load.yml`:3-4). The finding keeps P1 as the default until a trigger in §9 fires.

**Residual.** The "Who can start a run" column and the "dispatch only" line describe what the workflow files say, not what the runner enforces, and the enqueue-time review gate is procedural (branch protection requires `ci-required` only). Until that control exists, code that has not been reviewed can still reach the runner (a dispatch on any ref, a branch's own workflow file). §7 adds a runner-side admission control for this; until it exists the residual stays open and is named in `TM` §5.

**Follow-on, not done here.** If the recommendation is taken as P4, the PR-level `engine-bench` of C-9.1 #16 and `ADR13`:43 ("only if chart-engine changed" on the self-hosted GPU runner) change: per-PR numbers come from O7 and the GPU gate runs at the merge queue. That is a follow-on amendment to `ADR13`:43 and to C-9.1 #16 (a constitutional amendment, C-16), to be raised by the orchestrator. This PR does not make it.

## 7. Recommendation

Staged:

1. **Now (until T1 of §9: the first run of PR code on a self-hosted runner from any event other than `workflow_dispatch` on `main` only, `schedule` or `merge_group`).** Keep the runner dispatch-only, as it is. When E03-T14 builds the GPU job, build it as O1 plus the §5 policy:
   - the job runs as a non-root user in a container with no host mounts and a read-only root filesystem; the host enforces these settings (the runner itself ephemeral per job), and they are not set in the job's own `container:` key;
   - the workspace is wiped after each job;
   - the runner environment holds no shared secrets and the runner group is restricted to this repository;
   - egress is limited to the package registries and GHCR;
   - a runner-side admission control that a branch cannot edit decides which runs may use the runner: a runner group whose workflow allow-list is pinned to `main`, or a host-side pre-job check (whether this plan tier supports the allow-list is UNVERIFIED);
   - the job starts only from `workflow_dispatch` on `main` only, `schedule` or `merge_group` (policy P4 of §5), for `packages/chart-engine/**` changes, and never from `pull_request` or a fork. Taking this as policy needs the follow-on amendment to `ADR13`:43 and C-9.1 #16 named in §5; it is not done by this PR.
2. **When a trigger in §9 fires.** Move to O6 (a dedicated host reset from an image after each job) if the GPU is available on that host class, or to O2 if a GPU can be passed through to a microVM. The choice between them is made then, on a measurement this spike could not run.
3. **Always.** O7 stays the recorded lane. It is not a substitute for the GPU gate.

**Residual until the admission control exists:** the current controls are what the workflow files say, not what the runner enforces, and the enqueue-time review gate is procedural (branch protection requires `ci-required` only). Until that control exists, code that has not been reviewed can still reach the runner (a dispatch on any ref, a branch's own workflow file). `TM` §5 names it in the G1 row.

Why not defer outright: E03-T14 is blocked by this finding, and it needs the O1 settings and the §5 policy as its build list. Why not move to O2 or O6 now: no GPU runner exists and the workflow files route no PR code to a self-hosted runner today, so the risk the isolation layer would remove is not yet present.
