# Spike E42-K01: audit query plan and index strategy at 10 M rows

- Ticket: E42-K01 (#888). Decision record: `ADR-0025`. The ticket says ADR-0021, but 0021..0024 are
  already taken, so 0025 is the next free number.
- **Source of every number below: CI run
  [37011721464](https://github.com/CandleViewer/CandleViewer/actions/runs/37011721464), job
  `integration / audit-query-plan`, artefact `audit-query-plan-report`** (committed verbatim as
  `E42-K01-ci-report.json`). Harness: `services/api/tests/integration/audit/test_query_plan_spike.py` +
  `services/api/bench/audit_index/ci_spike.py`. It is opt-in: it runs on PRs labelled `run-audit-spike`.
- Environment: GitHub-hosted `ubuntu-latest` (4 vCPU), testcontainers `postgres:16-alpine` (16.15),
  `shared_buffers=2GB`, `maintenance_work_mem=1GB`, `work_mem=64MB`. Schema = real Alembic `head`
  (`0003_audit_log`: trigger, existing indexes, `pgcrypto` chain function).
- Data: **10,000,000 synthetic rows, measured directly (no extrapolation)**. They were loaded set-based
  (`INSERT … SELECT generate_series`, 10 × 1 M chunks, 506 s) with the chain trigger disabled for the bulk
  load only, then the five 0003 indexes were rebuilt. Heap 4.26 GB, indexes 3.42 GB. Mix: orders 72 %,
  auth 18 %, rules 5 %, admin 3.5 %; severity error+critical 1.5 %; 50 users.
- Method: keyset `ORDER BY event_ts DESC, id DESC LIMIT 50`, page 1 and a cursor 90 % deep (`@90%`).
  Each query is `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`, with 1 warm-up and then 20 runs (3 runs for
  plans slower than 1 s). Percentiles are nearest-rank, so with 20 samples p99 = max. The cache is warm,
  and the job is a CI runner, not the reference machine.

How to read this table:
- On the existing set (a), **21 of 22 rows meet the budget**. The one miss is `severity_actor` page 1: p95
  442.6 ms against a 400 ms budget (the `@90%` cursor gives 184 ms). The planner walks `ix_audit_time` and
  filters on `actor_label`, because the existing partial `ix_audit_sev` leads with `severity` and so cannot
  give `event_ts` order across the two-value `IN`.
- Adding the partial `(event_ts DESC) WHERE severity IN (…)` (e/f) brings it to **0.92 ms** (≈480×).
- The composite (b/f) halves `actor_action*` (0.15 → 0.08 ms). That is not needed for the budget.
- BRIN (c) changes nothing for ordered `LIMIT` queries.
- Sub-millisecond differences elsewhere (for example `action` 0.09 vs 0.8 ms) are noise from 4-vCPU runner
  scheduling, not plan changes. The plan node types are identical in those rows.

## Q1b: full text over a wide range vs the 2 s worst-case budget (p95 ms, 10 M rows)

The tokens are `v424242` (selective, a handful of rows) and `field_1` (common, in about 70 % of rows).
"naive" means `WHERE tsv @@ q ORDER BY … LIMIT 50`. "CTE" means the `WITH m AS MATERIALIZED (…)` form,
which forces the match set to be built first. "30d" adds a one-month `event_ts` window.

| Query form | selective, no GIN | selective, GIN | common, no GIN | common, GIN |
|---|---:|---:|---:|---:|
| naive, wide | 36,549 MISS | 36,098 MISS | 43.7 | **1.6** |
| CTE, wide | 30,863 MISS | **31.3** | 32,335 MISS | 3,361 MISS |
| CTE, 30d | 2,595 MISS | **27.6** | 2,700 MISS | 2,683 MISS |

Plans:
- naive: Gather Merge → Index Scan `ix_audit_time` with a tsvector filter. This is fast when matches are
  dense, because 50 rows arrive early, and it walks the whole table when matches are rare.
- CTE + GIN: Bitmap Index Scan `ix_spk_fts` → Bitmap Heap Scan → Sort. This is fast when the match set is
  small, and it sorts millions of rows when the match set is large.

**No single query form meets 2 s for both token classes. One GIN index plus selectivity-aware dispatch
does:** selective → CTE+GIN (≤ 31 ms), common → naive (≤ 1.6 ms). The planner's own row estimate
(`EXPLAIN` without `ANALYZE`) is a cheap selector. Without the GIN index, selective tokens miss the
budget in every form, including a 30-day window (2.6 s).

## Q2: per-INSERT write latency per index set (single-row INSERT through the real chain trigger)

Run https://github.com/CandleViewer/CandleViewer/actions/runs/37031566428 (artefact `E42-K01-ci-report.json`). Each INSERT is one row in its own transaction, so it takes
the chain trigger's advisory lock and computes the hash; it is timed individually and rolled back. Neither
the ticket nor `06-performance-and-load-standard.md` states an audit write rate, so the harness **paces at
500 INSERTs/s**, well above the expected tens per second of state-changing requests. Percentiles come from
the full sample, not max-of-N. The 100k sample is used for the full recommended set (g); the other sets use
20k to fit the job budget.

| Set | n | p50 ms | p95 ms | p99 ms |
|---|---:|---:|---:|---:|
| a existing | 20,000 | 1.862 | 1.986 | 2.210 |
| b + composite | 20,000 | 2.458 | 2.630 | 2.958 |
| c + BRIN | 20,000 | 3.076 | 3.507 | 4.050 |
| d + GIN (`ix_spk_fts`) | 20,000 | 1.959 | 2.156 | 2.511 |
| e + partial sev | 20,000 | 3.791 | 4.627 | 5.453 |
| f recommended (b+e) | 20,000 | 4.796 | 6.513 | 7.484 |
| **g f + GIN, measured together (full recommended set)** | **100,000** | **5.829** | **7.750** | **8.714** |

The sets ran in sequence on a shared CI runner, so differences of 1-2 ms between sets include runner
drift (e.g. d + GIN ran after the indexes of f were dropped and is faster than e). The robust comparison
is a (2.2 ms p99) against g (8.7 ms p99): the recommended set adds about 4 ms p50 and 6.5 ms p99 per
INSERT. Max for g was 449 ms (checkpoint/autovacuum outlier, 1 in 100k).

Batch totals (INSERT ... SELECT through the trigger, rolled back): one 100k-row batch per set took
a 18.3 s, b 19.8 s, c 19.9 s, d 25.6 s, e 20.4 s, f 20.9 s, g 26.9 s (about 0.18 ms/row to 0.27 ms/row).
These are single samples, so they carry no percentile. The earlier 10k-row batch table (run 37011721464)
is superseded.

Budget: no write-latency budget is named in the ticket, so "meets budget" cannot be asserted. 8.7 ms p99
on a shared runner is small next to the 300 ms write-endpoint p95 budget in
`06-performance-and-load-standard.md`, but the owner has to confirm that is the right comparison.

## Q3: GIN build cost and CONCURRENTLY feasibility

`CREATE INDEX CONCURRENTLY ix_spk_fts ON audit_log USING gin (to_tsvector('simple', before||after))` on
10 M rows, with a second session inserting one row at a time throughout:
- **139 s** build, **256 MB** index, `indisvalid = true`.
- **2,469 inserts completed during the build**: p50 4.4 ms, p99 6.8 ms, max 638 ms (the brief lock at
  the final phase). **CONCURRENTLY is feasible: writes were not blocked.**
- The earlier local run (760 s, 552 MB) used a different generator payload width; the CI number above
  replaces it.

## Decision (ADR-0025)

1. **Index set f + GIN**: add `ix_audit_hisev (event_ts DESC) WHERE severity IN ('error','critical')`,
   `(actor_user_id, action, event_ts DESC)`, and the GIN full-text index. All three are built
   `CONCURRENTLY` in their own migration (#1710).
2. Full-text `q` (E42-T02) uses selectivity-aware dispatch (#1711): estimate the match count, then use
   CTE+GIN for selective tokens and the naive keyset form for common ones. Both stay under 31 ms at 10 M rows.
3. Reject BRIN (no benefit). Range partitioning is **not** needed at 10 M rows.
4. Budgets: every combination meets 400 ms p95 with set f, and full text meets 2 s with GIN + dispatch.
   **Not met:** the existing set alone fails `severity_actor` (443 ms), and any single full-text form
   fails one token class.

## Limits
- CI runner with a warm cache, not the reference machine. The ranking and orders of magnitude are the
  claim; absolute numbers will differ.
- 20 samples per query, so p99 = max.
- The bulk load bypassed the chain trigger. The Q2 batches ran through it.
- Q2 is per-INSERT, measured in run 37031566428: 100k samples for set g, 20k for sets a-f (job budget).
  Rate was paced at 500/s, an assumption (no production rate is documented). Rolled back, so commit fsync
  is excluded; it is identical across sets.
- Cold-cache first-run figures (cold `shared_buffers` after restart) are in the report's `cold_cache`:
  worst is env_action at 203.5 ms first run vs 1.3 ms warm.
- Cold cache means cold `shared_buffers` after a container restart; the host OS page cache is not dropped.
