## 1. Scope and assumptions

E39 is the control that stops new risk, so the attack that matters is not theft but **defeating or spoofing the
control**: trading continuing while the system or the operator believes it is blocked, a lockout cleared that should
hold, or a block that cannot be engaged when it is needed.

Attackers:

- **A1** a Manager acting against another trader or beyond their grants (AC-14, the primary insider threat).
- **A2** a compromised browser session of any role (AC-15), an Owner session without its TOTP device included.
- **A3** a Viewer or other low-privilege user probing state (AC-03).
- **A4** a well-meaning operator: an accidental freeze or release, a loose policy, a mistyped cap.
- **A5** a holder of the `cv_app` database credentials or of a shell on the host (AC-16).
- **A6** an internal producer that reaches the exchange by accident: a rule action (AC-06), an algo child, a deferred or
  retried fan-out leg, an amend, a reverse.
- **A7** failure as the adversary: Postgres, the exchange, the private streams, the clock (A-20), a restart, a restore.

Assumptions:

- Tailscale only (TB-1) and TOTP on every user. The 04 §5 standing assumption "the kill switch is available" is the
  property this model tests, so it is not assumed here.
- One API process holds the gate state. The 5 s state cache is safe only because an engagement invalidates it
  in-process; a second API worker process is a re-model trigger (§11).

Out of scope (ticket): executing the abuse cases and authoring SAST/DAST rules (E39-X02), the pen-test (E43), the order
paths themselves (E29) and the key vault (E27), the dead-man's switch (US-RULE-013, E35), flatten-all mechanics (E29).

## 2. Data flow and trust boundaries

Boundaries from 04 §4: TB-4 (client to API) and TB-7 (backend to Bybit). Local ones: TB-K1 API to the gate
(in-process, synchronous), TB-K2 risk services to the Postgres state, TB-K3 kill-switch effects to the exchange, TB-K4
flag console to the order-entry gate, TB-K5 host console to the kill-switch service, TB-K6 server to client
propagation.

```text
 Owner / Manager / Viewer --TB-4--> [C5 REST: summary, limits, override, kill switch] --> C11 audit, page
      |  order intents (ticket, chart, DOM)       | authorise: RBAC + scope + step-up (one function)
      v                                           v
 [OMS] --TB-K1--> [C1 gate (account, acting user, origin)] <-- C2 counters <-- oms.* events, private streams
   ^ rules, algos, fan-out legs, retries (A6)  | reads every blocking source; refuse or reserve headroom
                                               v
                           sized leg -> native-SL guard -> adapter --TB-7--> Bybit
 [C3 lockout, B20] [C4 kill switch, B18] --TB-K2--> [C7 kill_switch_state, risk_lockouts, risk_policy]
      | cancel entries, reduce-only close, verify --TB-K3--> Bybit (critical bucket)
      +--TB-K6--> WS system, auth_ok.kill_switch, wallet.risk_cap_usage --> clients
 Flag console PUT /admin/feature-flags/killswitch.* --TB-K4--> MaintenanceGate (built)
 Host console `candleviewer kill` (A5) --TB-K5 (local channel)--> C4 (SR-086, not built)
```

Structural facts the diagram must not hide:

- **A synchronous read enforces; the machines record** (C-2.21, INV-B18-a, INV-B20-a). B18 and B20 cannot
  authenticate a sender: their guards read owner and elevation from the event payload and the statechart gateway has
  no per-event sender check, so every authority decision is taken by synchronous code before the event is sent.
- **"Trading blocked" has several sources**: `kill_switch_state` (B18), the flag-class switch, per-manager `frozen`,
  `risk_lockouts` (B20), the account's `trading_enabled` and policy disarm, and the B17 live gate. Some bind an
  account, some a manager on an account; a path that reads some of them and not all is a bypass.
- **Engagements accumulate.** Several targets can be engaged at once (global, an account, another account); the block
  in force is their union, and only a release reduces it.
- **Risk state lives in memory first.** A restart, a stalled private stream or a failed rebuild must fail closed, and
  only for orders that add exposure.
- **The two write directions fail opposite ways.** A restrictive transition (engage, lock, freeze) must never be refused
  by an outage or by the requester's session posture (a global engage leaves view-as first); a permissive one (release, override, loosen a policy, the clock
  release of a lockout) must never happen without durable state and a durable audit record.

## 3. Rating scale

L = likelihood, I = impact (H/M/L); risk Critical (H/H), High, Medium or Low; residual after the listed control.
"Detect" names the audit action or metric that reveals the threat, or "none"; the E39 names are planned until E39-S02
and E39-S03 register them (SR-E39-12). A control that is only a requirement leaves the row at its inherent rating until
its ticket ships it (§8).

## 5. What "nothing escapes the gate" must cover (E39-S01, E39-S03, E32-T01 sufficiency criteria)

RK-E01 is the epic's central threat. The gate is sufficient only if all of the following hold:

1. **One choke point.** Every position-opening adapter call passes the gate, proven by E32-T01's single call-site
   architecture test; a new order origin fails E39-S01's origin registry test until it is gated.
2. **Every origin and every send**: ticket, chart, DOM, rule action, fan-out leg (first send, deferred send, retry), TP
   ladder rung, algo child, amend that raises size or notional, the opening half of a reverse, a leverage raise; at
   send time, not only at intent or preview (SR-E28-27, SR-E29-04).
3. **Who it acts for.** The gate's input is (environment, account, acting user, origin). A session-less origin carries
   the user it acts for (the rule's owner, the group's creator, the algo's starter), so a per-manager freeze or lockout
   blocks that user's origins on the account (E35's `owner_frozen` check is the model).
4. **Every blocking source in one synchronous function** (C-2.21): the union of `kill_switch_state` rows, the
   flag-class switch, the manager's `frozen`, the active `risk_lockouts` rows (account-wide and the acting user's), the
   account's `trading_enabled` and policy disarm, the live gate and the caps. Each refusal maps to one registered code
   (G-4).
5. **Unreadable means refused** for an order that adds exposure; never for a cancel, a reduce-only close inside the
   position or a native-SL attach, repair or tightening (SR-E39-02).
6. **Mutation evidence**: removing any one source from the function, or any one origin from the registry, turns the
   E39-Q02 matrix (UI paths) or the E39-Q01 regression pack (non-UI paths) red.

## 6. Performance as a security constraint

The 5 ms p95 budget covers the gate's decision, which is I/O-free: in-memory counters and a cached state that an
engagement invalidates in-process, with no Postgres read on the path except E39-T01's cached lockout probe. The
refusal's audit record is written after the decision and before the response returns, so it sits outside the 5 ms
decision but inside the backend allowance of `06-performance-and-load-standard.md` §5.2; "no refusal without a record"
is kept and only its latency moves. The record of a permissive transition stays write-ahead (SR-E39-05). Two departures
from 04 are proposed at approval as an exception (EX entry) or an amendment: the in-process block precedes the
engagement's intent record, which reorders §9.2's sequence (the cancel and flatten still follow the lane-accepted
intent); and the engagement proceeds when the audit lane refuses its record, which departs from §8.3 rule 2 (the
RR-20 tension). If the gate ever runs
in more than one process, the in-process invalidation no longer holds and the cache staleness becomes a bypass window
(§11 re-model trigger).

## 9. Contract gaps, decisions and abuse cases

Contract gaps G-1 to G-13, each closed through its own gate (C-2.19 for the charts with a hash bump, contract first
for REST and WS):

- **G-1, B18 (E39-S03).** The `engaged_incomplete` release arm writes no record (INV-B18-e). `RETRY_FLATTEN` is
  unguarded and ignores `context.flatten`, so after a root `KILL` it could flatten positions nobody chose to flatten.
  `cancelling`'s error arm reaches `engaged` with only an alert (SR-E39-06 needs `engaged_incomplete`). INV-B18-c
  ("`engaged` requires every account flat") contradicts "stops new risk, does not force-close": restate it as "every

- **D-1 (open, Owner)** Manager engagement. (a) Owner only, as 04 §7.2.2 rows 31 and 32 and SR-082 say; (b) within the
  Manager's grants, never `flatten_positions`, disarming only rules the Manager owns (or paging the Owner for each other
  rule disarmed), the Owner paged, release Owner-only, as 22, 04 §7.2.1 and E39-S03 say. Recommended: (b), because
  halting one's own runaway trading is protective; row 33 already lets a Manager close a granted account's positions.
- **D-2 (open, Owner)** Engagement defaults. SCR-072 shows both options off; 22 defaults `cancel_open_orders` to true.
  Recommended: true, because a resting entry order is new risk that can fill after the engagement (RK-S02).
- **D-3 (open, Owner)** Environment and paper. Recommended: `global` covers every environment; account rows, counters
  and policy evaluation are keyed by environment and paper, and a mixed request is refused.
- **D-4 (decided, #2701 issuecomment-6290513561, 2026-10-20)** An override grants a typed `extra_loss_usd` allowance
  over the loss figure the cap uses (E39-K01's source; the ruling says "realised", and this reading is to be confirmed
  on #2701) at override time, bounded by `risk_policy.override_extra_loss_max_usd` (default 0, raised only by the Owner on SCR-134);
  the lock re-arms at that bound or at the window end, whichever comes first; `max_daily_loss_usd` never changes.
- **D-5 (open, Owner)** Policy floors. May `block_trading_when_degraded=false`, `lockout_minutes_default=0` or a removed
  limit be saved at all? Recommended: refused server-side, so SCR-134's "cannot be disabled entirely" is a server rule.
