## 1. Elements, actors and data

| Id  | Element               | Surfaces and behaviour                                                                                                                                                                                                     | Task and slices                      |
| --- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| L1  | Disable               | `DELETE /users/{userId}` and `PATCH /users/{userId}` to `disabled`: revoke sessions, close sockets, disarm rules, soft-revoke grants, revoke an open invite; last-owner protection; positions and working orders stay (O2) | E42-T04 S3–S7; E42-T09 S11 (`PATCH`) |
| L2  | Account-access grants | `GET` and `PUT /users/{userId}/account-access`: the soft revoke (O4) and the `revoked` push                                                                                                                                | E42-T08 S8–S9                        |
| L3  | Roles and sessions    | `GET` and `PATCH /users/{userId}` with an ETag and `PUT /users/{userId}/roles`, under the owner lock; `GET /users/{userId}/sessions` and `DELETE /users/{userId}/sessions/{sessionId}`                                     | E42-T09 S10–S12                      |
| L4  | Deferred purge        | `DELETE /users/{userId}?purge=true` sets `purge_after` 90 days out; the reaper writes the surrogate and nulls PII; audit rows are never updated (O6)                                                                       | E42-T10 S2, S13, S14                 |

Actors: **A1** a Manager or Viewer calling an Owner route; **A2** a stolen or unattended Owner session; **A3** the
target user's live session, socket, armed rule or resting order; **A4** two Owners acting at once, or an Owner's
mistake; **A5** a reader of the database, a backup or the audit mirror after a purge. Data: `users.email`,
`display_name` and `username` are P1; `last_login_ip`, the session `ip`, `user_agent` and `tailscale_node`, and
`audit_log.actor_ip` are P2 (`21-database-schema.md` §12); grants and roles are Confidential (E42-T04 and E42-T09
security notes).
Boundaries (`04-security-program.md` §4): TB-4 (cookie session, CSRF, RBAC, step-up) in front of the users router,
and TB-6 (backups and the off-box copy) for A5. The API and Postgres both run inside the TB-3 zone (the
WSL-internal compose network), so the API-to-Postgres edge crosses no boundary.

Out of scope: the rest of the admin area (E42-X01); session issuance, MFA and step-up internals (E09, consumed); the
rule engine beyond B9 DISARM (E35); the WS transport (E17); alerts of a disabled user (O7, §6).

## 2. Flow

```text
Owner session (A2, A4) --TB-4: cookie, CSRF, users:write, step-up `users`--> users router (L1-L4)
  --inside TB-3, one transaction (R7)--> lock the user row; lock the owner rows (#2502, #2508)
      DML: status | session rows | grants (soft, O4) | roles | purge_after
      SET CONSTRAINTS ALL IMMEDIATE (owner-floor trigger) -> write-ahead audit (C-2.9) -> commit
  --after commit (R7: a failure is counted and alerted, never rolled back)-->
      B16 REVOKE per session (auth.session_revoked) | bye user_disabled + 4403 | grants_changed -> revoked
      B9 DISARM per rule | invite revoke
Synchronous readers (C-2.21), both gaining users.status (O5), next to the can_view filters (O4):
  _PERMS_SQL for /auth/session and the WS principal at every auth and re-evaluation (app.py)
  _PERMS for the rule engine on every evaluation tick (rules/service.py)
Retention scheduler --> anonymisation reaper (L4) --inside TB-3--> users, sessions; never audit_log (O6)
Postgres --TB-6--> backups and the off-box audit mirror (SR-068), which keep pre-purge copies (A5, UL4-I1)
```

UL1-E2's race needs three things at once: the new socket's `auth` passes `authenticate` and reads its principal
before the disable commits; the user's own refresh rotates the presented session before the transaction revokes it,
so the disable never names that session; and the socket registers after the per-user close. That close keeps no
memory of the user and does not advance the registry's version (`ws/permissions.py:1112-1125`), so SR-189's re-check
(#2318; `ws/gateway.py:1081-1083`) does not read the principal again, and the hub's check of an `auth` in flight
(#2739; `ws/gateway.py:1126`) knows only the session ids the disable revoked. #2318 and #2272 landed on 2026-10-16
and do not cover this path. The likelihood is low: the window is a few milliseconds around a commit the user does not
control, and new auths are rate-limited. A per-user memory in the registry, refusing that user's later registrations
until every access token issued before the disable has expired, would close it: the follow-up #3413, not built here.

No High residual remains once the slices, UL-F1 to UL-F7 and UL-F9 to UL-F13 ship. `32-risk-register.md` already
tracks the missing SR-029 cascade under RSK-020 (E09 review R-7); this appendix changes no register row, and E42-X01
carries any update.
