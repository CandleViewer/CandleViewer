## 1. Scope

In scope, the two paths the ticket names: client → REST `/orders` → RiskGate → OMS → RateBudget → BybitAdapter →
Bybit, and Bybit private WS → OMS → Postgres → WS fan-out → client. That covers the OMS routes (`/orders*`,
`/positions*`, `/executions*`, diagnostics), the submission pipeline, the `orderLinkId` allocator, the B1 order
machine, the private-stream consumer, the reconciler and stuck-order detector, the four private topics with
`trade_groups` and `system`, the stores `orders`, `order_events`, `executions`, `positions` and
`position_snapshots`, the idempotency records, and the audit and telemetry these emit.

Out of scope (ticket): key storage and envelope encryption (E27 model), with the C-2.8 withdrawal-off permission gate
and the Semgrep rule `cv-withdrawal-endpoint-ban` (E27 KV-E05), fan-out unwind (E34), the rule-engine sandbox (E35),
kill-switch bypass (E39), penetration testing (E43). Referenced, not re-modelled: profiles, sizing and risk caps (E28
model), native-SL enforcement and brackets (E32-X01, #933), emulated algos (E33-X01, #995), the reconciliation job
(E45-X01, #1281), the order ticket and arming (E30-X01, #920), live gating (E44-X01, #1249).

### 1.3 Rating

Risk = L x I on the programme scale (Low / Medium / High / Critical):

| L \ I | L      | M      | H        |
| ----- | ------ | ------ | -------- |
| L     | Low    | Low    | Medium   |
| M     | Low    | Medium | High     |
| H     | Medium | High   | Critical |

Impact **H\*** marks an outcome that lets value leave an account (E27 D2) or leaves a position without a working
native stop, which C-2.6 calls a Severity-1 defect (E28 D2); it raises the cell one band. Disposition: **Q** a
requirement (`SR-E29-nn` or a ticket-body control) that a named ticket must build and a named test must prove; **C** an
existing control on `main`, cited with its test; **R** referenced, owned by another epic's model; **A** accepted
(Owner sign-off, §12.2). Verification layers follow `04-security-program.md` §6. Row ids are `OM-xnn`. `24 Sn` is rule
Sn of `24-internal-schemas.md` §8.2 and `WS Sn` rule Sn of `23-ws-protocol.md` §16.1.

Text description (the diagram is not the only carrier): a client sends an order mutation (F1) or a read (F2) to the
REST surface, which runs the E09 chain and the idempotency store (F16). The risk gate checks the intent against the
account's grant, profile and gate state (F3, F20), and the OMS core sizes, rounds and builds the `orderLinkId`
(F4). Rule-engine and algo intents enter the same gate in process (F5). The OMS writes the order row and its first
event before any send (F6), takes a token from the account's budget (F7) and hands the request to the adapter,
which signs through M2 and calls Bybit (F8); the answer comes back untrusted (F9). On live, once E44 enables it, the
send may use the WS trade socket instead (F8b, acks on F9, `[O-9]`). Private pushes (F10) are applied as fills,
positions and events (F11). The reconciler polls the exchange through the `poll` bucket (F12) and applies corrections,
`untracked` rows and stop repairs (F13). Persisted changes reach clients as private-topic frames (F14). Every mutation
is audited write-ahead (F15); telemetry (F17), client caches and exports (F18) and backups (F19) receive copies.

Elements: external entities **E1-E5** and **E3b**; processes **P1-P8**; data stores **DS1-DS8**; flows **F1-F20** and
**F8b**. Every element and flow is in the coverage matrix (§3.7).

Boundaries (`20-architecture.md` §2.2, `04-security-program.md` §4.1, E27 model §2):

- **TB-4, client to API** (F1, F2, F14, F18): untrusted until authenticated, RBAC-scoped after. The client enforces
  nothing (C-2.12); a blotter that hides a button is not a control.
- **Store boundary** (F6, F11, F13, F15, F16, F19, F20): a database writer is its own integrity domain;
  `order_events` and `executions` are the order path's non-repudiation stores beside `audit_log`.
- **TB-7, backend to Bybit** (F8, F8b, F9, F10, F12 through F8): owned by E08 and E27; the exchange is semi-trusted
  (programme AC-08), so every answer is validated and the private stream is reconciled against REST.
- **TB-6** (F19): backups and the 24-month partition export receive whatever `order_events` holds.
- **E5** runs in process but is semi-trusted (programme AC-06): its intents take the P2 and P3 path (OM-E04).
- The **M2 capability boundary** sits inside P5 (E27 model §4.3). B4 (renderer to Electron main) carries no E29 flow.

## 4. Structural conclusions and decisions

### 4.1 Account and purpose come from the server, never from the client

A request names an account and an intent; both are objects to check, not facts. The account rule is E27's (E27 model
§4.2: scope comes from the session; RBAC is enforced server-side, C-12.4) and covers every E29 route, including the id
routes, where the account is read from the stored order or position. The purpose rule is new here: two downstream
controls key on it, NativeStopGuard (the contract requires a stop "for entry intents") and the budget bucket
(protective purposes draw the reserve). A label the server trusts is therefore both a C-2.6 escape and a reserve drain
(OM-S02). The purpose is derived from the order's effect on the exchange-truth position: anything that opens or grows
exposure is an entry (SR-056), whatever the label says.

### 4.2 The `untracked` path is a privilege boundary

An order the OMS treats as its own counts as OMS intent, and SR-E27-19's no-intent detection rests on that line. Three
texts draw it differently: `24-internal-schemas.md` S9, which at the slice tip covers every exchange order with no
local row, ours whose row was lost included (displayed, adoptable, never rule-managed); `21-database-schema.md` §3.3.1,
which sends our own timed-out orders to `untracked` and lets an `untracked` row become `accepted`; and the B1 contract,
which has no such state. A fourth, RSK-017's adoption of orphaned algo orders "by `orderLinkId` prefix", is amended by
the slice together with `20-architecture.md` §3.5: ids are compared whole, and a group owns an order by relation, never
by its id text (24 §8.3 rule 2, §8.5, §9.5.1) `[O-8]`. The rules this model adopts: only an order the OMS persisted
before sending, and bound by the full match, is ever ours (SR-E29-03); every other order, an `untracked` row under an
`OUR_ID` included, is `untracked` and pages; adoption is a deliberate, audited act that re-runs the validator (D6);
rules, algos and group cancels never act on an `untracked` order; and a squatted id is caught by the full match
(OM-S05, OM-E02, SR-E29-03, SR-E29-12).

### 4.3 Decisions recorded

The kickoff session with the Architect and the Security engineer is replaced, as for E27 and E28, by this agent-written

## 5. The idempotency key as a security control

This section rests on the slice `[O-8]`: `24-internal-schemas.md` §8.3 rule 1 for the replay anchor (§5.1), and §8.5
with §14.2 rule 11 for the adoption match (§5.2, §5.3).

### 5.1 Three keys, three jobs

| Key                             | Minted by                                                                                                                                        | Scope and lifetime                                                                                              | What it stops                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `Idempotency-Key` header        | the client (UUIDv4, contract)                                                                                                                    | a response cache: stored with the body fingerprint for 24 h (contract); per principal and operation (SR-E29-07) | a retried request inside 24 h receiving anything but the original response                                       |
| `client_group_ref`              | the client: the server stores the request's `Idempotency-Key` as the group's ref (slice rule 1; on `POST /orders`, the one-leg group's, E29-T04) | permanent; unique over all `trade_groups` today, principal-scoped under SR-E29-07                               | a replay at any age creating a second group or new ids: it reaches the same group and order rows before any send |
| `order_link_id` (`orderLinkId`) | the server, once, before the first send (§8.3)                                                                                                   | unique over every `orders` row in any state (#846 Q1); deduplicated by the exchange within its window `[O-1]`   | a retried send creating a second exchange order; the reconciliation join key                                     |

The contract's `placeOrder` text and its shared `IdempotencyKeyRequired` parameter say the server derives the
`orderLinkId` "from" the `Idempotency-Key`, while §8.3, which #846 ruling B2 makes canonical, derives it from the
trade-group UUID, and slice rule 1 keeps every client-supplied string, the `Idempotency-Key` included, out of the id.
The group UUID is therefore server-random, and a client cannot choose an id (contract text: G-1).

Replay protection has two layers. The 24 h record is a response cache: inside it, the same key and body return the
original response and another body is a 409. The permanent anchor is `client_group_ref`: slice rule 1 stores the key
as the group's ref, so a replay after the cache expires still reaches the same group and order rows before any send.
No window remains after which a replay mints new ids, and three duties move to the anchor (SR-E29-07):

- **Principal scope.** The ref is a client-chosen string in a column unique over all groups. Looked up by ref alone, a
  second principal who sends a value the first one used receives the first principal's group, an IDOR across accounts;
  inserted under the global UNIQUE, the request fails with a conflict that tells the sender the value exists. Scoped by
  principal and operation, a foreign value is simply new, so a foreign key gets the answer of a missing one.
- **Body binding.** Unless the anchor keeps the body fingerprint, a same-key request with another body after 24 h
  reaches the old group instead of a 409.
- **Current grants.** A replay at any age is answered from the group's current state, re-authorised against the
  caller's current grants, never from a response stored under grants since withdrawn.

The column is documented as a "UI-generated ULID" (`21-database-schema.md` §3.3.2) and the header as a UUIDv4
(`IdempotencyKey`, `IdempotencyKeyRequired`), and the `createTradeGroup` example returns `cv-0c000000`: which format the
column holds and validates is for the slice to settle (G-6).

### 5.3 Why the collision check and the persisted-before-send rule bound it

- **Persisted before send.** In §8.4 the order row and its first event are inserted before the token is taken and
  before any byte leaves. Every id the exchange can see from us therefore has exactly one local row. A crash between
  the insert and the send leaves an `unsent` or `in_flight` row that the reconciler resolves by looking that id up,
  so the OMS never mints a second id for the same logical order, the one way a crash could double-submit. If the
  insert fails, nothing is sent (24 S7).
- **Collision check over every row.** With #846 Q1 the check covers every row in any state, as `ux_orders_link` and the
  exchange's own deduplication do. A lookup by id returns one local order, and a new intent never inherits a terminal
  order's exchange history.
- **Together.** The set of `cv` ids the OMS sends equals the set of persisted rows, unless a row is lost (a restore).
  An exchange order with an `OUR_ID` and no row is therefore foreign, or ours whose row was lost: either way it becomes
  `untracked` under that id and pages, and no rule, algo or group cancel treats it as the group's (§4.2) `[O-8]`. One
  that a row holds but that fails the full match is foreign too (SR-E29-03).
- **Limits.** The bound holds only within the exchange's deduplication window `[O-1]`, and only if no path sends an id
  it did not persist. Today `OrderLinkId` (`domain/primitives.py`) is a pattern-checked `str`, so any matching string
  is one; SR-E29-03 adds a nominal type that only the allocator returns and `place_order` alone accepts, with an
  E29-X02 rule against any other constructor (a change, not a current control).

### 5.4 Accepted risk: the predictable id (#846 ruling Q7)

The id is deterministic by design (C-2.10); predictability is the price of idempotency. It holds no secret, no user
identifier and no account name, and `acct4` is a diagnostic tag (#846 ruling B3). What remains after SR-E29-03: an
actor who already holds exchange-level access to a UID can squat one future id to stall one child or conceal one
order until the adoption match pages, and readers of an id learn the group structure (OM-I09). Level Low. Owner: the
Owner/PO, on the Security engineer's recommendation; ticket E29-T02. Review by 2027-02-04 (R3 gate), and again before
the first live order (R4, 2027-02-25), or at once if E29-K01 shows deduplication behaviour other than O-1. An expired
acceptance is re-decided, not extended (`32-risk-register.md` §1.3).

## 6. `order_events.payload` as a credential-leak channel

**What reaches it.** `21-database-schema.md` §3.3.5 stores the "raw exchange message, redacted of credentials";
E29-T03 requires the raw payload behind every exchange-sourced transition; diagnostics returns exchange request and
response pairs (E29-T07). A signed REST request carries `X-BAPI-API-KEY`, `X-BAPI-SIGN`, `X-BAPI-TIMESTAMP` and
`X-BAPI-RECV-WINDOW`; an `auth` frame carries the key and the MAC as positional `args` (`24-internal-schemas.md`
§14.3), on the private stream and, once E44 enables it, on the live trade socket (F8b, `[O-9]`). On `main`, M2 hands
M4 the hex MAC and the key id (#2350), so both sit briefly in M4's request objects. Responses and pushes carry
financial data, the exchange's text, and headers whose account-identifying content is unconfirmed `[O-3]`.

**Why it is worse than a log leak.** `order_events` is append-only and kept indefinitely (C-12.8), copied into
backups and the 24-month partition export (DS8), and served by `getOrder?include_events=true`, whose `OrderEvent.payload`
is an open object, to every `orders:read` holder on the account without an audit record (OM-I06). A credential written
once cannot be removed through the application, and removing it by hand breaks the append-only guarantee. The key id is
Secret (E27 model §1.2); a stored MAC is not reusable after `recv_window`, but it is still credential material under
C-12.6 and SR-122.

**Why deny-list redaction is not enough.** Both shipped redactors are deny-lists. `audit/redact.py` matches field
names only (`X-BAPI-SIGN`, `X-BAPI-API-KEY`, `sign`, `apikey`, ...) and leaves a non-JSON string unchanged, so an
`auth` frame's positional `args` and a signed query string in a URL pass it. `observability/redaction.py` scans every
string, list elements and URLs included, but its only key shape is an 18-to-36-character alphanumeric word: a
64-character hex MAC (`args[2]`, a query-string signature), the `expires` value and a key of any other length pass.

**Requirement (SR-E29-08).** Classification: Secret before redaction, Financial / restricted after (D1).

1. Allow-list at the source: M4 builds the stored record (method, endpoint, allow-listed body fields, `retCode`,
   `retMsg`, allow-listed result fields, latency; for a trade frame, `op` and `reqId` in place of method and endpoint).
   Headers, both `auth` frames and URLs with a query string never leave M4. The OMS treats the record as opaque, which
   also keeps raw exchange dictionaries out of business logic (C-2.3).
2. Fail closed before insert: `redact_exchange_payload()` (E29-T01) runs again and drops anything oversized or
   unrecognised, with a marker.
3. Typed contract: `OrderEvent.payload` and `exchange_calls[].request_redacted` and `response_redacted` get closed
   schemas instead of open objects (G-1); events are served without payload (SR-E29-09).
4. Proof: a property test seeds fixture keys, MACs, `auth` frames and signed URLs through every path into
   `order_events`, diagnostics, audit rows and logs, and finds none of them; an E29-X02 Semgrep rule fails a write to
   `order_events.payload` that does not take the adapter's record type.

## 7. Denial of service: the protective reserve is a security control

The `critical` bucket keeps a flood of normal traffic from starving a stop (ticket Performance notes; the per-UID
reserve for risk-critical actions of C-12.7), so who may draw it is a security decision:

- the purpose that selects the bucket is derived from the order's effect, never from the client's label (SR-E29-01);
- cancels and cancel-all are risk-reducing and draw `critical` (ADR-0008 rule 4, SR-071), so a cancel flood is the one
  flood that reaches the reserve; stop attach and repair need a slice cancels cannot spend (OM-D06, SR-E29-14);
- reconciliation, wallet and position refresh, and key verification draw `poll` only (E29-T06, SR-E27-05);
- the reserve fraction is written three ways (E28 model §11.3 note 2); E34-T02 implements one value inside the shipped
  `TokenBucketGovernor`, which has per-UID buckets but no purpose classes and no reserve today (§1.1; SR-044a allows
  one tracker per UID, so not a second governor), and the page on `oms_rate_tokens_available{bucket="critical"}`
  (`20-architecture.md` §4.3) proves it holds;
- a `10018` hold gates every REST path, stops included (`24-internal-schemas.md` §8.6), so the native stop already on
  the exchange is the floor (C-2.6); the shipped per-IP bucket (SR-044c) keeps our own bursts from causing the hold,
  and `hold_ip` caps one hold at 900 s; on live, a stop never waits on the trade socket, whose connections share the
  per-IP budget (C-12.7, OM-D07).

Chaos coverage: C-13.6 scenarios 2, 4, 5, 6, 7, 10, 11 and 12 exercise this model's rows; E29-Q04 and E34-Q04 own them.

## 8. Abuse cases for E29-X02

### 8.1 Adversary narratives

**N1. A malicious or coerced Manager.** The Manager holds a grant on account A only, which shares its UID budget with
the Owner's trading. They place an order for B and for a random id, amend and cancel an order of B by its id, send
`cancel-all` with an empty list and with A and B, filter by a `trade_group_id` that spans both, subscribe to `orders`
for both, label an opening order `stop_loss` to skip the stop and jump the reserve, spam cancels on A, adopt an
`untracked` order, and hunt diagnostics for raw pairs. Every attempt is refused or narrowed, the answer for B equals the
answer for a missing id, each refusal is audited, the scope-denial spike alerts, the mislabelled order is treated as an
entry, and the Owner's stop attaches on A throughout (OM-E01, OM-I01, OM-I02, OM-S02, OM-D06, OM-E02, OM-I06).

**N2. A compromised client.** An XSS payload or an extension acts with the Owner's session but has no step-up and, on
live, no arm nonce. On demo it can place orders inside the caps, each with a native stop, each audited with the session
id and replay-safe; on live the per-request arm nonce stops it (SR-043, E30 and E44), once G-1 makes `arm_token`
mandatory for every live order mutation and not only for one-click and hotkey entry. The OMS contributes the stop
invariant, the audit trail and idempotency (OM-S01, OM-R01, OM-T09).

**N3. An exchange-level actor.** The KV-E11 actor (a key used from the egress IP, or in-process code) reads a TWAP's
group id from any child id, places an order under the next child id with the opposite side and a larger size, and
places another order under an unused id of the algo's group before forcing a restart. Both ids are `OUR_ID`s, which
the adapter keeps (24 §14.2 rule 11), so at the slice tip the first is adopted as the child by success-after-lookup, its fills
pair with the child on `order_link_id` (24 §8.5 step 2), and the second is adopted `untracked` under an id that names
the algo's group `[O-8]`. With SR-E29-03 (after G-3 and G-6) the child's lookup mismatches, the child is held with a
P1, and the first order is recorded `untracked` under `ext_key(orderId)` with its fills paired on `exchange_order_id`;
with SR-E29-12 the second stays `untracked` and pages, because a group owns an order by relation, never by its id text
(24 §9.5.1); the no-intent detection of SR-E27-19 sees both (OM-S05, OM-E02).

**N4. A Viewer hunting for payloads.** The Viewer reads `getOrder?include_events=true`, diagnostics, CSV exports, the
`system` topic and a support bundle. No header, MAC, `auth` frame or other account's data appears anywhere (OM-I05,
OM-I06, OM-I03, OM-I10).
