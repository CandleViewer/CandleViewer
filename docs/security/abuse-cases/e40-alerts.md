# E40-X01 — Abuse-case seeds: the alert and notification surface

- Ticket: E40-X01 (#1204). Part A writes these seeds; Part B automates them. Threat source:
  `docs/security/threat-models/e40-alerts.md`, its §3 rows (AL-S01 to AL-E06) and its §10 requirements (SR-E40-01 to
  SR-E40-27). The E35 suite (`docs/security/e35/abuse-case-suite.md`) and E17's catalogue
  (`docs/security/abuse-cases/e17-ws.md`) are referenced, not repeated.
- One seed per model claim that needs a test; a claim with no test here is not an accepted mitigation (the ticket's
  test plan: every Critical and High maps to a test in E40-X01 or E40-Q01).
- Method: white-box. Server cases use a raw HTTP client through `create_app()` that ignores every client rule, so the
  server is what refuses; client cases run in Vitest under `apps/web` and in the shell's tests under `apps/desktop`.
  No network, no live account, no real key; fixture account ids only (C-13.5). The payloads are adversarial by
  design and never run against live (the ticket's Security notes).
- Paths: server tests under `services/api/tests/` (new cases in `tests/security/alerts/`); Semgrep rules under
  `.semgrep/`, each with a fixture that fails on a deliberate violation; the ZAP profile under `.zap/`. A `tests/` path
  in the table is under `services/api/`.
- Actors: **O** the Owner; **M** a Manager granted account A only, holding `alerts:read` and `alerts:write`; **V** a
  Viewer. B is an account M is not granted.
- Verdict key: **COVERED** an existing test on `main` holds it, cited after `COVERED:`; **NEW** Part B writes it
  against code on `main`; **WAITING** the code is not on `main` yet, and the verdict names the ticket that builds it.
  Never skipped.
