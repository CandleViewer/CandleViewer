# E10-Q03 (#302): shell accessibility audit v0, run record (PR 1)

## 0. Honest scope

This is an **agent-run** audit, PR 1 of 2 (`Refs #302`). It is not a human pass: no screen reader was operated by a person, nobody tabbed the shell by hand, and nobody zoomed a browser. Every number below was measured by the committed driver. Driver B (Tab walk, 400% reflow, greyscale, computed names against `E10-D04-names.json`, the 1 Hz chip count) and the owner-run rows OR-1..8 are PR 2.

- **Swept tree:** the PR head's `apps/` (tree `2ecb4a57a90a`) and `docs/plan/a11y/_tools` (tree `436dc9279ba4`); the sweep is tree-identical to the PR head for those two paths (the manifests in the results record these tree ids, not a commit, because the head is amended and rebased). That is `main` at `46e6acd2d` plus the fixes in §3. The "before" numbers in §3 come from the same driver run at `46e6acd2d` plus the driver, before the fixes.
- **Environment:** the built web app (`vite build`) served by `vite preview` on loopback, API and WebSocket stubbed at the network layer with `apps/web/e2e/support` (C-13.5), Playwright 1.64.1 Chromium headless; the Electron leg is the built `apps/desktop` main process (Electron 45) on its own `xvfb-run` display, loading the same preview through `CV_DEV_SERVER_URL`.
- **Electron provenance (not CI):** the 48 Electron cells were run on the audit lane's local `xvfb-run` display, not in CI: CI's `e2e-electron` job does not run this driver, so no CI job reproduces them. Run date 2026-11-01; OS Ubuntu 26.04.1 LTS under WSL2 (Linux 6.6.87.2-microsoft-standard-WSL2), Xvfb; observed Electron `v45.0.0` (`npx electron --version` in `apps/desktop`). The web leg ran on the same host the same day (Chromium headless, Playwright 1.64.1). A CI-run Electron leg, and the Windows 11 and macOS builds, are owner-run rows OR-1 and OR-3 (§6). No live exchange; off-site requests are aborted and counted (0).
- **Not re-swept:** E47-T01's shell rows (`screens.ts`, `axe-baseline.json` and `e47-sweep.qa.ts` are untouched). Findings are A11Y-F rows in `docs/plan/a11y/findings.json` for E47 to aggregate.
- **Not built, so not assessed:** SCR-012 command palette (#5236), SCR-027 floating window, CMP-211 panic button. The driver records `CMP-211` and `CMP-059` counts of 0 on the chrome (the `shipped:false` pattern), so a gate trips when either lands.

- **States (web):** chrome as owner, viewer and a LIVE session (`session.environment = "live"`, a driver-local `/api/v1/me` stub, no fixture change); rail expanded, collapsed (a link keyboard-focused so the echo tooltip is open) and the 320 px overlay; drawer; cheatsheet; toast; SCR-152 connection down; SCR-153 banner; SCR-157 update banner and the blocking dialog (a welcome frame with another protocol); 403; 404; offline; route-crash fallback.
- **Electron states:** chrome (owner and LIVE), rail collapsed, drawer, cheatsheet, toast, connection down, 404.
- **Every impact counts**, colour-contrast on, tags `AXE_GATE_TAGS` plus `best-practice`.
- **Disabled rules: none.** Whole pages are scanned (no `include`), so the page-level rules E05-Q02 had to disable (`landmark-one-main`, `page-has-heading-one`, `region`) run here, and `region` is what found §3 F-2.
- **A cell must be the cell it names:** the driver reads `data-theme`, `data-density` and `prefers-reduced-motion` back and fails the cell if they differ (this caught a wrong assumption about the high-contrast theme during development).
- **Negative control:** an image with no alt, an unnamed button, a heading skip, an empty heading (a minor rule) and low-contrast text are injected into the chrome; the run fails as `A11Y-INFRA` unless `image-alt`, `button-name`, `color-contrast` and every impact level (critical, serious, moderate, minor) are counted; a violation with a null or unknown impact fails its cell instead of being dropped. It tripped `button-name`, `color-contrast`, `empty-heading`, `heading-order`, `image-alt` and `region`, on web and on Electron.
- **Off-site guard, both legs:** every non-loopback request is aborted and counted (web: a browser-context route; Electron: `app.context().route`). The control proves the guard can count: it navigates to a non-routable TEST-NET address and the run fails unless the guard recorded it. It is a navigation on purpose: the app's strict CSP refuses a renderer `fetch` or image to another host before the request leaves, so the guard never sees one (observed on Electron: `Failed to fetch`, image error, nothing at the route). So for renderer subresources the CSP is the barrier and the guard is the counter for everything the CSP does not govern (navigations, new windows). Result: 0 off-site requests on both legs. The Electron process gets an explicit environment allow-list (`PATH`, `HOME`, `LANG`, `TMPDIR`, `DISPLAY`, `XAUTHORITY`, `XDG_RUNTIME_DIR`, the preview URL), not the whole environment.
- **Determinism:** each cell waits (bounded at 10 s) for animations and fonts, and for the connection chip's cross-fade (CMP-076) to be fully opaque. A first re-run of the sweep caught one cell (version banner, high-contrast, comfortable) where axe read the chip word mid-fade as a serious `color-contrast` hit; the wait removed it, and the web leg was then run twice with identical clean results.
- **`incomplete` results:** axe reports `color-contrast` as "needs review" in 180 of 204 web cells and 42 of 48 Electron cells (text over an element it cannot resolve a background for). It is not a violation and is not counted as pass: it is human-owed (OR-5, with the greyscale and contrast captures in PR 2). Each `incomplete` entry in `web.json.gz` and `electron.json.gz` records the rule id, the node count and the first five node targets (as `violations` does), so FU-4's reviewer can find the nodes.
- **LIVE announce:** in all 12 `chrome-live` cells the route change wrote the single polite message "Trading environment: Live" and the banner badge is named "Trading environment: Live".
- **Electron deviation (BQ-5):** `@axe-core/playwright` cannot analyse an Electron window (`browserContext.newPage: Protocol error (Target.createTarget): Not supported`), and `page.addScriptTag` is refused by the app's strict CSP (`script-src 'self'`), which is the CSP working as intended. The leg therefore evaluates axe-core's own `axe.min.js` source into the page over CDP (`page.evaluate`), which the CSP does not govern, and runs `axe.run` with the same tags; every Electron cell records `axeVia: "inject"`. Same engine and version, different loader.
- **pa11y:** not run (AD-1 of #262): axe is pa11y's default engine, so it would not be independent, and it would be a new dependency.

### 3.1 Re-verifications the ticket asked for

- **E04-D02-F39 (CMP-092, focus after the last Dismiss, SC 2.4.3): not confirmed as a defect.** The observed behaviour (focus goes to the TopBar's "Search commands" trigger, not forward to "Notifications") is exactly E10-D04 T-19 as implemented by #4979: next row, else the next banner's first control, else the search trigger, "never into the canvas, where a held key could act". It is asserted by `DegradedBanner.test.tsx` ("after the last row's dismissal focuses the next banner, else the search trigger") and `VersionBanner.test.tsx`. The only open question is the designer's: T-19 is marked PROPOSED, so the choice (earlier in the order, but a labelled control, never `<body>`) stays with E10-D04's owner. No code change.
- **A11Y-F-0023 (CMP-076, SC 1.4.11): re-measured, unchanged.** The chip's hairline `color.border.default` against the surface behind it measures **1.41 / 1.22 / 2.86** (dark / light / high-contrast), the same as E04-D02 F07, in all 12 `chrome-owner` cells (both densities, both motion states); the chip's fill is the surface (1.00). SC 1.4.11 applies only if the border is needed to identify the control: the glyph and the word do that, and the component's own comment records the border as decoration (BQ-04). The row stays open as a candidate for the designer to close as "not needed to identify the control"; nothing was changed.

### 3.2 Deviations

- **D-1: two landmarks E10-D02 :255 does not list.** E10-D02 :255 names five landmarks: `banner` (TopBar), `navigation` "Primary", `main`, `complementary` (RightRail) and `contentinfo` (StatusBar). The fix for F-2 makes the CMP-092 band (`DegradedModeBanner.tsx`, "System notices") and the SCR-157 update band (`VersionBanner.tsx`, "Software update") `role="region"`, present only while a row shows. It is kept because axe's `region` rule flags the rows' label and message text as content outside every landmark in 24 of 24 cells of the two states, and the text carries the notice. **Designer remedy note:** the alternative that stays inside the five-landmark model is to nest the banner slot in the existing `banner` landmark (the TopBar's `<header>`) or the `complementary` one, so the rows sit inside a landmark that already exists; that moves the banner slot in the DOM and needs E10-D02 §13 and D04 to agree on the order. Until the designer chooses, the two regions stay. The PR body lists this under Deviations. (FU-1.)

Regenerating the register and catalogue (`register.py`, `catalogue.py`) also changed rows this PR did not author: the committed outputs were stale against `main`'s `findings.json` (for example the status of rows fixed since the last regeneration). Those row changes are the tools' output for `main`'s own data, not drive-by edits; the only hand edits are the two new rows, the SCR-011 `noFindings` flag, the routing override and the pin (119 to 121).
