## 1. Purpose

Two artefacts, delivered together because they share one constraint (`26-chart-engine-design.md` §3.8: colour is a
256×1 LUT texture, not per-vertex data, so it must be swappable without a data re-upload):

1. **SCR-046 diagnostics overlay** — the `Ctrl+Shift+D` developer/owner telemetry panel, the in-app twin of the
   benchmark harness's JSON report (E06-K01). One counter vocabulary must describe both.
2. **Heatmap colour convention + CMP-113 HeatmapLegend** — the machine-consumable 256-entry colour ramp
   (owner decision #10: green = bid, red = ask, configurable) and its user-facing reading.

This spec is **token-referential only** (`--cv-*` / `color.*` names from `packages/ui/tokens/semantic-dark.tokens.json`,
never literal hex) so a later token change re-themes both artefacts for free — only contrast re-checks ride along with
a future token PR (per this ticket's dependency note on E05-D04).

## 2. SCR-046 — Chart engine diagnostics overlay

### 2.1 States

| State | Trigger | Behaviour |
|---|---|---|
| **Hidden** (default) | app boot | Overlay not mounted; zero GPU/CPU cost. Enabled from **SCR-118** renderer settings ("Show diagnostics overlay" toggle) or `Ctrl+Shift+D`. |
| **Shown, unpinned** | `Ctrl+Shift+D` | Floats top-right over the active chart panel; closes on a second `Ctrl+Shift+D` or `Esc`. |
| **Pinned** | user clicks the pin affordance | Stays open across panel focus changes and navigation; persisted per `apps/web` Zustand UI-state slice (`layout` domain), restored on reload. |
| **Threshold-breach** | any counter exceeds its §4.3 budget | That row's value chip switches to the danger tone **and** appends literal text `"above budget"`; never colour-only (`05-accessibility-standard.md` §4). |

- Container: CMP-069 InfoPanel shell (non-modal, dismissible, focusable on open).
- Header counters + per-stage rows: CMP-036 KeyValueRow (`dt`/`dd` pairs) — satisfies "static readable table" a11y
  requirement without extra markup.
- Per-stage sparklines: CMP-024 Sparkline, fixed-length ring buffer (30 samples = 15 s trail at 2 Hz), updated only on
  the 2 Hz tick — **never per rendered frame** (that would itself blow the 0.5 ms/frame overlay budget).
- Aggregate tone tile (top strip, "engine health" summary): CMP-178 SystemHealthTile, `tone` driven by whichever
  counter is worst (`ok` / `warning` / `danger`), always paired with the literal worst-counter name as text.
- "Copy diagnostics" button (CMP-001 Button, secondary variant) copies the harness-shaped JSON (§2.5) to the
  clipboard and shows a CMP-011-style transient "Copied" confirmation chip.

### 2.4 Interactions / hotkeys

- `Ctrl+Shift+D` — toggle shown/hidden.
- `Tab` / `Shift+Tab` — cycle pin, copy, close controls; overlay does not trap focus (non-modal).
- `Esc` — close (unless pinned; pinned overlay requires an explicit close click, matching "pinned" persistence intent).
- Screen reader: the whole panel is `role="region"` `aria-label="Chart engine diagnostics"`; row values update via
  `aria-live="polite"` at the 2 Hz sampling rate only — never per WS message or per render frame (this is the
  specific mechanism that satisfies acceptance criterion "cannot flood a screen reader").

### 2.5 Vocabulary sync with the harness (E06-K01)

The overlay and the harness JSON report **must** describe frame cost with the same nine §4.3 stage names, the same
units, and the same aggregate fields. Table below is the shared contract; E06-K01's `perStageMs{}` keys and this
overlay's row ids are the same strings — the nine `FRAME_STAGES` keys E06-K01 shipped
(`packages/chart-engine/bench/instrumentation.mjs`): `inputHandling`, `dataWindowRecompute`, `candleGeometry`,
`footprintTextGeometry`, `heatmapUpload`, `paneRedraw`, `overlayRedraw`, `domMirrorSync`, `compositePresent`. The
harness column is the shipped report shape (`BenchReport` in `packages/chart-engine/bench/report.mjs`): per-run
`p50` / `p95` frame time in ms, and one `machine{}` descriptor per run.

| Vocabulary key | Unit | Sampling | Definition | Overlay row | Harness JSON field (shipped `BenchReport`) |
|---|---|---|---|---|---|
| `fps` | frames/s | 2 Hz (overlay) / per-run aggregate (harness) | Reciprocal of measured frame time | FPS | derived from `p50`/`p95` |
| `frameTimeP50Ms` | ms | 2 Hz / per-run | Worker render-loop wall time incl. GL submission, rAF-to-rAF is NOT used | Frame p50 | `p50` |
| `frameTimeP95Ms` | ms | 2 Hz / per-run | As above, 95th percentile | Frame p95 | `p95` |
| `drawCalls` | count/frame | 2 Hz | Count of `drawArraysInstanced`/`drawElementsInstanced` invocations this frame | Draw calls | `drawCalls` |
| `gpuMemoryEstMB` | MB | 2 Hz | Estimate from tracked buffer/texture allocations, **labelled "(est.)" in the UI** | GPU memory | `textureMemMB` (+ tracked buffer bytes) |
| `bufferUploadsPerSec` | count/s | 2 Hz | `bufferSubData`/`texSubImage2D` calls per second | Buffer uploads/s | derived from `uploadedBytesPerSec` / avg upload size |
| `wsMessageRate` | msg/s | 2 Hz | Inbound WS frames/s across all subscriptions feeding the engine | WS message rate | not in harness (harness has no live WS; noted as overlay-only, justified below) |
| `droppedFrames` | count | 2 Hz, reset on read | Frames where composite+present missed the vsync deadline | Dropped frames | not in the shipped report (its `perStageMs` holds per-run stage means, not per-frame totals); overlay-only |
| `perStageMs.inputHandling` … `perStageMs.compositePresent` | ms | 2 Hz / per-run | The nine §4.3 stage costs, same 9 keys both sides | per-stage sparkline rows | `perStageMs{}` (9 keys) |
| `machine{}` | — | per run | The run's machine descriptor (`packages/chart-engine/bench/machine.mjs`): `cpu`, `cpuCount`, `totalMemMb`, `os`, `osBuild`, `arch`, `gpu`, `driver`, `webview2Version`; a run missing `cpu`, `os`, `osBuild`, `gpu` or `driver` fails | not on the overlay (harness-only, justified below) | `machine{}` |

**Justified single-sided counters** (acceptance criterion: "explicitly justified in the spec"):
- `wsMessageRate` is overlay-only: the harness drives synthetic scripted sequences with no live WS transport
  (`E06-K01` scope explicitly excludes network access), so there is nothing on the harness side to report. Recorded
  here rather than silently dropped from either side.
- `droppedFrames` is overlay-only: the shipped report keeps per-run percentiles (`p50` / `p95` / `p99`) and per-run
  stage means, not a per-frame series, so a dropped-frame count cannot be derived from it.
- Harness-only fields not surfaced in the overlay: `scenario`, `runtime`, `runtimeVersion`, `gpuFlags`, `machine{}`,
  `seed`, `lodProfile`, `repetitions`, `admissibleForAdrEvidence`, `p99`, `unattributedMs`, `textureMemIsEstimate`,
  `peakProcessMemSource`, `uploadedBytesPerSec` (raw bytes; overlay shows the derived per-second upload
  *count* instead, to keep the row list short) — these describe the *run*, not live engine state, so they don't
  belong in a live overlay. `peakProcessMemMB` is also harness-only (no cheap live signal at the process level from
  a Worker/OffscreenCanvas context); the overlay's `gpuMemoryEstMB` is the closest live proxy and is explicitly
  labelled an estimate to avoid implying parity.

This table is the "Counter vocabulary table" required by the Definition of Done and is the artefact
`14-screens-catalogue.md` SCR-046 and E06-K01 both should reference once merged.

## 3. Heatmap colour convention + 256×1 LUT

### 3.1 Convention (owner decision #10)

- **Default:** green = bid (buy-side depth), red = ask (sell-side depth). Configurable per user (SCR-118 renderer
  settings), stored as a single enum: `"green-bid-red-ask" | "red-bid-green-ask"`.
- Implemented as a **256-entry 1-D LUT texture** (`26-chart-engine-design.md` §3.8): index 0 = zero/no-depth,
  1–127 = bid ramp (near→far from mid), 128–255 = ask ramp (near→far). Swapping convention = swapping the two
  128-entry halves of the LUT — **one texture upload, never a data re-upload** (this is the acceptance-criterion
  requirement verbatim).

### 3.2 Ramp definition (generatable data, not a screenshot)

Five documented stops per side (matching the five `color.heatmap.{bid,ask}.1..5` semantic tokens already in
`packages/ui/tokens/semantic-dark.tokens.json`), interpolated across the 128-entry half in **perceptually uniform
space (Oklab)**, converted to sRGB at generation time:

| Stop | Position (index within half, 0=near mid, 127=far) | Bid token | Ask token |
|---|---|---|---|
| 1 (weakest, near-zero depth) | 0 | `color.heatmap.bid.1` | `color.heatmap.ask.1` |
| 2 | 32 | `color.heatmap.bid.2` | `color.heatmap.ask.2` |
| 3 | 64 | `color.heatmap.bid.3` | `color.heatmap.ask.3` |
| 4 | 96 | `color.heatmap.bid.4` | `color.heatmap.ask.4` |
| 5 (strongest, deepest liquidity) | 127 | `color.heatmap.bid.5` | `color.heatmap.ask.5` |

Index 0 (exact zero depth) uses `color.heatmap.zero` regardless of side, so an empty price level always reads as
the same neutral regardless of bid/ask convention.

Generation algorithm (implemented in E06-K04, specified here so the shader and legend can be generated from one
source):

```text
for side in [bid, ask]:
  stops_srgb = resolve_tokens(side)               # 5 sRGB colours from the token table above
  stops_oklab = [srgb_to_oklab(c) for c in stops_srgb]
  for i in 0..127:
    t = i / 127                                     # linear position within the half
    stop_pair, local_t = locate(t, positions=[0, 32/127, 64/127, 96/127, 1.0])
    lut_oklab[i] = lerp(stop_pair[0], stop_pair[1], local_t)
    lut_srgb[i] = oklab_to_srgb(lut_oklab[i])
lut[0] = token(color.heatmap.zero)
lut[1..127]  = lut_srgb(bid)   # index 1 = near mid ... 127 = deepest bid
lut[128..255] = lut_srgb(ask)  # index 128 = near mid ... 255 = deepest ask
```

Swapping convention = `lut[1..127], lut[128..255] = lut[128..255], lut[1..127]` — a slice swap, no recompute.

### 3.3 Intensity mapping (linear + log)

Given raw depth `v` (contract size at a price level) and view-window max depth `vMax`:

- **Linear:** `t = clamp(v / vMax, 0, 1)`; `index = round(t * 127)` offset into the bid or ask half.
- **Log:** `t = log1p(v * k) / log1p(vMax * k)`, with `k` a documented constant (**k = 8**, chosen so that depth at
  10% of `vMax` still resolves to a visually distinct band rather than crowding near-zero — matches the ticket's
  technical note formula verbatim). Default view mode is **log** (liquidity depth is heavy-tailed; linear crushes
  most of the book into the bottom 2–3 LUT entries in practice) with a per-panel toggle to linear.
- Both shader (LUT lookup) and CMP-113 legend (tick placement) **must** use this identical formula — this is what
  the acceptance criterion "legend tick values map to the same colours the shader produces" requires.

### 3.4 Age-decay curve

Heatmap columns older than the newest (per `26-…` §3.8's rolling-texture ring) fade toward `color.surface.sunken`
as they age out of the visible trail, so the eye reads "now" as most saturated:

- `age` = seconds since a column was the newest (0 at the newest column, up to the trail length — 4 h nominal,
  30 min for the B10 soak fixture).
- `decayFactor(age) = exp(-age / tau)`, **tau = 900 s (15 min)** — chosen so a column is still >85% of its original
  saturation at 2 min (recent detail preserved) and fades to <5% by 60 min (old columns recede without a hard cut).
- Rendered colour = `lerp(color.surface.sunken, lut[index], decayFactor(age))` — computed once per column on
  write into the ring texture, not per frame (protects the ≤2ms heatmap-upload budget in §4.3).

### 3.5 Colour-blind-safe candidate (open item O5 — candidate only, per this ticket's explicit out-of-scope note)

Green/red bid/ask fails deuteranopia/protanopia discrimination at low saturation. Candidate alternative recorded
for the M8 a11y pass to evaluate, not adopted here:

- **Candidate:** blue (bid) / orange (ask) ramp, same 5-stop structure, sourced from a new primitive pair
  (`palette.blue.{300,500,600,700,900}` already exist for `color.action.*`; a new `palette.orange.*` primitive
  ramp was flagged as a token gap, now closed by E47-S06's `palette.cvd.orange.1..5` — see §5).
  This pair has a larger CIEDE2000 separation under deuteranopia/protanopia simulation than green/red at matched
  lightness, per standard colour-vision-deficiency palette guidance (Okabe–Ito style blue/orange pairing).
- Convention enum would extend to a third value (`"blue-bid-orange-ask"`) if adopted — no architecture change
  needed since the LUT is already index-based per side.
- **Decision deferred** to O5 / M8 owner; this spec does not select it.

## 4. CMP-113 HeatmapLegend spec

### 4.1 Layout

```
+---------------------------------------------+
| Bid liquidity        |        Ask liquidity |
| [deep ██ mid ▓▓ near ░░] 0   [░░ near ▓▓ mid ██ deep] |
|  1,200          600         0   600          1,200   |
+---------------------------------------------+
Green = bid/buy liquidity · Red = ask/sell liquidity   (text, not colour-only)
```

- Composed of CMP-035 LegendItem (per this ticket's referenced parent) rendered via CMP-037 SwatchLegendItem rows
  (catalogue's actual component for ramp legends) — one row per visible tick, side-labelled "Bid" / "Ask".
- Convention sentence ("Green = bid/buy liquidity · Red = ask/sell liquidity") is **always** rendered as literal
  text beneath the ramp, per CMP-113's catalogue a11y note — satisfies "non-colour reading path".
- `scaleType` prop switches tick placement between linear and log per §3.3's shared formula; tick values shown are
  the **raw depth values** (`v`), not LUT indices — a trader reads "1,200 contracts", never "index 127".

### 4.2 Non-colour reading path

- Legend ticks carry numeric value text (never swatch-only).
- Tooltip/cursor announcement (engine-side, `26-…` §12): hovering a heatmap cell announces
  `"{side} {value} contracts at {price}"` — intensity is available as text at the point of interaction, not only
  via the legend. This satisfies the ticket's "non-colour reading path (tooltip / cursor announcement carries
  intensity as text)" requirement independently of the legend widget.

## 7. Accessibility notes (summary)

- Overlay is a text panel (`role="region"`), never a canvas; `aria-live="polite"` at 2 Hz only (§2.4).
- All threshold states carry text in addition to colour, both overlay (§2.1/§2.3) and legend (§4.1/§4.2).
- Heatmap intensity is available as text via tooltip/cursor announcement independent of the legend (§4.2).

## 8. Performance notes (summary)

- Overlay: ≤0.5 ms/frame, 2 Hz sampling — achieved by sampling+redrawing sparklines only on the 2 Hz tick, never
  per rendered frame (§2.2).
- Heatmap: age-decay and LUT-index colour resolution computed once per column write (§3.4), not per frame,
  protecting the ≤2 ms `texSubImage2D` budget in `06-performance-and-load-standard.md` §4.3. Targets informed:
  B4 p95 ≤10 ms, upload ≤12 KB/s, texture memory ≤20 MB (LUT itself is 256×1×4 bytes = 1 KB, negligible).
