## 3. Conventions used for every component

The component sections in §8 cite these as "conventions §n" (the build conventions, revision 2, carry the same
numbers).

1. **Naming:** one Penpot variant component per CMP id, `CMP-0xx · Name`. Properties in Title Case (`Variant`,
   `Size`, `State` first, then the component's own axes); values are the catalogue's literal lower-case values;
   boolean axes are `true`/`false`; inner layers are named by anatomy part, and the shared state parts keep one name
   everywhere (`plate`, `locked`, `lock-badge`, `reason`, `focus-ring`). Each section's description shows the catalogue
   Props and A11y lines as this PR edits them, with the Markdown markers removed.
2. **Matrix rule:** every documented Variant × every documented State at the default size; every non-default Size at
   State=default for every Variant; component-specific axes once each unless the catalogue lists states for them.
   States the catalogue does not list are not invented, except the universal ones: `focus-visible` and `disabled`
   for every interactive component, `disabled-with-reason` wherever a control can be RBAC- or environment-gated
   (ticket AC3), and `hover` for every pointer control (one cell per Variant, one per checked value whose hover
   differs; a group's selected-option hover is a documentation sample). Derivable combinations are not drawn: a
   deviation from brief §10's full product, recorded as §6 C13.
3. **States:** hover → the variant's `.hover` token on a filled action (dark primary hover and active fills darken
   under #3925 and are not held to the 3:1 boundary; the label identifies the control); ghost and neutral surfaces →
   `color.surface.hover` with the label stepping up to `color.text.primary`; an unselected segment →
   `color.surface.hover` + `color.text.primary`; a selection control keeps its fill and gains a 1 px inner
   `color.text.secondary` outline (an unchecked outline steps from `color.text.tertiary` to `color.text.secondary`;
   the switch's off track keeps its fill too, so the knob keeps its contrast; the slider's unfilled track steps to
   `color.text.secondary` and its thumb does not change); a swatch → a 1 px outline outside it; a link →
   `color.text.primary`. focus-visible → the CMP-039 ring (2 px `color.focus.ring`, `border.focus` width, 2 px offset,
   radius +2), never inside a dimmed layer. active → `color.action.primary.active`, neutral/ghost →
   `color.surface.selected`. **Selected or pressed** (CMP-002 `Pressed=true`, CMP-003's selected segment; #3925's
   `selected` role) → a `color.action.selected` fill, a 2 px inner `color.border.selected` outline (`border.thick`)
   and a `color.text.primary` label or glyph, unchanged on hover (no selected-hover token, §6 A2). Plain disabled →
   the whole component at `opacity.disabled`, only for a control that is simply unavailable: its contrast rests on the
   exemption WCAG 1.4.3 and 1.4.11 give inactive components (05 has no disabled exemption of its own), and it is never
   used for an RBAC, environment or risk denial, which is always disabled-with-reason (`14-screens-catalogue.md`
   §0.5.5). **disabled-with-reason** (§6 D13) → a readable first-class state: only the control's shape (fill, outline,
   track, box) dims to `opacity.disabled`, drawn on a `plate` that paints below the content; the label and every glyph
   or value indicator that sat on that fill render above it at full opacity in `color.text.primary`, and a selected
   control's 2 px outline, which marks the selection, also stays at full opacity; the `locked` glyph renders at full
   opacity in `color.text.secondary`; the reason is a CMP-016 Tooltip above the control (side=top; beside the row,
   side=right, for an option in a vertical list, CMP-006); a colour swatch keeps its true colour. **Lock position, one
   rule:** status trails, identity leads — the lock is the last item of the control's row (after the label, or after
   the control's shape when the atom has no label of its own); icon-only controls never grow and carry a
   `size.icon.sm` lock badge in the bottom-right corner. Superseded by E09-D09 §2.2 T2 (#3953); the boards PR folds §3, D13, §9, the audit's gated rows and the catalogue States lines into T2, and T2 governs until then. loading → a CMP-014 Spinner (Buy/Sell: after the label, so
   the word and the arrow stay), width locked, no time cap; after 5 s the host shows slow-path text (§6 D15): an order
   submit says "Checking with the exchange…" and stays busy, with no Cancel, until the exchange resolves it; only a
   load, an export or a replay also offers a Cancel action.
4. **Colour never alone:** buy/sell keep their words and lead with `arrow-up`/`arrow-down` in every state (§6 D16);
   status tones carry their registry glyph.
5. **Auto-layout and density:** flex on every component and every internal container. Brief §10 allows no
   absolutely-positioned internals; this PR carves out five (the focus ring, overlay anchors, EXC-CMP-001-1, the gated
   plate and the icon-only lock badge), each placed by constraints and never measuring content, for you to ratify
   (§6 B3). Heights bind `size.control.height` or `size.row.height`, paddings and gaps bind the `space.*` aliases, and
   the `density` theme group re-points only the two heights, so a density switch changes nothing structural.
   `size.icon` never changes with density (§6 A10). Static documentation illustrations (recorded 2026-10-20) may
   place data-positioned marks absolutely inside one clipped board, with token-bound paint (CMP-039's
   RingOnCustomSurrogate chart).
6. **Typography:** UI text binds `type.ui.*`; every number binds `type.num.*` (JetBrains Mono, tabular),
   right-aligned where tabular.
7. **Icons:** only the 47 base registry glyphs, as `icon/{name}`; the stroke colour is the context's text token; the
   size is the semantic `size.icon` (16 px in both densities). Recorded primitive exceptions: the CMP-019 size scale
   (`size.icon.sm|md|lg`, §7) and the icon-only lock badge (`size.icon.sm`). An icon next to visible text is
   decorative; an icon-only control carries `aria-label`. The custom trading glyphs of brief §5 are drawn in slice 5.
8. **Shape tokens:** radius `radius.control` (controls), `radius.card` (cards, popovers, tooltips), `radius.badge`
   (chips, pills), `radius.dialog`; elevation `elevation.popover|dialog|card`; surfaces
   `color.surface.app|canvas|raised|overlay`; borders `color.border.subtle|default|strong`.
9. **Token mapping:** a catalogue token name that does not exist is mapped to a shipped semantic token and recorded
   in the component's token-mapping table (this PR rewrites the catalogue Tokens lines to match); where no semantic
   token can express it, an open question is recorded instead of inventing a token. Tokens another ticket is adding are
   named with their stand-in (none left in this slice: #3925 added `color.action.selected` and `color.border.selected`).
10. **Hit targets:** compact controls are at least 24×24 px (`size.control.height` = 24); a smaller glyph (checkbox
    box, radio ring, slider thumb) gets its 24 px row or rail as the hit area; a gated control keeps its full target,
    and an icon-only control never grows. Exceptions are logged per component; this slice has none.
11. **Resize & overflow:** heights are minimums: the in-app text scale (112–150 %) grows text while control and row
    heights stay fixed lengths, so a control grows and never clips; browser or OS zoom up to 200 % (05 §5.7) scales
    everything and narrows every container, where the same rules apply. One-line actions do not wrap and grow
    instead; labelled selection controls wrap with the control aligned to the first line; icon-only controls never
    grow; numbers never wrap or truncate. Each component's §8 entry states its own rule.
12. **Forced colors:** Windows/Electron is the P0 assistive-technology platform (05 §8.1). Each component's §8 entry
    maps its parts to system colours: text and icons `currentColor`; a 1 px border keeps every control's shape (a
    shape with no border at rest carries a transparent one, which forced colours paint ButtonText or CanvasText);
    selected, checked, pressed and on states are set explicitly to a Highlight fill with HighlightText content
    (`forced-color-adjust: none` on that part only, with system colours only); the focus ring is a Highlight outline;
    plain disabled is GrayText; a gated control's shape border is GrayText, while its label, its value indicators
    (knob, check, dot, thumb, a selected outline) and its lock stay CanvasText or ButtonText. A swatch, whose colour
    is its value, keeps that colour (`forced-color-adjust: none` and a 1 px CanvasText border, CMP-031).
13. **Catalogue edits:** a catalogue line states only what the catalogue said, what a binding rule forces, a token
    mapping, or a choice listed in §6 (e) as awaiting your approval; a choice you still have to make is held (§6 (f))
    and never written as decided.
14. **Build records:** the per-component build records quoted in §8 are written for you, without agent-internal
    names or process logs.

### (a) Token gaps (E05-D01's token files, outside this PR's write set)

- **A1 — Retune the five label-on-fill pairs below 4.5:1? Resolved by #3925** (merged 2026-10-20, ticket #3896). Every
  button label now clears 4.5:1 on every state fill in every theme: dark `color.text.on-action` on
  `color.action.primary.hover` 6.75:1 (was 3.54), high-contrast `on-action` on `primary.active` 4.56:1 (was 2.87),
  light `on-action` on `color.status.danger.default` 10.31:1 (was 3.45), high-contrast `on-action` on `danger.default`
  4.54:1 (was 3.83) and light `color.text.inverse` on `color.buy.hover` 8.37:1 (was 3.90). A label-on-fill matrix test
  (`tools/contrast/label-on-fill.json`, gated in CI) holds them. The components kept their bindings, so nothing was

  label at 6.75 and 9.79:1 identifies the control. **Affects:** CMP-001 and CMP-002 (no action left).
- **A2 — Add the missing state tokens?** No `color.status.danger.hover|active`, `color.buy.active`,
  `color.sell.active` or `color.action.secondary.active`. Danger hover and active are drawn unchanged, buy and sell
  active fall back to `.default`, and secondary active binds `color.surface.selected`, which equals the rest fill in
  dark and light, so a press shows nothing. The `selected` role of #3925 (a pressed IconButton, the selected segment)
  has no hover token either; a sibling name is needed, because `color.action.selected` is a value token and cannot
  also be a group. Nor is there a semantic border-width token for the 2 px selected outline (drawn with the primitive
  `border.thick`, §5.2). **Recommended:** yes, in the next E05 token pass (#3925 retuned these ramps without adding
  the missing states), then redraw those cells. **Affects:** CMP-001, CMP-002.
- **A3 — Which token draws non-text control outlines?** No `color.border.*` or `color.surface.*` token reaches 3:1 on
  raised and overlay in every theme (`color.border.strong` is 1.35–2.02:1; high-contrast `color.border.default`
  reaches 3.20:1 on app and 3.03:1 on canvas only), so the off track, the unchecked box and ring and the slider's rest
  track bind the text token `color.text.tertiary` (5.20–5.96:1 dark, 5.44–6.36:1 light, 10.36–11.87:1 high contrast).
  `color.neutral.default` matches it in dark and light but leaves the high-contrast on and off tracks only 1.18:1
  apart. The hover outline (`color.text.secondary`, D17) is the same kind of binding. **Recommended:** add a semantic
  control-outline token aliased to today's `color.text.tertiary` values, so nothing changes visually and no component
  binds a text token for a non-text part; keep `color.text.tertiary` until it lands, and add the dark knob pair

## 7. Icon optical sizes (the question raised on #161 from E05-T06)

**Proposal: adopt the brief's 16 / 20 / 24 px scale, with `size.icon` at 16 px in both densities.**

- **The two sources disagree.** The shipped primitives are `size.icon.sm|md|lg` = 12 / 16 / 20, with the semantic
  `size.icon` = md = 16. The brief (§5) and #271 say 16 / 20 / 24 at a 1.5 px stroke.
- **Why 16 / 20 / 24.** The base set is Lucide, drawn on a 24 px grid. At 12 px every glyph is halved: a 1.5 px stroke
  is 12.5% of the box, interior counters close up (`settings`, `filter`, `pin`, `disconnected`), and the result falls
  below a comfortable reading size for 13 px body text. 16 px is the smallest size at which the whole registry stays
  legible on this slice's boards; 20 px fits a 32 px control with 6 px each side; 24 px is the glyph's native grid, used
  by empty states and dialogs.
- **What changes.** `size.icon.sm|md|lg` become 16 / 20 / 24, and the semantic `size.icon` re-points from `md` to `sm`,
  so every control renders exactly as today (16). Code that sets an explicit `size="md"` on an icon grows from 16 to
  20 and should switch to the semantic default; the #271 registry is size-agnostic and follows the tokens.
- **What does not change: density.** The first round also proposed re-pointing `size.icon` to 20 px in comfortable
  density. That is dropped (§6 A10): the checkbox box, radio ring, switch knob and track, slider thumb and sm spinner
  bind `size.icon`, and brief §3 lets density change only spacing and row heights.
- **Knock-on.** The gated icon-only lock badge binds `size.icon.sm` (12 px today); under this proposal it needs its own
  12 px size.
- **Who does it.** A token change in `packages/ui/tokens` (E05-D01's files), outside this PR's write set: if you
  approve, the coordinator schedules it with the E05 token work. The `icon/{name}` components already draw every glyph
  on the 24 px grid, so no icon is redrawn.

- Should CMP-016 tooltips hug short text (as the 'Cyan' name tooltip is drawn) up to a 240 px maximum width? This affects CMP-016's own resize rule.

**Motion:** None. The ring appears and disappears instantly in both modes (no fade), so focus is never delayed; motion-safe equals motion-reduce.  
**Resize & overflow:** The ring is a CSS outline that follows its element's size and corner radius at any text scale and density; it never changes layout. A parent that clips (scroll areas, toolbars, table cells) must leave 4 px of room around a focusable child (the 2 px offset plus the 2 px width) or let the outline overflow; the ring is never cut off or hidden behind sticky chrome (WCAG 2.4.11).  
**Forced colors:** The ring is a real outline (never a box-shadow, which forced colours remove), set to Highlight at the same 2 px width and 2 px offset; outline: none without it stays forbidden.
