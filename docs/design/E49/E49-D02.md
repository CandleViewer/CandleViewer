## 7. The 403 / 404 disclosure clauses (AC 3; a security control, not cosmetics)

These restate E09-D09 and E42-D03 verbatim in effect (BQ-7); the lane's own `security-reviewer` pre-lens ran
on them (BQ-0: no `security-review` label, no added review) and the owner's `approved` stands for DoD 5.

- **D-1 An admin route 404s identically.** For a session without `admin:read`, `/admin/**` resolves to SCR-155
  client-side, before the admin route chunk is imported, with no network call; its copy, title and analytics are
  byte-identical to an unknown route's for the same session (D09 :170; `15` :1018; D03E42 :670–675). The "Try:" list
  is derived from the session's permitted routes, so it differs by session, never by route. This is the target, not
  the shipped router, which denies `/admin/**` by role and ships the invite screen in the main bundle (D03E42
  :670–675; E42-S01, E42-Q01). The API: a foreign account and an absent one get the same 404 (`22` :3280–3281), an
  unknown id the same `403 account_scope_denied` (`22` :6410); the rest is G-6 (F-15).
- **D-2 The capability, not the resource.** SCR-154 names the missing capability in E09-D09's vocabulary —
  never a resource name, a route, a raw permission code or an account label; the account variant echoes only
  the id the client itself asked for (D09 :158, :162; `15` :1012). Because every admin-area route is a 404 by
  D-1, a 403 is shown only for a resource the session may know exists (AC 3's second clause).
- **D-3 "Ask the owner", no request path.** No "Request access": no endpoint notifies the owner (D09 :160;
  D03E42 :668). `14` :3161 and :3164 still say otherwise; that text is A-1, open.
- **D-4 The Ref is opaque and real.** "Ref {instance}" renders `Problem.instance` only when a 403 body arrived — never
  empty, never synthesised client-side (D09 :161); it is the correlation id `urn:cv:req:{uuid}`, the `X-Correlation-Id`
  header's (`22` :18766; D09 :161 says `X-Request-Id`), so it encodes no account or user id (the ticket's Security notes).
- **D-5 The server audits regardless.** Every 403 writes `rbac.denied` whatever the UI showed; the client's
  own step-3 check sends no request and so writes nothing (D09 :166; `14` :85).
- **D-6 Nothing elsewhere reveals the area.** Navigation, palette, search, the DOM and every sentence name a
  capability, never an admin route or screen (D09 :174–183).
- **D-7 The echo is the pathname, scrubbed.** SCR-155 echoes the pathname only, never the query or the hash, and a
  segment in a route-manifest param position (`:name`; R-009 `/invite/:inviteToken` is PUBLIC,
  `apps/web/src/routes/manifest.ts` :37) renders as `…`, so a stale invite link echoes `/invite/…`, never its token.
  `error.404_shown`'s `route` is the matched route pattern (`*` for an unknown route and, by D-1, a denied admin
  route), never the raw path, so no token reaches analytics or an incident payload (C-12.6; `04` :560, WG6). This
  changes D09 :170 / :180's echo and `14` :3177's broken-link use: A-10.
