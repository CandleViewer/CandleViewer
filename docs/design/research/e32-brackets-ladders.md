## Locked, not relitigated

**C-2.6** (`CONSTITUTION.md`): every position-opening order, on every account, in every environment, including every fan-out leg, carries a native exchange-side stop-loss; rule-engine, client-side and OMS-managed exits are additional, never substitutes; no flag, environment or "advanced mode" disables it (**C-4.14**); an SL-attachment rejection means cancel / flatten and an `SL_ATTACH_FAILED` alert. The binding texts under it: `20` P4 and §3.5 `NativeStopGuard` ("refuses to submit any position-opening order that does not carry `stopLoss`"); `24` §8.8 rules 1–5 (attached on create; else `trading-stop` within 2 s of the first fill; watchdog every 5 s, >10 s naked = `critical` + fallback stop at `profile.fallback_sl_offset`; reconciliation re-checks; smarter stops **only tighten**); `28` B8 `position_protection` (`protected` reachable only from an exchange read; `sl.naked` → `raise_critical_alert`, `emit_naked_metric`, `attach_fallback_sl`; `sl.naked_unrecoverable` → `page_owner`, `consider_reduce_only_close`; `TIGHTEN_SL` guarded `tightens_only`; KILL never switches the stop off) and B1 `protection` (`sl_pending` → `sl_present` / `sl_missing`); `22` `placeOrder` ("A native exchange-side stop-loss is mandatory for every entry … No field, flag or profile setting waives it") and `setPositionTpSl` ("The stop-loss of an open position can never be cleared (C-2.6)"); `24` §8.10 (attaching a missing SL, tightening a stop and `closePosition` are never gated). **Shipped today** (`origin/main` `aa90fd114a8e5e71e88382225e0917725e8ccb89`): `oms/order_machine.py` records the native-stop verdict `FAILED` for any non-reduce-only order with `stop_loss is None` ("so no caller places it unprotected"); `accounts/profiles.py` `require_native_sl: Literal[True]` and the stop "never defined in R"; `21` `ap_native_sl CHECK (require_native_sl = true)`, `ix_pos_no_sl`, `ix_tgl_no_sl` (the safety alarm); `api/order_entry_gate.py` carve-out; `exchange/base/models.py` `TradingStopRequest` "always writes both TP and SL sides"; B8's bindings are stubs whose logic E32 owns (`b08_position_protection.py`). This research designs **no opt-out, no removal and no loosening**; US-ORD-013 scenario 3's "Explicit opt-out" is E30-D01 SC-4 / E30-D02 A-14's amendment and is not re-proposed (C7).

## 5. The non-removable stop: hard-lock vs explain-and-restore `(heuristic; PROPOSED)`

**5.1 The two paper-prototype arms (the §8 P4 stimulus).** **Arm A — hard-lock:** the stop field has no clear or remove affordance; `Delete`, `Backspace`, select-all-and-type-nothing and the pointer's clear glyph leave the value in place; one inline line explains and names the alternative; the field stays fully editable for tightening. **Arm B — explain-and-restore:** the field can be emptied; Apply is blocked with the reason; on blur or Apply the field restores the last valid stop and explains why ("Restored to 63,900.0 — every position keeps a native stop").

**5.2 Choice: Arm A, hard-lock with the explanation at the point of refusal.** Evidence: (1) **the plan already chose "refuse, explain, stay put"** for the sibling case — US-ORD-008 sc. 3 "the drop is refused with an explanation and the stop stays put"; the shipped order-entry gate refuses stop-loosening amends synchronously and never gates tightening (`24` §8.10); `22` `setPositionTpSl` refuses a clear; so client and server say the same thing (N4). (2) **Arm B misrepresents exchange truth**: while the field is empty the editor shows an unprotected position that is protected — the look D18 reserves for real danger (SCR-064 Performance "never optimistically as confirmed"; 06 §5.2) — and restore is an automatic value change the user did not make (N3) that a screen reader must announce as a change (A5). (3) **N5 error prevention beats N9 recovery** when the error is impossible by contract: there is nothing to recover. (4) Precedent cuts the other way — Sierra Chart ("Cancel the existing Target and Stop orders"), Quantower ("You can delete or limit orders or stops") and Bybit ("click Cancel next to the order") all allow removal — which is exactly why the refusal must say **who holds the stop and what the user can do instead**, not merely "cannot". **Risks of Arm A:** the field may read as read-only (mitigation: the value stays live, the caption says "move it", `Tighten to breakeven` and the ↑/↓ nudges show it moves; the pending-amend state shows an edit in flight); a user who expects the Bybit behaviour tries twice (mitigation: the line is persistent, polite once per attempt, never a toast). **Risks of Arm B** (recorded for the owner): the empty state, the surprise restore, and a window in which Apply with an empty stop could be sent by a stale client — refused by the server, but a refusal the UI should never provoke. Pending P4: if ≥3 participants read Arm A as "the app fighting me" **and** Arm B as protection, the choice flips (pre-registered flip rule).

## 7. The one-page mental-model summary for E32-D02 (PROPOSED; every line `(heuristic)` until §8 runs)

1. **A bracket is one thing the server owns.** The UI renders the `TradeGroup` (`algo.kind: bracket`) as one card: entry on top, the exchange-held stop and the target legs indented, one group status, one id, one cancel. Three peer rows are the failure.
2. **The stop is part of the entry, placed with it, held by Bybit.** "It is placed with the order, not after it" (E30-D02 `sl.note`); after the first fill it belongs to the position and only an exchange read says it is there (B8).
3. **Three classes, three words:** exchange-held · resting at Bybit, managed by CandleViewer · app-managed. Each carries one sentence on what happens if the app stops. "Emulated", "engine" and "native" never appear alone.
4. **An app-managed layer only ever tightens** the exchange-held stop (`24` §8.8 rule 5; `TrailSpec.only_tighten` binding). If the app stops, the stop stays where it last was, never lower.
5. **A ladder the user never typed is trusted when it is shown as real orders:** one table with cumulative columns and a running average, a totals row with the worst-case loss for the fully-filled ladder, the request count, and every rounding the generator made, in words.
6. **A ladder has one shared stop on the resulting position** (PROPOSED default pending G3); a reduce-only ladder adds no stop and says so.
7. **What is previewed is what is sent:** local numbers are `(provisional)` until `/trade-groups/preview` answers; the server's numbers win and the change is highlighted.
8. **Currency leads on risk, R leads on exits;** both are always on screen; R is never an input unit for the stop.
9. **The stop cannot be cleared, and the refusal is a sentence, not a disabled control:** "Kept at {price} — every position keeps a native stop. Move it instead." Tightening is free and immediate; loosening is not drawn (C1).
10. **The only empty stop field on an open position is `sl.naked`,** reached from D18's "Set stop by hand"; there Apply means attach and is never gated.
11. **Partial fills are text:** "covers 0.120 of 0.120 filled"; the TP ladder tracks the filled quantity and the last leg absorbs the rounding remainder.
12. **Residual risk is disclosed where it applies:** emulated OCO can double-fill (reconcile, "flatten to intended"); a stop removed at the exchange is re-attached by the watchdog within its 5 s scan (plan, E32-T02), with up to about 10 s unprotected — said out loud, never hidden.
13. **Every drag has a keyboard twin and every refusal has its reason at the point of action;** nothing depends on colour, hover or a hold.
14. **Hollow, dashed or hatched means estimated or absent protection, never a side** (E25-D01 §9.5's proposed `16` §6 rule; D18's hatched edge is the one hatch here).

## 8. Session protocol (ready to run; owner or a future moderator; nothing below has been run)

**8.1 Framing, participants, consent.** 5–6 sessions of 45 minutes: the owner (P1, tagged on every sheet because the owner also approves this report), the account managers (P2a / P2b, `10` §3) and, where available, comparable discretionary futures traders; at least one habitual keyboard-first participant for P6 (ticket Accessibility notes; `10` §3 assumes one manager prefers keyboard-first operation). Opening script (read verbatim): "Two things are fixed and are not what we test today: every order that opens a position carries a stop-loss held by the exchange, and that stop can be moved but never removed. We want to learn how you read a bracket and a generated ladder, and whether the stop's rules read as protection or as the app fighting you." Stimulus is **demo data only**: printed paper prototypes and the public pages of §2; no live or demo account is connected; no API key, balance or account id appears (ticket Security notes). Recording with consent; recordings live in the restricted research space, are redacted in this report (balances, symbols, ids) and are deleted after the report is accepted (ticket); `04` has no research-data clause (G7), so the E30-D01 protocol §1 consent text and the human-only viewing rule are reused verbatim. Pilot once as a dry run before the first participant.

**8.2 Stimulus (paper, from the boards once drawn).** Board 02 in two variants (one card vs three peer rows); board 03 in two variants (three columns vs the R2 table with totals); board 04's three wording cards; **board 05's two arms** (A hard-lock, B explain-and-restore) as clickable paper frames of SCR-064's stop field with a sequence for "try to remove the stop"; board 06's two read-outs (currency-first vs R-first); competitor stimuli: the TradingView brackets page, the Sierra Chart Attached Orders page, Bybit's TP/SL and Scaled Order pages, printed. **8.3 Probes and time budget** (consent 3 · primer 2 · P1 7 · P2 8 · P3 7 · P4 8 · P5 4 · debrief 3 = 42 min; the keyboard-first participant swaps P2 for P6 at 9 min = 43 min). Think-aloud throughout except the timed first reading of each card.

- **P1 — bracket read (RQ1, H1).** Show board 02 variant A for ~3 s, mask: "How many things did you just submit? What happens if you cancel this one?" (forced choice one / three / don't know; then verbatim). Repeat with variant B, counterbalanced. Then the chart frame: "Which line is the stop?" without colour (greyscale print). Record: answer, the element named, whether the connector or the glyph was named.
- **P2 — ladder trust (RQ2, H2).** Show board 03 variant A: "Would you press Place? What would you want to see first?" Then variant B; card-sort the columns and totals into must / nice / noise. Show the rounding disclosure line: "What does '+0.002 added to level 1' mean to you?" Record: would-place (y/n) per variant, the ranked columns, the disclosure read correctly (y/n).
- **P3 — wording (RQ3, H3).** Board 04: three cards (exchange-held / resting-managed / app-managed) with their sentences. "If CandleViewer crashes right now, which of these still protects you?" Score correct / incorrect per card; then the same with the catalogue's words ("native", "engine-managed", "emulated") on a second card set. Record the words participants use themselves.
- **P4 — the stop (RQ5, AC 2; H5).** Board 05: "Remove the stop." on Arm A, then Arm B (counterbalanced). Do not prompt for 15 s. Record: what they did, how many attempts, the first words (blocked / protected / fighting me / fine), whether they found "move it", time to first understanding (recording, 30 fps), and the preference with a reason. Then the loosen attempt and the `sl.naked` frame: "Are you protected right now? What would you do?"
- **P5 — R vs currency (RQ4, H4).** Board 06: forced choice "Which number did you read first?" on the stop card and on the TP card; then "Which number decides whether you place it?" Record per persona.
- **P6 — keyboard-only (one participant; mouse disconnected).** From a positions row: `Enter` opens the editor; tighten the stop by 10 ticks with `↑`; commit with `Enter`; `Tab` into the ladder table and read two rows; `Esc`. Record: Tab count to each stop, any unreachable control, focus return (y/n), whether a step needed a pointer, whether the pending state was perceivable without sight.
- **Debrief (3 min):** "Where did the stop's rules cost you the most time or attention, and what would have made them read as protection?" (verbatim; input to §5.3 copy, never a design change).

**8.4 Analysis.** Two independent affinity passes (the owner and a second human, or an agent on de-identified notes only); a finding needs **≥3 participants**; a single participant is a **signal**; H1–H5 are scored confirmed / refuted; the P4 flip rule of §5.2 applies; results are appended here as a dated addendum (OQ-5).
