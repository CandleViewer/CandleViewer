## 1. Purpose, scope, method and locked inputs

### 1.1 What this spec fixes

Fifteen admin surfaces (CMP-087, SCR-149, SCR-120, SCR-121, SCR-122, SCR-123, SCR-124, SCR-135, SCR-136, SCR-143, SCR-144, SCR-145, SCR-146, SCR-148, SCR-154) drawn **together** from the catalogue's ASCII skeletons, so that the four cross-screen questions the catalogue leaves open get one answer each (§4): how the re-auth state lives in the chrome and interrupts an edit, how destructive confirmations are graded, how "this value is old" and "this subsystem is down" look, and how a screen says "this will be recorded". Every state the catalogue lists per screen is inventoried (§7) with the board that draws it; every wireframe carries its data source, its budget and its audit/analytics events (§6). Out of scope, per ticket: hi-fi visual design and DS contributions (E42-D03/D04/D05), motion (E42-D04), and the screens other epics own — SCR-125..129 (E27), SCR-130..134 (E28/E39), SCR-137 (E43), SCR-140..142 (E16), SCR-147 (E04/E46), SCR-071/072/073 (E39-D01, #829) — referenced for consistency, never redrawn.

### 4.4 The re-auth interruption pattern (D2)

**Variant (a) — area window.** 1. The owner edits SCR-122; the badge reads "4:58 left". 2. At 5 min: polite "Admin unlock expires in 5 minutes". 3. At 1 min: assertive; the badge takes the danger tone. 4. Expiry while typing: nothing moves focus; the badge reads "Admin locked — unlock to save"; **Save stays enabled** and its description reads "Unlock admin to save"; the danger zone, toggles and row actions become disabled-with-reason with the same text. 5. The owner presses Save → SCR-149 overlays the page; the form content stays under the scrim; the save is held unchanged (method, path, body, `Idempotency-Key`). 6. Success → the held save is re-sent once → "Saved". 7. Cancel → "Not saved — unlock admin to save"; the page stays, the draft intact. The entry gate (the first `/admin/*` route of a session) cancels to the previous non-admin route (SCR-149 checklist).

**Variant (b) — per-action step-up.** 1. The owner edits SCR-122; no countdown anywhere. 2. Save → `403 step_up_required` (`users`). 3. SCR-006 "Confirm it's you" names the exact action ("Change alex's accounts"), password + code; the request is held unchanged. 4. Success → the identical request is re-sent once; the page confirms only on the server's answer. 5. Esc, expiry or the third failure → "Not saved"; the draft stays; nothing was sent. 6. A live grace window → the band shows "Still trusted for user changes · 02:14"; no dialog for 5 minutes. There is no entry gate: the admin routes render for the Owner at once and `admin.area_entered` is still recorded.

Both variants share: the overlay is the E09-D06 chassis (`alertdialog`, 60 % scrim, no blur, focus trap, focus on the password field, failures announced assertively, lockout state, Esc = safe no-op); the held request is never re-sent on its own after a network error (the `/auth/step-up` holding rule: the action may have executed, so the page says "outcome pending" and re-reads); E09-D06's "Not sent" is adapted to "Not saved" here (an order is sent, a form is saved; the rule is the same: nothing was sent and the draft stays); one-click arm and anything armed is not an admin concern here. The step-up classes a screen meets are stated on its frame so the owner can predict the prompt (CR-6): SCR-122 `users` (and `risk_caps` for the caps section), SCR-123 the `users` line is drawn: SR-025 (`04`) lists creating a user as a step-up action while `createUser` names no class — a contract gap (§13.2), SCR-124 `users`, SCR-135 export `audit`, SCR-145 `flags` / `killswitch` / `live_enablement` by row, SCR-146 `backups` (no grace), SCR-148 `flags` on / `killswitch` off.
