## 11. Security notes (for the security lens; ticket Security notes; the threat model E25-X01 is not on `origin`)

1. **Non-optimistic apply (AP-1 … AP-5).** "Applied" is entered on the 200 alone and the fields re-read the response body; the press and the in-flight state show "Applying…" and nothing else. No frame shows a value as in force before the server confirms it (`14` 1369).
2. **Fail-safe restore (AP-4) and the unknown outcome (AP-5).** A refused request — 403 `csrf_token_invalid` after the one re-send (`22` 16102), 403 `forbidden` once D04-G3 lands, or 503 — restores the last confirmed values; the before → after line names exactly what was not applied and "Try again" re-fills the attempt deliberately — no ambiguous, half-applied field state exists on any frame (the ticket's "a rejected change restores previous values"). An incomplete request (timeout, network) may have been applied: the client re-reads `GET /detectors/config` before any value is shown and never re-sends — `setDetectorConfig` has no `Idempotency-Key` (D04-G7) — and if the re-read fails too, no field shows a value as in force. A view closed in flight lands its outcome as the app-level CMP-045 toast and a reopened dialog re-reads, never an in-memory draft.
3. **The armed-rule warning is a blocking confirmation (CF-1 / CF-2), not only a callout.** It lists the affected armed rules before the write; when the dependency cannot be checked it treats every visible armed rule as affected and says so, with the scope line ("Rules outside your account scope are not shown." when the session is not the Owner; otherwise "Every armed rule on this server is listed.") — an error never reads as "safe". The callout stays on every fieldset for the at-a-glance warning while editing. **Fetch point and the residual window:** the armed list is re-fetched on the Apply press and the variant decided from that response alone (§4.4); a rule armed after the press and before the 200 is the accepted residual — the authoritative dependency check belongs server-side and is routed to D02-G6.
4. **Apply is Owner-only (D-4; BQ-04 ruled differently) — a client lock.** Until the contract scopes the config, a Manager's Apply would change thresholds feeding the Owner's armed rules that the Manager cannot list (`listRules` scope `granted_accounts`); the Manager frame locks every write with one notice and the `rbac.owner_only` reason, reads free. **At the base the server would accept a Manager's `PUT /detectors/config`** (`22` 13797 `settings:write` / `scope: self` and `x-permissions` 1102; `04` §7.2.2 row 9b ✔(own); the SR-018 matrix expects `manager: allow`) — the route is `not_mounted` on `main`, so nothing is exposed today, but the Manager lock is presentation and is not a control (C-12.4, C-2.12; `14` §0.5 rule 5). The control is D04-G3 (#4948), a blocker for the implementation ticket that ships the dialog (E25-S05 / HO-4): the `22` PR lands before SCR-059's Apply ships, and a Manager's dialog ships read-only only once the server refuses. Until it lands the gap is open — a Manager who calls the API directly changes thresholds that feed every user's armed rules, and no frame can prevent it. **Recorded as an E25-X01 input: the open Manager gap at the base.** The Viewer and view-as legs are D02's (S59-9, S59-10; `view_as_read_only`).
5. **Audit.** `detector.enabled_changed` / `detector.threshold_changed {detector, key, before, after}` are `14` 1370's words: `setDetectorConfig` declares no audit action and `21`'s closed set has no `detector.*` (D04-G6 — not C-2.9, whose list is order, auth, key and kill-switch events; `14` 1370 is the only source); the footer sentence "Changes are recorded in the audit log." is stamped D04-G6 on board 05 until the action is declared, and "audit log" links to SCR-135 only for a session holding `admin:read` and `audit:read` (the Owner today; §4.1, T2-14); the recording CTA is audited as `recorder.start` (`22` 5172).
6. **No step-up, by the standard.** SR-025's list (`04` 842) does not include detector config and `22` declares no `step_up_required` on `setDetectorConfig`; inventing one would add friction the owner has not asked for and would not close the Manager gap (which is a scope question, D04-G3). The CMP-044 confirmation is the control: recorded as an E25-X01 input, not a design invention.
7. **No arm token.** The settings write is not a live-account order path (§4.1; D02 D21 / §19).
8. **Honesty.** Every absent capability is a stamped inset, never a live field (BQ-14 RULED on #668); the dependency notice names its field shape as PROPOSED; the methodology samples are stamped as samples; no real identifier appears (the D05 synthetic set: BTCUSDT / ETHUSDT, 63,118.0, 0.71).
