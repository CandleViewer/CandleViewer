## 1. Purpose

E05 will author real token *values* (palette, type scale, motion curves, themes). Before `packages/ui`
is scaffolded (E02-T03 implements the Style Dictionary build), engineering and design need one agreed
answer to: what file format, what directory layout, what naming rule, what build outputs, and what
sign-off gate. This ticket is that contract. It adds no token values and no components — see
`docs/plan/16-design-system-brief.md` §11 for the merged contract text (this file is the working
spec/rationale; §11 is the authoritative merged section).

Out of scope (per ticket, belongs to E05/other tickets): palette/type-scale/motion values, component or
screen design, Storybook content, visual-regression baselines.

## 2. Tokens JSON format (Tier 1/2/3, W3C DTCG)

Source of truth is JSON in the [W3C Design Tokens Community Group format](https://design-tokens.github.io/community-group/format/):
`$value`, `$type`, `$description`, and alias references as `{path.to.token}` strings (never a bespoke
converter — this is the one shape Figma Variables, Style Dictionary, and any future tool all read).

- **Tier 1 — Global/primitive.** Raw values, no semantic meaning: `palette.green.500 = "#2EBD59"`,
  `space.1 = "4"`. Never referenced directly by a component or a screen spec.
- **Tier 2 — Alias/semantic.** Meaning-carrying names components consume: `color.buy.default =
  "{palette.green.500}"`, `space.field.gap = "{space.2}"`. This is the layer `15-component-catalogue.md`
  entries cite.
- **Tier 3 — Component.** Rare, only where a component needs an override the semantic layer can't
  express (e.g. `button.primary.background = "{color.action.primary}"`). Used sparingly; most
  components consume Tier 2 directly.

**Naming convention:** `category.subcategory.variant.state`, all-lowercase, dot-delimited
(`color.text.buy`, `color.action.primary.hover`, `space.field.gap`). Maps 1:1 to CSS custom properties
(`--color-text-buy`) and to Figma Variables naming. Where a group has both children and a leaf value
(e.g. `color.buy` needs children `hover`/`subtle`/`hc` *and* a base value), the base leaf is named
`color.buy.default` — a token path may not simultaneously be an object and a value (Style Dictionary /
Penpot constraint), confirmed against the real files below.

## 3. Directory layout

```
packages/ui/tokens/
├─ primitives.tokens.json       # Tier 1 — palette, space, size, radius, border, font, opacity
├─ semantic-dark.tokens.json    # Tier 2 — dark theme (source of truth theme; §2.1 of the brief)
├─ semantic-light.tokens.json   # Tier 2 — light theme (same names, re-mapped values; E05)
├─ semantic-high-contrast.tokens.json  # Tier 2 — high-contrast theme (same names; E05)
├─ component.tokens.json        # Tier 3 — sparing overrides
├─ density-compact.tokens.json  # density-mode overrides (§3 of the brief) — spacing/sizing only
├─ density-comfortable.tokens.json
└─ themes.json                  # theme + density activation map consumed by the build
```

This mirrors the two files that already exist in the repo (`packages/ui/tokens/primitives.tokens.json`,
`packages/ui/tokens/semantic-dark.tokens.json`, `packages/ui/tokens/themes.json`, built for E05-D01) —
this contract does not rename or move them; it fixes the *file split rule* going forward (one Tier-1
file, one Tier-2 file per theme, one Tier-3 file, one file per density mode) so E05 knows exactly where
light/high-contrast/density files land when authored.

**Theme file structure:** each `semantic-<theme>.tokens.json` uses the *same* Tier-2 token names as
`semantic-dark.tokens.json` (dark is the source of truth per brief §2.1) with different `$value`
references into `primitives.tokens.json` (or a theme-specific primitive, e.g. `.hc` high-contrast
variants). No new token names are introduced by a theme file — only re-mapped values. `themes.json`
declares which primitive + semantic files compose each named theme (`dark`, `light`, `high-contrast`)
and is the single place a build reads "what files make up theme X."

**Density mode** (`16-design-system-brief.md` §3: compact/comfortable) is a second, independent
dimension from theme: a `density-<mode>.tokens.json` file overrides only spacing/sizing Tier-2 tokens
(`space.*`, `size.control.height`, `size.row.height`, `size.icon`) — never colour or typography. A theme
and a density mode compose independently (dark+compact, dark+comfortable, light+compact, ...).

## 4. Style Dictionary build — outputs engineering may consume

One `style-dictionary build` run over `packages/ui/tokens/*.tokens.json` produces:

| Target | Output path | Format | Consumer |
|---|---|---|---|
| CSS vars (dark/light/high-contrast) | `packages/ui/build/css/tokens.{dark,light,high-contrast}.css` | `css/variables` under `[data-theme="…"]` | React app theme switch (single `data-theme` attribute) |
| TS token object | `packages/ui/build/ts/tokens.ts` | `typescript/es6-declarations`, `const tokens = {...} as const` + derived types | React components, Storybook, compile-time-checked token references |
| **Chart-engine export** | `packages/ui/build/engine/theme-uniforms.json` | custom `json/flat-rgba` (plain JSON, **flat, fully resolved — no `{alias}` left unresolved**) | `packages/chart-engine` WebGL shader uniforms — canvas rendering, cannot read CSS custom properties (C-2.16) |
| Electron main JSON | `packages/ui/build/electron/tokens.main.json` | custom `json/flat` | Electron main process (title-bar, tray icon, OS theme hint) — no CSS/TS parsing needed |
| Contrast-matrix report | `packages/ui/build/reports/contrast-matrix.{json,md}` | custom | CI gate + human review |

The exact Style Dictionary config and the full target table already live in
`docs/plan/16-design-system-brief.md` §11 — this ticket does not duplicate it (owned there per C-16.5);
this file only points at it and adds the two worked examples (§6) and the sign-off/lint rules (§5, §7)
that were missing.

**Engine export shape (binding on E02-T03):** every `color.chart.*`/`color.candle.*`/`color.footprint.*`/
`color.heatmap.*`/`color.node.*`/`color.buy.*`/`color.sell.*` token resolves to an object carrying
**both** a hex string and normalised float RGBA, because WebGL needs floats and a per-frame string parse
would blow frame budget #1 (≤16.6 ms p95, `06-performance-and-load-standard.md`):

```json
{
  "color.buy.default": { "hex": "#2EBD59", "rgba": [0.1804, 0.7412, 0.3490, 1.0] }
}
```

**Theme switching for the engine is a data swap, not a CSS cascade**: the engine host adapter loads the
resolved `theme-uniforms.json` for the active theme and calls the engine's typed "set theme" API with the
parsed object; it never reads `data-theme` or any DOM/CSS state (C-2.16, `26-chart-engine-design.md`).
E11 (and any later engine-consuming ticket) must not assume a CSS cascade drives engine colour.

## 5. Lint rule — Tier 1 never referenced directly by a component

A token-build lint step (run in the same CI job as the Style Dictionary build, `packages/ui` package
CI) walks every component/screen spec and Tier-3 file for a reference into `primitives.tokens.json`
(i.e. any token path under `palette.*`, `space.<n>`, `size.<n>`, `radius.<n>`, `border.<n>`, `font.<n>`,
`opacity.<n>` used outside of a Tier-2/Tier-3 `$value` alias) and fails the build. Concretely: the linter
parses each `component.tokens.json` (Tier 3) and each generated `tokens.ts` consumer import, and flags
any hex/px/raw literal or direct-Tier-1-path reference that did not come through a Tier-2 alias. This is
the enforcement mechanism for brief §2's rule ("Tier 1 — never referenced directly by components").

**Acceptance-criterion trace:** *"Given a token that exists in Tier 1 but is referenced directly by a
component, when the contract's lint rule is applied, then it is flagged"* — satisfied by this rule;
E02-T03 implements the linter script (`tools/style-dictionary/lint-tier1-refs.*`) and wires it into the
`packages/ui` build/CI.

## 6. Two worked examples, end-to-end

### 6.1 `color.buy`

| Stage | Value |
|---|---|
| Tier 1 (`primitives.tokens.json`) | `palette.green.500` → `$value: "#2EBD59"` |
| Tier 2 (`semantic-dark.tokens.json`) | `color.buy.default` → `$value: "{palette.green.500}"` (also `.hover → {palette.green.300}` `#6BD48A` as shipped, `.subtle → {palette.green.900}` `#0E3D1F`, `.hc → {palette.green.300}` `#6BD48A`) |
| CSS output | `--color-buy-default: #2EBD59;` under `[data-theme="dark"]` |
| TS output | `tokens.color.buy.default === "#2EBD59"` (typed, autocompletable) |
| Engine output | `"color.buy.default": { "hex": "#2EBD59", "rgba": [0.1804, 0.7412, 0.3490, 1.0] }` in `theme-uniforms.json` |
| Contrast | `color.buy.default` on `surface.canvas` validated ≥3:1 (chart data-ink, `05-accessibility-standard.md` §5.4 rule 4); `color.buy.hc` on any surface tier validated ≥7:1 (AAA stretch, high-contrast theme, rule 3/6). |

### 6.2 `space.field.gap`

| Stage | Value |
|---|---|
| Tier 1 (`primitives.tokens.json`) | `space.2` → `$value: "4"` × 2 = `4` unit steps; repo value `space.2 = "8"` (px, 4px grid step 2) |
| Tier 2 (`semantic-dark.tokens.json`) | `space.field.gap` → `$value: "{space.2}"` |
| Density override | `density-compact.tokens.json` may re-point `space.field.gap` at a smaller Tier-1 step; `density-comfortable.tokens.json` at the default step — same Tier-2 name in both, per §3. |
| CSS output | `--space-field-gap: 8px;` |
| TS output | `tokens.space.field.gap === "8"` (raw numeric string per Style Dictionary `css/variables` + `typescript/es6-declarations` convention; unit applied at the CSS layer) |
| Engine output | not included — spacing tokens are not part of the chart-engine's colour/typography uniform export (§4 filter `category: "chart"` / colour-only); layout spacing is a host-adapter (DOM) concern, never a WebGL uniform. |
| Contrast | N/A (spacing token, no contrast requirement). |

Both examples resolve Tier 1 → Tier 2 → all applicable outputs with no ambiguity, satisfying the ticket's
acceptance criterion for E02-T03 to implement against.

## 7. Accessibility — contrast ratios and gating sign-off

Per `05-accessibility-standard.md` §5 and brief §9:

- **Body text / labels:** ≥4.5:1 (WCAG 1.4.3 AA). **Large text (≥24px regular / ≥19px bold):** ≥3:1.
- **Non-text/UI component contrast** (buttons, field borders, focus rings, icon-only controls, meaningful
  chart axis/gridlines, buy/sell indicators themselves): ≥3:1 (WCAG 1.4.11 AA).
- **AAA stretch for critical state:** buy/sell primary actions and the LIVE/DEMO badge target ≥7:1 where
  the palette allows; the `.hc` token variants (`color.buy.hc`, `color.sell.hc`, `color.status.*.hc`)
  are the mechanism — `Ctrl+Shift+H` swaps the whole token set to these, app-wide, as a **first-class
  theme** (not a filter/overlay), matching this contract's `semantic-high-contrast.tokens.json` file.
- **Chart data-ink:** candle/footprint/heatmap/profile colour pairs ≥3:1 against `surface.canvas` at
  every gradient stop, independently validated (not spot-checked) — this is exactly the contrast-matrix
  build target in §4's table, gated in CI on any token-file change.
- **Focus ring:** `color.focus.ring` ≥3:1 against every adjacent surface tier, validated per tier, in all
  three themes.
- **Motion:** a `prefers-reduced-motion` token dimension exists for `motion.*` (brief §7); this is
  orthogonal to theme/density and is authored in E05, not this ticket.

**Gating:** the contrast-matrix report (§4) is generated by every token-file-touching PR's CI; a PR
that drops any required pair below its threshold fails CI (`packages/ui` package CI, feeding the
`unit-frontend`/coverage-adjacent gate — exact CI job name owned by CONSTITUTION §9, not restated here).
Accessibility specialist sign-off (below) is additionally required as a human gate before this contract
itself can move to Done.
