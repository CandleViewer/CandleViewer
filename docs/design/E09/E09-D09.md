## 1. Purpose, scope and method

### 1.1 What this spec fixes

The grammar every screen uses to say no: the four treatments a control can have for the current session (enabled; disabled with a visible reason; hidden; server-denied), the **decision rule** that yields exactly one of them, the fixed **reason vocabulary**, what happens when a role or grant changes **mid-session**, the two faces of the **403 landing** (never had / withdrawn just now) with the server signal behind each, how the **admin area stays hidden** without leaking, the a11y contract (`aria-disabled`, `aria-describedby`, focusability, announcements), the measured tokens, and the normative text in `14` §0.5 rule 5 and `15`. Out of scope (ticket): the RBAC policy itself (roles, permissions, `roles` / `role_permissions`), the admin screens beyond how they are hidden (E42), and the account-switcher scoping UI (E27), which consumes this grammar.

### 1.2 Method (honest)

Desk design and a heuristic evaluation under the ticket's Agent-delivery adaptations (owner decision 2026-09-25): the "two research sessions" are a written protocol for the owner to run (§13.2), the "two-designer dry run" is a written protocol plus this author's own worked application of the rule to the three test controls, recorded as a single-agent run (§2.4, §13.3); contrast and CVD are computed (§11, §12), never eyeballed; the security engineer's sign-off is the owner's, with the exact items to tick in §14.4. Frame: Nielsen's ten heuristics plus the trading heuristics of `05` (keyboard-first §3.1; no hover-only interaction §3.1 item 6; focus never silently moved §3.4 item 3; colour never alone §4; polite/assertive rules §6.2). Reference products are cited only where an earlier research ticket verified them (E42-D01 §2.1); nothing new was read from the web.

### 1.3 Locked inputs (built on, not re-decided)

- **Roles and permissions.** Three roles (`owner`, `manager`, `viewer`; C-12.4, `10` §7 "admin is a hat, not a role"). The permission vocabulary is the `x-rbac` blocks of `22` (38 codes; `24` §15.2 and `21` §10.1 are generated from it): `viewer` holds 13 read permissions and no write; `manager` holds 24, including `orders:write`, `positions:write`, `rules:write`, `recording:write`, `replay:write`, `killswitch:write` and `audit:read`; `owner` is `*`. Fourteen codes are held by no non-owner role (measured, §11 E): `accounts:write`, `admin:read`, `admin:write`, `audit:export`, `backups:read`, `backups:write`, `flags:read`, `flags:write`, `instruments:write`, `keys:manage`, `keys:read`, `rules:arm_live`, `users:read`, `users:write`. Authorisation is the 4-tuple `(permission, account ∈ grants, symbol ∈ allowed_symbols, environment enabled)` plus step-up for the dangerous classes (`24` §15.2); the server enforces, the client only presents (C-2.12, `04` §7.3).
- **What the session carries.** `GET /auth/session` → `SessionInfo` {`user.roles`, `permissions[]`, `account_scope[]` (`[]` = all for an owner, none for anyone else), `allowed_environments[]`, `kill_switch`, `step_up_expires_at`, `session{…}`} (`22`). The WS `permission_change` frame re-sends the identity subset (`user_id`, `roles`, `permissions`, `account_scope`) on every role, permission, grant or kill-switch change, **before** any `revoked` frame (`23` §9.5, §13.4); a frozen grant is not listed (`23` §4.3, #415).
- **The server's refusals.** `403` problem codes (`22` `x-error-codes`): `forbidden` (carries `required_permissions[]`), `account_scope_denied`, `step_up_required`, `session_read_only`, `view_as_read_only`, `view_as_expired`, `trading_disabled` (with `reason`), `risk_limit_breached`, `mfa_enrollment_required`; `404 not_found` "does not exist or is out of the caller's scope". - **The router.** `apps/web/src/routes/rbac.ts`: `/admin/**` denies non-owners with `denyAs: "404"`, every other RBAC-denied route renders 403; the decision is "never an authorisation grant". `14` §0.3 and §10: non-owners get 404 from the router and 403 from the API; SCR-155 copy identical to any unknown route.

## 2. The pattern: four treatments, one rule

### 2.1 The decision rule (D1, D2) — normative home: `14` §0.5 rule 5 (quoted in §16); this is its anatomy and proof

For any control, answer the questions in order; the first "yes" decides. The rule branches on what the session **carries** (`permissions`, `account_scope`, `allowed_environments`, the read-only and view-as flags), never on a role name, so a role it was not designed for gets a treatment without a rewrite (§2.4).

| Step | Question                                                                                                                                                                                                                                                                                                                                                                                                                                  | Treatment                                                                                                                                                                                                                                    |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Is the control's **destination** under `/admin/**` (a route, a nav item, a palette command, a deep link, a "manage…" button) and does the session lack `admin:read`?                                                                                                                                                                                                                                                                      | **T3 Hidden** — structurally absent from every tree; a typed URL renders SCR-155 (§6). Where the catalogue asks for an explanation (`14` §0.5.3), the control's **sentence form** appears instead (§2.2)                                     |
| 2    | Has the **server** just refused this control's action or route — `403 forbidden`, `account_scope_denied`, `session_read_only`, `view_as_read_only`, `view_as_expired`, or a WS `revoked` naming its target?                                                                                                                                                                                                                               | **T4 Server-denied** — a route lands on SCR-154 in the variant §5 chooses; a control shows the refusal at the point of action in the host's refusal anatomy (E30-D02 `refusal.*` for the ticket); then steps 3–5 re-run on the fresh session |
| 3    | In the **session** (`GET /auth/session`, then every `permission_change`), is a leg missing, checked in this order: (a) the operation's `x-rbac` permission ∉ `permissions`; (b) the target account ∉ `account_scope` — unless the kill-switch view names that account, which is the E30-D02 `frozen` state; (c) `live` ∉ `allowed_environments` for a live-targeting control; (d) the session is read-only (three strikes) or viewing-as? | **T2 Disabled with a visible reason** — the key of the first missing leg (§3.1)                                                                                                                                                              |
| 4    | Does a **state** the client knows positively block the action (profile cap, risk lockout, freeze, disconnected, arm locked, maintenance, no active key…)?                                                                                                                                                                                                                                                                                 | **T2** with the owning state vocabulary (E30-D02 §14, E17-D01, E39-D01): the same anatomy, other words. Not this spec's keys                                                                                                                 |
| 5    | Otherwise.                                                                                                                                                                                                                                                                                                                                                                                                                                | **T1 Enabled**. A missing step-up elevation is **enabled**: the press opens SCR-006 and the request is held and re-sent once on success (E09-D06 §2 item 7, E42-D02 D2); elevation is never a reason to disable                              |

Step 1 is the **one mandatory hiding case** (ticket AC 1). Everything else that the session may not do is shown, disabled, with its reason: hiding teaches nothing and reads as a missing feature; a reasonless disabled control reads as a defect `(heuristic, SCR-017's "what you cannot do" promise)`.

### 2.2 The four treatments — anatomy, states, keyboard and screen reader

- **T1 Enabled.** The host spec's control, unchanged. Nothing here adds a description for a step-up class; the dialog says before the press whether a code will be asked (E42-D02 D2).
- **T2 Disabled with a visible reason (D4).** _Semantics:_ the native element keeps its role; `aria-disabled="true"`; **never the `disabled` attribute**, so the control stays in the Tab order and a menu item stays arrow-navigable; `aria-describedby` points at the reason node, which is **in the DOM at mount** (§2.2 renderings). _Visual, every density and theme:_ the enabled fill goes (buy / sell / primary → `color.surface.raised` with a `color.border.default` hairline); the label stays the **full label** — E30-D02's `submit.label.*` keeps "BUY 0.250 BTCUSDT limit 64,010.0 · stop 63,900.0" — in `color.text.tertiary`; a `lock` glyph (CMP-019, `decorative=false`, name "Not available") leads the label in the same colour; the reason sentence in `color.text.secondary`. **Never `color.text.disabled`, never `opacity.disabled` on the label, glyph or reason** (measured 2.86–4.31:1 in every theme, §11): the state is carried by text + glyph + the fill change + `aria-disabled`, not by dimming (`05` §4; ticket a11y notes). _Two renderings:_ **(2a) inline** — the reason sits under or beside the control; the default for primary actions, fields, checklist rows, menu items (second line) and panel notices. **(2b) tooltip echo** — only for icon-only controls (CMP-002) and toolbar segments with no inline room: the glyph badge on the icon is the visible marker, the description node is visually hidden, and CMP-016 echoes it on hover **and** focus; the tooltip is a duplicate, never the only copy (ticket AC 2). _Sentence form:_ when the host is an empty state whose sole CTA is gated (`14` §0.5.3, E11-D04 D12) or the destination is hidden by step 1, the reason sentence stands alone, no button — an empty panel with one dead button reads as broken `(heuristic)`. _One notice, many pointers:_ when a whole panel is read-only for the session (SCR-060 for a viewer) one panel-header notice carries the reason and every gated control's `aria-describedby` points at that node, so the sentence appears once. _Keyboard (D12):_ Tab reaches it; Enter, Space or a hotkey bound to it changes nothing and **re-shows the reason inline** at the point of action with one polite announcement (E17-D01 D13); a screen reader hears the name, "unavailable" (from `aria-disabled`), then the reason. _Emits nothing:_ no audit, no analytics (ticket Observability).
- **T3 Hidden (D3).** The admin destination only. Router behaviour (§6), not a style: no placeholder, no disabled ghost, no palette command, no search hit, no title, no count.
- **T4 Server-denied (D7).** SCR-154 for a route in one of two variants (§5); for a control, the refusal at the point of action. The server audits `rbac.denied`; the page emits `error.403_shown` (analytics). The UI then re-renders from the fresh session: a route the session can no longer see stays on SCR-154; a control becomes T2 with its reason.

### 2.3 Where the data comes from (D10)

Permissions arrive **once**: `GET /auth/session` at bootstrap and after unlock, then the `permission_change` frames (`23` §9.5). The session store exposes `permissions`, `account_scope`, `allowed_environments`, `kill_switch`, the read-only and view-as flags; CMP-079 and every `disabledReason` atom read it through selectors. The required permission of a control is the `x-rbac` block of the operation it calls (`22`; generated into `24` §15.2), never a hand-written role check. **No control fetches its own permission; no per-control round-trip** (ticket Performance).

## 3. The reason vocabulary (D5)

### 3.1 The keys

Every T2 reason is one of these six keys, or a key of a registered **state** vocabulary (E30-D02 §14, E17-D01 §7, E39-D01's lockout and freeze). A screen never writes its own string. A reason names a **capability** (the verb) and never data: no balance, position, symbol, count, user name (except the view-as target the viewer chose), route or screen name. One sentence, ≤ 60 characters, full stop. The ask line "Ask the owner if you need it." appears only on SCR-154 and in the SCR-017 orientation card, never under a control: the owner is the only grantor (US-ADMIN-002), so inline it adds nothing `(heuristic)`.

| Key               | String                                | Condition (from the session)                                                                                                               | Where it may appear                                                                      |
| ----------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `rbac.permission` | "Your role can't {verb}."             | the operation's permission ∉ `permissions`, and at least one non-owner role holds it                                                       | T2 reason, panel notice, SCR-017 card; SCR-154 body (withdrawn variant adds " any more") |
| `rbac.owner_only` | "Only the owner can {verb}."          | the operation's permission ∉ `permissions`, and **no** non-owner role holds it (14 codes today, computed from `22` `x-permissions`, §11 E) | the same surfaces                                                                        |
| `rbac.account`    | "This account isn't assigned to you." | the target account ∉ `account_scope` (an owner never meets it)                                                                             | T2 reason; SCR-154 account variant; SCR-010's account-picker refusal (A-2)               |
| `rbac.env`        | "Live trading isn't enabled for you." | `live` ∉ `allowed_environments` for a live-targeting control                                                                               | T2 reason on SCR-060 / 061 / 074                                                         |
| `rbac.read_only`  | "Read-only after three wrong codes."  | the session answered `403 session_read_only` (5 minutes; survives lock and unlock, `22`)                                                   | T2 reason on every write; the banner of §3.3                                             |
| `rbac.view_as`    | "Read-only while viewing as {user}."  | `GET /auth/session/view-as` reports an active context                                                                                      | T2 reason on every write while viewing (E42-D02 D10; the C-2.6 carve-out stays enabled)  |

The chooser between `rbac.permission` and `rbac.owner_only` is data, not copy: it reads the role lists of `22` at build time, so a new role that gains a permission flips the wording for everyone without a copy change.

### 3.3 The three-strike read-only banner — final copy (D9; supersedes the provisional copy on E09-D06's `SCR-006 / three-strike-downgrade` frame)

CMP-028 `tone="warning"`, `role="alert"` announced once (E09-D06 §6), not dismissible while the state holds, in the shell band under the TopBar — the dialog is already closed (E09-D06 §3). **Title:** "Read-only after three wrong codes." **Body:** "Changes are off for 5 minutes. Market data keeps streaming; exchange-side stop-losses are unaffected." Every write control is T2 with `rbac.read_only` meanwhile. **No countdown:** the contract gives the client no `read_only_until` (§15.3 CG-2) and this product never times a security state from a client clock (E09-D06 §4); the banner clears on the next write the server accepts. The E09-D06 frame needs a re-export with this copy (§15.4 H-1).

## 4. Role or grant change mid-session (D6): degrade in place

### 4.1 What the user sees

The `permission_change` frame replaces `permissions`, `account_scope` and `roles` in the session store **atomically**; every gated control re-renders by §2.1 steps 3–5 **where it stands** — the layout does not move, nothing is removed. Then each `revoked` frame empties its subscription's panel into E17-D01's placeholder, "No longer shown — access to {account} was withdrawn.", with the account label taken from the client's own cached list, never from the frame's `message`; a narrowing keeps the panel and re-snapshots (`23` §9.5). One shell banner (CMP-028 `tone="warning"`, under the TopBar, dismissible once read): "Your access changed just now." with a "What changed" disclosure listing the removed verbs and accounts from the client-side diff (old set − new set); with a position panel open the disclosure adds "Open positions and their exchange-side stop-losses are unaffected." (C-2.6). If the **current route** now lacks its permission or account (e.g. `/journal` after `journal:read` went), the route is replaced in place by SCR-154's _withdrawn_ variant (§5) — the shell stays, nothing reloads. A disabled user gets `bye 4403` → SCR-001; a revoked session `bye 4401` → SCR-005 / SCR-001 (E09-D06); a kill-switch transition is E39-D01's `frozen` state, not this spec.

### 4.2 In-flight actions: the server is truth

A request sent before the change either **executed** (its answer arrives; the result shows in Orders through the `orders` topic or reconciliation), was **refused** with a `403` (T4 at the point of action: "Not sent — your access changed. {reason}"), or has **no answer** (network): "Outcome pending — see Orders", then `GET /orders?open_only=true` (E09-D06 §2 item 4). **The client never re-sends an unknown-outcome request, and never under a new `orderLinkId` or `Idempotency-Key`** (C-2.10). A request held behind an open SCR-006 when its permission vanishes is dropped and the dialog closes — "Not sent" (E09-D06 §2 item 7's abandonment path). When `orders:write` for the ticket's account leaves the session, one-click disarms and the arm pill reads LOCKED with the reason (the pill is E30-D02 §8's; this spec only says the arm must fall with the permission). Open positions stay open; native stop-losses are untouched (C-2.6).

### 4.3 In place, not reload — the rationale

(1) `23` §9.5 sends `permission_change` precisely "so the client can refresh its permission-gated UI without a reconnect"; a reload tears down every subscription and re-snapshots — the storm E09-D06 §2 item 1 avoids. (2) A reload during an in-flight order hides the one thing the user must see, its outcome. (3) Chart viewport, drafts and layout survive in place and die on reload. (4) There is no second code path: the same rule (§2.1) renders the new state, and a user who reloads anyway gets the identical state from `GET /auth/session`.

### 4.4 Announcements (`05` §6.2: discrete, once, never per tick)

## 5. The 403 landing (D7): "you never had this" versus "this was taken away just now"

### 5.1 The two variants and the server signal behind each

| Variant                       | Server signal                                                                                                                                                                                           | Client evidence                                                                                                                                    | SCR-154 copy                                                                                                                                                                                                                   | User action                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| **never-had**                 | `403 forbidden` (with `required_permissions[]`) or `403 account_scope_denied` on a route, deep link, typed URL or stale bookmark — or the client's own step-3 check on navigation, with no request sent | the cached session (bootstrap, or the last `permission_change`) **also lacks** the permission or account: nothing changed                          | H1 "You don't have access to this" · the vocabulary sentence ("Your role can't see the journal." / "This account isn't assigned to you.") · "Ask the owner if you need it." · link "Back to your workspace" · "Ref {instance}" | ask the owner                |
| **withdrawn**                 | the same `403`, **or** a `permission_change` / `revoked` that removes the current route's permission or account                                                                                         | the cached session **had** it, and either a `permission_change` arrived or the one `GET /auth/session` re-read the 403 triggers shows the leg gone | H1 "Your access changed" · "{sentence} any more — this changed just now. Anything you already sent was decided by the server: check Orders. Ask the owner if this is unexpected." · the same link and ref                      | check Orders, then the owner |
| disagreement without a change | a `403` while the fresh `GET /auth/session` **still** grants it                                                                                                                                         | server and client disagree and no change event exists                                                                                              | rendered as **never-had** (fail safe), with the ref; `error.403_shown {unexpected: true}`                                                                                                                                      | report the ref               |

- `required_permissions[]` on `forbidden` names the permission; the verb table (§3.2) gives the sentence. `account_scope_denied` carries no account field, so the page echoes only the account id the client itself asked for (its route or request), never a label or an existence hint from the server (SR-056, E09-X01 U25).
- Evidence order: a `permission_change` is the authoritative "changed just now" (it carries the new identity); the `GET /auth/session` re-read is the confirmation when the REST 403 lands before the frame; the 403 code alone never decides the variant. That one re-read is the only fetch SCR-154 makes beyond rendering the problem (SCR-154 says "without additional fetches": amendment A-4).
- "Request access" (`14` SCR-154) is not drawn: no endpoint notifies the owner (E42-D02 §6.14, O-F). The copy says "Ask the owner" and will carry the owner's contact route from Settings when E42 adds it.

### 5.2 What is audited

Server-side, for every 403 whatever the UI showed: `rbac.denied` {actor, role, resource, action, ip, reason, request id} (`14` §0.5 item 8; the registered code — not `authz.denied`, A-1). The client's step-3 pre-check emits nothing: no request reached the server, so there is nothing to audit. Client analytics only: `error.403_shown {variant, code, route}`; `error.404_shown {route}` for SCR-155, identical for an admin route and an unknown one.

## 6. The hidden area (D3, D8): router behaviour, an identical 404, no leak

The router (`apps/web/src/routes/rbac.ts`, `denyAs: "404"`) resolves `/admin/**` for a session without `admin:read` to SCR-155 **client-side, before the admin route chunk is imported, with no network call** (SCR-155 Performance) — so an admin route and `/nowhere` take the same path, in the same time, to the same page: "Page not found — There's nothing at {route}. Try: Workspace · Journal · Settings" (E42-D02 §6.14), the attempted route echoed as text, the same document title, the same `error.404_shown {route}`.

Nothing elsewhere reveals the area — the checklist every later screen inherits:

- **NavRail (CMP-071):** no Admin item, no gap, no placeholder, no disabled ghost (E10-D02; E42-D02 D6).
- **Command palette (CMP-059):** commands are built from the same session store; no `admin.*` command exists for the session; the no-results copy is the same for every query.
- **Search (CMP-054 / CMP-084):** users, keys, flags and backups are never indexed for a session without `admin:read`.
- **User menu (CMP-061):** the manager's own-actions log is the non-admin route "My activity" (E42-D01 OQ-15, E42-D02 D6); the role is shown as text.
- **Sentences and empty states (§2.2):** name a capability, never a route or a screen — "Recording is set up by the owner.", not "Open Admin → Recorder".
- **SCR-017 "what you cannot do":** verbs from §3.2 only; no screen name, count or route.
- **Deep links:** `/admin/users/{id}` renders the same SCR-155; the id is part of the echoed route text and nothing else.
- **DOM:** no "Admin area" landmark exists (CMP-087 never mounts); no title, breadcrumb or `aria-label` says "Admin".
- **Onboarding checklist (CMP-097):** an owner-only task is `aria-disabled` with "Only the owner can manage users." — a capability; its deep link is not rendered.
- **API:** the UI never calls an admin endpoint for such a session — no probe, no prefetch. Whether the API answers a hand-made request with 404 or 403 is SR-056's and E42's question, not this ticket's (§15.5 OQ-2).

### 9.2 `aria-describedby`

The reason node is rendered at mount and stays in the DOM while the control does; its text is swapped in place when the reason changes (never re-mounted, `05` §6.2 region hygiene). One node may describe many controls (the panel notice). The description is the reason sentence alone — never "Ask the owner", never the control's own label. The tooltip echo (2b) is a visual duplicate: the hidden description keeps the semantics, CMP-016 (`role="tooltip"`, hover **and** focus, Esc dismisses) only shows it. The HTML `title` attribute is never used.

## 14. Security (E09-X01 U25, D1-shared, SR-056; `04` §7.3)

### 14.1 The disclosure boundary: capability, never data

A disabled control may say **that** a capability exists and that this session lacks it ("Your role can't place orders.", "Only the owner can manage API keys."). It never says anything about the **data** behind it: no balance, position, order or symbol count, user or key label, account the session does not already hold, route, screen name or number of anything. The vocabulary is closed (§3.1) and the verbs are a table (§3.2), so a future screen cannot leak by writing its own string. The 403 page names the permission from `required_permissions` and echoes only identifiers the client itself sent.

### 14.2 Anti-enumeration

`/admin/**` is a router 404 identical in copy, timing (client-side, no fetch, before the chunk import) and analytics to an unknown route (§6); no nav item, palette command, search hit, title, landmark or empty state names the area; the onboarding card speaks in capabilities. The UI never calls an admin endpoint for a session without `admin:read`, so the UI path cannot probe. The REST `403` body is uniform whether a resource exists or the caller lacks scope (SR-056); `account_scope_denied` names no account.

### 14.3 The UI is never the security control

**Every treatment in this document is presentation. The server authorises every request against the 4-tuple of `24` §15.2 and answers `403` with a stable code and an audit record (`rbac.denied`) regardless of what the UI showed — a disabled button, a hidden route or a missing palette command is never relied on to prevent anything (C-2.12, C-12.4, `04` §7.3, E09-X01 D1-shared). No flag, density, theme or role variant changes this (C-4.14).**
