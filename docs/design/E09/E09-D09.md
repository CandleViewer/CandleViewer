## 1. Purpose, scope and method

### 1.1 What this spec fixes

The grammar every screen uses to say no: the four treatments a control can have for the current session (enabled; disabled with a visible reason; hidden; server-denied), the **decision rule** that yields exactly one of them, the fixed **reason vocabulary**, what happens when a role or grant changes **mid-session**, the two faces of the **403 landing** (never had / withdrawn just now) with the server signal behind each, how the **admin area stays hidden** without leaking, the a11y contract (`aria-disabled`, `aria-describedby`, focusability, announcements), the measured tokens, and the normative text in `14` §0.5 rule 5 and `15`. Out of scope (ticket): the RBAC policy itself (roles, permissions, `roles` / `role_permissions`), the admin screens beyond how they are hidden (E42), and the account-switcher scoping UI (E27), which consumes this grammar.

### 1.2 Method (honest)

Desk design and a heuristic evaluation under the ticket's Agent-delivery adaptations (owner decision 2026-09-25): the "two research sessions" are a written protocol for the owner to run (§13.2), the "two-designer dry run" is a written protocol plus this author's own worked application of the rule to the three test controls, recorded as a single-agent run (§2.4, §13.3); contrast and CVD are computed (§11, §12), never eyeballed; the security engineer's sign-off is the owner's, with the exact items to tick in §14.4. Frame: Nielsen's ten heuristics plus the trading heuristics of `05` (keyboard-first §3.1; no hover-only interaction §3.1 item 6; focus never silently moved §3.4 item 3; colour never alone §4; polite/assertive rules §6.2). Reference products are cited only where an earlier research ticket verified them (E42-D01 §2.1); nothing new was read from the web.

### 1.3 Locked inputs (built on, not re-decided)

## 2. The pattern: four treatments, one rule

### 2.1 The decision rule (D1, D2) — normative home: `14` §0.5 rule 5 (quoted in §16); this is its anatomy and proof

For any control, answer the questions in order; the first "yes" decides. The rule branches on what the session **carries** (`permissions`, `account_scope`, `allowed_environments`, the view-as context — and the three-strike read-only state once the contract exposes it, CG-2), never on a role name, so a role it was not designed for gets a treatment without a rewrite (§2.4).

Step 1 is the **one mandatory hiding case** (ticket AC 1) — the scope the orchestrator ruled on 2026-10-20 (A-6): a whole surface a session cannot see is hidden and hard-404s (`04` §7.3 applies there); a control inside a surface the session can see is never hidden. Step 1 therefore answers only for **navigation affordances** — a NavRail item, a palette command, a search hit, a breadcrumb, a bare link whose one job is to reach `/admin/**`; the checklist task "Invite a second user" (SCR-019), the row action "Edit risk caps" (SCR-063) and a "manage…" button represent a capability inside a surface the session sees, so they pass step 1 with their admin link dropped and are decided by steps 2–5 (§2.4 draws both) — the reading the earlier wording left open. **Non-RBAC `403`s are not this grammar's:** `csrf_token_invalid` (E09's CSRF design, SR-041), `kek_unavailable` (E27's key custody, ADR-0009), `live_trading_disabled` (E39's live gate) and `session_not_armed` (E30-D02's arm state, SR-043: the pill and `arm.*` — step 4's "arm locked" before a press, `arm.refused` at the point of action after one, §4.2) have their own owners and copy; no screen reaches for an `rbac.*` key for them. Step 2 names the RBAC, scope, session and view-as codes as this grammar's own and routes **any other `403`** — `trading_disabled` (§2.4 already does), `risk_limit_breached`, `session_not_armed` — to its owner's anatomy as a step-2 refusal. Everything else that the session may not do is shown, disabled, with its reason: hiding teaches nothing and reads as a missing feature; a reasonless disabled control reads as a defect `(heuristic, SCR-017's "what you cannot do" promise)`. An enrolment-only session (`22`: `permissions`, `account_scope` and `allowed_environments` empty; it may only enrol TOTP) never reaches these surfaces — the rule assumes a full session.

### 2.2 The four treatments — anatomy, states, keyboard and screen reader

- **T1 Enabled.** The host spec's control, unchanged. Nothing here adds a description for a step-up class; the dialog says before the press whether a code will be asked (E42-D02 D2).
- **T2 Disabled with a visible reason (D4).** _Semantics:_ the native element keeps its role (a checklist step stays `role="checkbox"` with its `aria-checked`; a menu item stays a menu item); `aria-disabled="true"`; **never the `disabled` attribute**, so the control stays in the Tab order and a menu item stays arrow-navigable; `aria-describedby` points at the reason node, which is **in the DOM at mount** (§2.2 renderings). _Visual, every density and theme:_ the enabled fill goes (buy / sell / primary → `color.surface.raised` with a `color.border.default` hairline); the label stays the **full label** — E30-D02's `submit.label.*` keeps "BUY 0.250 BTCUSDT limit 64,010.0 · stop 63,900.0" — in `color.text.tertiary`; a `lock` glyph (CMP-019, `decorative=false`, name "Not available") leads the label in the same colour; the reason sentence in `color.text.secondary`. **Never `color.text.disabled`, never `opacity.disabled` on the label, glyph or reason** (measured 2.86–4.31:1 in every theme, §11): the state is carried by text + glyph + the fill change + `aria-disabled`, not by dimming (`05` §4; ticket a11y notes). _Two renderings:_ **(2a) inline** — the reason sits under or beside the control; the default for primary actions, fields, checklist rows, menu items (second line) and panel notices. **(2b) tooltip echo** — only for icon-only controls (CMP-002) and toolbar segments with no inline room: the glyph badge on the icon is the visible marker, the description node is visually hidden, and CMP-016 echoes it on hover **and** focus; the tooltip is a duplicate, never the only copy (ticket AC 2). _Sentence form:_ when the host is an empty state whose sole CTA is gated (`14` §0.5.3, E11-D04 D12) or the control's only destination was an admin route (its link dropped by step 1), the reason sentence stands alone, no button — an empty panel with one dead button reads as broken `(heuristic)`. _One notice, many pointers:_ when a whole panel is read-only for the session (SCR-060 for a viewer) one panel-header notice carries the reason and every gated control's `aria-describedby` points at that node, so the sentence appears once. _Keyboard (D12):_ Tab reaches it; Enter, Space or a hotkey bound to it changes nothing and **re-shows the reason inline** at the point of action with one polite announcement (E17-D01 D13); a screen reader hears the name, "unavailable" (from `aria-disabled`), then the reason. _Emits nothing:_ no audit, no analytics (ticket Observability).
- **T3 Hidden (D3).** Navigation affordances to the admin destination only (step 1). Router behaviour (§6), not a style: no placeholder, no disabled ghost, no palette command, no search hit, no title, no count.
- **T4 Server-denied (D7).** SCR-154 for a route in one of two variants (§5); for a control, the refusal at the point of action. The server audits `rbac.denied`; the page emits `error.403_shown` (analytics). The UI then re-renders from the fresh session: a route the session can no longer see stays on SCR-154; a control becomes T2 with its reason.

### 2.3 Where the data comes from (D10)

Permissions arrive **once**: `GET /auth/session` **and** `GET /me` at bootstrap and after unlock, then the `permission_change` frames (`23` §9.5), each followed by one `GET /me` re-read because the frame carries no per-account mode (CG-3). The session store exposes `permissions`, `account_scope`, the per-account `mode` (`read` / `trade`, from `Me.accounts[]`), `allowed_environments`, `kill_switch` and the view-as context; CMP-079 and every `disabledReason` atom read it through selectors. **Sticky refusal:** after a `403 account_scope_denied` the refused control is T2 with `rbac.account` until the next `permission_change` or `GET /me` re-read changes that account's entry — the client never flips a refused write back to T1 on its own, so a server–client disagreement cannot loop (press, refuse, re-enable). The required permission of a control is the `x-rbac` block of the operation it calls (`22`; generated into `24` §15.2), never a hand-written role check. The owner-only chooser (§3.1) reads the role lists of `22` x-permissions **only once the E16 amendment lands**; until then the ruling (Key) is applied over the file and `recording:write` counts as owner-only. `allowed_environments` is not in `permission_change` (CG-6), so the environment leg refreshes only on a `GET /auth/session` re-read. **No control fetches its own permission; no per-control round-trip** (ticket Performance).

## 3. The reason vocabulary (D5)

### 3.1 The keys

Every T2 reason is one of these seven keys, or a key of a registered **state** vocabulary (E30-D02 §14 — today's owner of `lockout` and `frozen`; E39-D01 is planned, not yet designed — and E17-D01 §7 for the feed states). A screen never writes its own string. A reason names a **capability** (the verb) and never data: no balance, position, symbol, count, user name (except the view-as target the viewer chose), route or screen name. ## 4. Role or grant change mid-session (D6): degrade in place

### 4.1 What the user sees

The `permission_change` frame replaces `permissions`, `account_scope` and `roles` in the session store **atomically**; every gated control re-renders by §2.1 steps 3–5 **where it stands** — the layout does not move, nothing is removed. Then each `revoked` frame empties its subscription's panel into E17-D01's placeholder (§5 row "Revoked / permission change", line 132: "No longer shown — <reason>"), here — for `revoked.reason` `permission_revoked` or `account_scope_changed` (`23` §9.5) — "No longer shown — access to {account} was withdrawn.", with the account label taken from the client's own cached list, never from the frame's `message`; every other `revoked.reason` (`account_disabled`, `key_revoked`, `user_disabled`, `session_revoked`, `replay_session_ended`, `resync_rate_limited`, `topic_removed`) takes E17-D01's own `<reason>` fill, so no screen says "withdrawn" for a disabled account; a narrowing keeps the panel and re-snapshots (`23` §9.5). One shell banner (CMP-028 `tone="warning"` in the shell-band slot under the TopBar, DS-6; dismissible once read): "Your access changed just now." with a "What changed" disclosure (CMP-051 Accordion inside the band — CMP-028 has no slot for a disclosure; only its connection tones take a `details` string, `15`) listing the removed verbs and accounts from the client-side diff (old set − new set); with a position panel open the disclosure adds "Open positions and their exchange-side stop-losses are unaffected." (C-2.6). **One live region per event:** CMP-028 `warning` renders `role="alert"` (`15`), a role whose implicit live value is `assertive`; an explicit `aria-live="off"` on it would be contradictory ARIA that leaves the one-voice guarantee to how the host resolves the conflict, so this banner is mounted with **no live role at all** — no `role="alert"`, no `role="status"`, no `aria-live` (DS-6 asks CMP-028 for `live?: "assertive" | "polite" | "off"`, where `off` omits the role) — and the §4.4 row for the event is the only announcement (polite when nothing focused or armed is affected; assertive, once, when it is); the banner is the visible record, not a second voice. A banner's own `role="alert"` is kept for the three-strike banner alone (§3.3; E09-D06 §6). If the **current route** now lacks its permission or account (e.g. `/journal` after `journal:read` went), the route is replaced in place by SCR-154's _withdrawn_ variant (§5) — the shell stays, nothing reloads, and **focus is never moved**: the one exception is a **restoration** — when the replacement unmounts the element that held focus, focus would otherwise drop to `body`, so after the §4.4 announcement the client places it on the SCR-154 heading (`05` §3.4 item 3 forbids stealing focus from a live element — only a user action or an explicit `role="alertdialog"` may move it; restoring focus the DOM itself lost is not a move of the user's focus; §9.4). The same restoration applies when the control that held focus sits in a panel that `revoked` empties into "No longer shown" (CMP-078): focus goes to that panel's header or placeholder after the polite announcement, never to the route heading. A disabled user gets `bye 4403` → SCR-001; a revoked session `bye 4401` → SCR-005 / SCR-001 (E09-D06); a kill-switch transition is the E30-D02 §14 `frozen` state (E39-D01, planned), not this spec's. `allowed_environments` is not in `permission_change` (CG-6): a live environment enabled or disabled for the user mid-session shows after the next `GET /auth/session` re-read (unlock, a 403's re-read, a reload), not at once.

### 4.2 In-flight actions: the server is truth

A request sent before the change either **executed** (its answer arrives; the result shows in Orders through the `orders` topic or reconciliation), was **refused** with a `403` (T4 at the point of action: "Not sent — your access changed. {reason}" — `{reason}` is the vocabulary sentence for the code; a `trading_disabled` body **without** `reason` (the kill-switch FREEZE, the live-not-enabled refusal, `22` `Forbidden`) gets a sentence **derived from the session, never guessed**: `kill_switch` naming the account → E30-D02 `frozen`; `live` ∉ `allowed_environments` → `rbac.env`; neither → `inflight.not_sent.bare` "Not sent — trading is disabled for this account." and the one `GET /auth/session` re-read; a `403 session_not_armed` — a live order mutation without a valid `X-Arm-Token`, SR-043 — shows E30-D02's `arm.refused` at the point of action and disarms, not `inflight.not_sent`), or has **no answer** (network): "Outcome pending — see Orders", then `GET /orders?open_only=true` (E09-D06 §2 item 4). **The client never re-sends an unknown-outcome request, and never under a new `orderLinkId` or `Idempotency-Key`** (C-2.10). A request held behind an open SCR-006 when its permission vanishes is dropped and the dialog closes — "Not sent" (E09-D06 §2 item 7's abandonment path). When `orders:write` for the ticket's account leaves the session, one-click disarms and the arm pill reads LOCKED with the reason (the pill is E30-D02 §8's; this spec only says the arm must fall with the permission). Open positions stay open; native stop-losses are untouched (C-2.6).

### 4.3 In place, not reload — the rationale

(1) `23` §9.5 sends `permission_change` precisely "so the client can refresh its permission-gated UI without a reconnect"; a reload tears down every subscription and re-snapshots — the storm E09-D06 §2 item 1 avoids. (2) A reload during an in-flight order hides the one thing the user must see, its outcome. (3) Chart viewport, drafts and layout survive in place and die on reload. (4) There is no second code path: the same rule (§2.1) renders the new state, and a user who reloads anyway gets the identical state from `GET /auth/session` for every leg the session carries; the three-strike read-only state is carried by no field (CG-2) and stays identical only because the client never disables for it (§3.3) — writes are enabled before and after a reload, the server refuses them, and the banner returns on the next refusal.

## 6. The hidden area (D3, D8): router behaviour, an identical 404, no leak

The router (`apps/web/src/routes/rbac.ts`, `denyAs: "404"`) resolves `/admin/**` for a session without `admin:read` to SCR-155 **client-side, before the admin route chunk is imported, with no network call** (SCR-155 Performance) — so an admin route and `/nowhere` take the same path, in the same time, to the same page: "Page not found — There's nothing at {route}. Try: Workspace · Journal · Settings" (E42-D02 §6.14; the "Try:" list is **derived from the session's permitted routes**, so a Viewer without `journal:read` is never sent from a 404 to a 403, and it is identical for an admin route and an unknown route in the same session), the attempted route echoed as text, the same document title, the same `error.404_shown {route}`. This holds for the **rendered UI**: the shipped route manifest (`rbac.ts`, `/admin/**` with `denyAs: "404"`) and the lazy admin chunk are in the bundle any user can read — inherent to an SPA, rated Low by E09-X01 U25 — and the API's answer to a hand-made request is OQ-2 / SR-056.

Nothing elsewhere reveals the area — the checklist every later screen inherits:

- **NavRail (CMP-071):** no Admin item, no gap, no placeholder, no disabled ghost (E10-D02; E42-D02 D6).
- **Command palette (CMP-059):** commands are built from the same session store; no `admin.*` command exists for the session; the no-results copy is the same for every query.
- **Search (CMP-054 / CMP-084):** users, keys, flags and backups are never indexed for a session without `admin:read`.
- **User menu (CMP-061):** the manager's own-actions log is the non-admin route "My activity" (E42-D01 OQ-15, E42-D02 D6); the role is shown as text.
- **Sentences and empty states (§2.2):** name a capability, never a route or a screen — "Recording is set up by the owner.", not "Open Admin → Recorder".
- **SCR-017 "what you cannot do":** verbs from §3.2 only; no screen name, count or route.

## 9. Keyboard and a11y (WCAG 2.2 AA, `05`)

### 9.1 `aria-disabled` versus `disabled`, and focusability

| Case                                                                              | Attribute                                   | Focusable                                                              | Why                                                                                                                                                                 |
| --------------------------------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T2 for an RBAC, grant, environment or session reason (§3.1)                       | `aria-disabled="true"`; **no `disabled`**   | yes — Tab order kept; a menu item stays arrow-reachable, never skipped | the reason must be reachable by keyboard and screen reader; the `disabled` attribute drops the element from the focus order and with it the `aria-describedby` text |
| T2 for a state reason (frozen, lockout, disconnected, arm locked, …)              | the same                                    | yes                                                                    | one anatomy for every "no" (E17-D01 D13)                                                                                                                            |
| a control disabled by **form validity** (SCR-006 Confirm until both fields valid) | the host decides; native `disabled` allowed | per host                                                               | not a permission boundary; outside this grammar                                                                                                                     |
| loading                                                                           | `aria-busy="true"`                          | yes                                                                    | CMP-001                                                                                                                                                             |
| T3                                                                                | not in the DOM                              | —                                                                      | §6                                                                                                                                                                  |

### 9.2 `aria-describedby`

The reason node is rendered at mount and stays in the DOM while the control does; its text is swapped in place when the reason changes (never re-mounted, `05` §6.2 region hygiene). One node may describe many controls (the panel notice). The description is the reason sentence alone — never "Ask the owner", never the control's own label. The tooltip echo (2b) is a visual duplicate: the hidden description keeps the semantics, CMP-016 (`role="tooltip"`, hover **and** focus, Esc dismisses) only shows it. The HTML `title` attribute is never used.

### 9.3 Keys on a T2 control

| Key                                                          | Effect                                                                                                                                                  |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Tab` / `Shift+Tab`                                          | reaches it like any control; the CMP-039 ring (measured ≥ 5.86:1 on every surface, §11)                                                                 |
| `Enter` / `Space` / the bound hotkey (`Ctrl+Enter`, `Alt+…`) | nothing changes; the reason is re-shown inline at the point of action and announced once, politely (E17-D01 D13; E30-D02 `arm.refused` is the analogue) |
| `Esc`                                                        | closes the tooltip echo only                                                                                                                            |
| `↑` / `↓` in a CMP-041 menu                                  | land on the disabled item (its second line is the reason); `Enter` as above                                                                             |
| `Shift+F10` / Menu on a grid row                             | opens the row menu with its disabled items present (E11-D04 D10)                                                                                        |

### 9.4 Announcements and target sizes

Announcements are §4.4 plus: a T2 keystroke → polite, the reason; the three-strike banner → `role="alert"` once (E09-D06 §6); a 404 → the page's heading, as any route. **Nothing moves focus** on a permission change (`05` §3.4 item 3: only a user action or an explicit `role="alertdialog"` may move focus) — the two cases in §4.1 are **restorations**, not moves: when a route replacement or a `revoked` unmounts the element that held focus, the DOM would drop focus to `body`; after the announcement the client places it on the nearest stable heading — the SCR-154 `h1`, or the emptied panel's header / "No longer shown" placeholder (CMP-078) — never on the route heading for a panel case, and never while the focused element still exists. Target sizes are unchanged by state: ≥ 24 × 24 CSS px compact, 44 comfortable (`05` §3.4 item 7, CMP-002); the lock glyph sits inside the control's hit area and is not a target; the reason text and the tooltip echo are not targets.

## 14. Security (E09-X01 U25, D1-shared, SR-056; `04` §7.3)

### 14.1 The disclosure boundary: capability, never data

A disabled control may say **that** a capability exists and that this session lacks it ("Your role can't place orders.", "Only the owner can manage API keys."). It never says anything about the **data** behind it: no balance, position, order or symbol count, user or key label, account the session does not already hold, route, screen name or number of anything. The vocabulary is closed (§3.1) and the verbs are a table (§3.2), so a future screen cannot leak by writing its own string. The 403 page names the permission from `required_permissions` and echoes only identifiers the client itself sent.

### 14.2 Anti-enumeration

`/admin/**` is a router 404 identical in copy, timing (client-side, no fetch, before the chunk import) and analytics to an unknown route (§6); no nav item, palette command, search hit, title, landmark or empty state names the area; the onboarding card speaks in capabilities. The UI never calls an admin endpoint for a session without `admin:read`, so the UI path cannot probe. The REST `403` body is uniform whether a resource exists or the caller lacks scope (SR-056); `account_scope_denied` names no account. The claim is about the **rendered UI**: the route manifest and the admin chunk ship in the bundle (E09-X01 U25, Low), and the API's answer is OQ-2.

### 14.3 The UI is never the security control

**Every treatment in this document is presentation. The server authorises every request against the 4-tuple of `24` §15.2 and answers `403` with a stable code and an audit record (`rbac.denied`) regardless of what the UI showed — a disabled button, a hidden route or a missing palette command is never relied on to prevent anything (C-2.12, C-12.4, `04` §7.3, E09-X01 D1-shared). No flag, density, theme or role variant changes this (C-4.14).**
