## 3. The chip-state selector (PROPOSED; closes `types.ts` Q4)

One function of (`TransportState`, the retry state, the worst `TopicStatus` over live public subscriptions and its age, `meta.stale` on `ticker` / `book`, `exchange_state`) → the five chip values, applying D2's precedence: the transport values that stop the data first, then the topic rule for every other transport value, then Delayed only where the topic rule yields live. The chip keys on **retry state**, not on the raw value (B-1): E17-D01 §4 row 1 shows `reconnecting` "while a §9.2 retry is scheduled or in flight" and `offline` only "once auto-retry has stopped"; the shipped engine emits `connecting` for every socket it opens (`connection.ts` :272) and `offline` with a shell cause while the retry timer keeps running (:258–268, :502–503), so "Offline — retry stopped" is drawn only for `fatal` / `bye.reconnect: false`:

```text
offline, cause fatal                    → offline        (retry stopped: a fatal close 1002 / 1009 / 4400 — row 6; a 4403 — row 21 by Link.offline.closeCode, §10 F; or bye.reconnect: false folded into fatal by closePolicy.ts — row 21 with G12; the cause sentence is the region's L1, §10 B4 / E / F)
offline, a shell cause                  → reconnecting   (offline / tailnet_unreachable / backend_unreachable: the retry timer runs, connection.ts :258–268 — row 3's region and scrims, L1 the §10 D sentence; no counter and no countdown until G11)   B-1
reconnecting                            → reconnecting   (counter = Link.attempt; "~N s" from nextAttemptAtMs, approximate under jitter)
connecting, before the first auth_ok    → reconnecting   (no counter; word "Connecting…"; no scrims — nothing to freeze; row 1)   PROPOSED, Q1
connecting, after the first auth_ok     → reconnecting   (the attempt's socket is opening — :272 emits it for every socket; the region, chip and scrims persist; the countdown slot reads "Connecting…")
connected · degraded:lagging · degraded:saturated · shutdown_pending → the topic rule first:
    exchange_state.public_ws ∉ {connected, resyncing} or err exchange_unavailable → stale ("Stale — exchange feed down")
    meta.stale on ticker or book                                                  → stale ("Stale (server)")
    oldest live public topic age ≥ T2 (replay rs excluded; private + system never judged) → stale, strong ("Stale 15s")
    oldest live public topic age ≥ T1                                             → stale ("Stale 7s")
    otherwise, degraded:saturated → delayed ("Reduced rate ×N"; N = applied.throttle_multiplier; min display 5 s, T3; nothing while features.coalescing is false)
    otherwise                                                                     → live ("Live 42 ms"; lagging → tooltip numbers only)
D2 on one chip: every Stale flavour beats Delayed — a stale, server-stale or upstream-down public topic under a saturated transport shows Stale, never "Reduced rate ×N"; Delayed resumes on that topic's first fresh frame while saturated holds (T3's 5 s is anti-flicker between delayed and live, never a hold against a higher state).
shutdown_pending additionally raises the Read-only reason with the countdown (row 8); it is not a chip value.
```

Exits follow E17-D01 §4's exit column (warn fast, clear slow): `stale` clears on the first fresh frame of that topic, `delayed` on the next `healthy` / `lagging` frame **and** 5 s shown, `reconnecting` → `live` on `auth_ok` and the first public snapshots (the grid stays `reconciling` until the private snapshots and `system`). Resync storm (>5 resyncs / 60 s) is a tooltip detail, never a value (A4). Thresholds T1–T6 are E17-D01 §4.1's; entering is immediate for transport loss, Read-only and Resyncing, while Delayed follows the server's debounce (it already debounces the improving side, `23` §8.3).
