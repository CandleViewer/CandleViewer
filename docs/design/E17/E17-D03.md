## 1. The band, restated and checked

`23` §6.1.1 states the formula once; it is quoted here, not restated as a second list (C-16.5):

```
ideal_ms   = (window_seconds * 1000) / (pane_css_width_px * devicePixelRatio / 3)
bucket_ms  = smallest allowed value ≥ ideal_ms, from {100, 250, 500, 1000, 5000}
```

with the three-rule ladder (rule 1 the user's pin, rule 2 the client's derivation, rule 3 the server's `500` fallback), the clamp ("clamps upward selection at 1000 ms whenever `ideal_ms ≤ 2500`") and the 400 ms debounce of the re-derivation. Design owns two numbers and one affordance: **a column SHOULD occupy ≥ 2 and ≤ 8 device px**, the **3 device-px target** that is the `/3` divisor, and the "auto" affordance's appearance. Every input below is a planning assumption from §6.1.1 itself (`window_seconds` 900, a pane at ~62 % of the viewport width); the tool reproduces its six rows cell for cell and the contract test's seven boundary cases (2500 → 1000, 2500.1 → 5000, 1000 → 1000, 1000.1 → 1000, 500 → 500, 50 → 100, 6000 → 5000), and exits 1 if it cannot.

## 2. Legibility judgement (heuristic; no display viewed)

What has to be read: **a liquidity band** is a run of bright rows that persists across many columns, so it survives narrow columns by length — its legibility is luminance against `color.heatmap.zero` (measured by the tool from the token JSON with the WCAG 2.x formula of `docs/design/_tools/contrast_check.py` — the ten stops against `color.heatmap.zero` in the table below; `05` §4 and §5 item 4) and the visibility of its gap; **a single-column wall** is the hard case — one column at `color.heatmap.bid.5`, as wide as the column and no wider. `26` §3.6's heatmap LOD aggregates by the **max** of merged columns, so a wall survives when there is less than one device px per column; above 1 px per column no aggregation happens and a wall drawn into the narrower phase of a 1.32 px grid is a 1 px line. E06-D02 §3.4's age decay (tau 900 s) never dims the newest columns, so neither stimulus is faded. Colour is never the only channel (`05` §4 item "Heatmap bid/ask … + on-hover/focus text readout of side"; `26` §12 "heatmap intensity is also reflected in the tooltip and the cursor announcement"): the stimuli are judged by luminance, and the side words live in the legend, tooltip and mirror (E06-D02 §4.2), not in the pixels. ## 4. Debounced re-derivation, drawn (PROPOSED; scenario 4)

```
a pane resize, a DPR change (monitor move) or a trail (window_seconds) change starts — 23 §6.1.1's three
   triggers ─► the current columns stretch or compress through colTime (26 §3.8): the texture quad is
                remapped, nothing is re-uploaded, the pane is never blank; the chip shows nothing yet
400 ms after the last resize event, derived bucket ≠ active ─► ctl { time_bucket_ms } AND chip: "Re-sizing columns…"
   (23 §6.1.1; one ctl per settled resize; the pending text comes from the ctl, never from the first
    rung-crossing event — no scrim, no spinner over data, no error tone)
   ─► ctl_ok { resnapshot: true }  ─► snap, reason reconfigure (23 §5.4): the new columns replace the old
      in ONE frame (E11-D06 D14's rule: no crossfade, in both motion modes; reduced motion = the same cut,
      and heatmapFade off per flags.ts / the Accessibility settings) ─► chip settles to the new auto text
   ─► one polite announcement
```

- The client-initiated identity change is drawn like the depth-tier rebuild of SCR-051 ("1–2 s rebuild state"), **never** like Stale, Resyncing or Delayed (E17-D01 D15: a `snap` with a routine reason shows nothing beyond the chip's pending text; no scrim).
- A resize that stays on the same rung sends nothing and shows nothing, and so does a drag that crosses a rung boundary and comes back within the debounce — the pending text is tied to the `ctl`, so it cannot flicker during a drag; the columns simply re-map (a resize that settles on alternate sides of the 1080-device-px boundary is Q1 — the formula has no hysteresis, the 400 ms debounce is its only guard; E06-D01 §2's LOD hysteresis is a precedent, not a design made here).
- The `estimated` / hatched case (columns produced while the book resyncs: `24` §6.3, `25` §3, E17-D01 §5) is untouched by this flow and the stimuli draw no hatch (C6).
- **If the `snap` is slow:** the chip's pending text persists; the old columns stay drawn through `colTime`; no spinner over data; after T1-class silence the ordinary Stale rules of E17-D01 §4.1 apply to the pane as to the book — this spec adds no threshold. A `ctl` refused for the rebuild budget (`resync_rate_limited`, `23` §5.4) is not applied: the client keeps the last `effective` bucket, backs off per `23` §8.5 and re-derives when the back-off ends; the chip returns to the active value meanwhile (no error tone — the pane is live); the pane shows `23` §10.3's inline pane notice once, politely — its copy is a PROPOSED key for E17-D01 §7's owner (no screen writes its own string), and a refused pin is named in it, never reverted silently.
