What the three moving rows mean, beyond the table:

- **D9-03, the snap latch (BQ-06).** The marker is D02's 10 px ring with the value text "High 65,400" beside it
  (`D02`:332), in TP-13 `color.drawing.snap` (R352 BQ-05). The value text is part of the static marker: it appears as
  a cut at the latch, in the existing drawing-label batch (`26`:224), so T's "no new text" holds because the motion
  adds none. The motion is the ring alone. Starts are capped per HS-1: at least 500 ms between settle starts on the
  marker; when latches change faster, the latest latch wins, nothing queues, and the ring is drawn at rest (a cut).
  The same entry serves weak and strong magnet and the keyboard snap cycle (`Ctrl+↑` / `Ctrl+↓`). The magnet mode is
  carried by the magnet button's name, never by motion. Nudges never snap (`D02`:332). The polite announcement keeps
  D02's cadence (`D02`:525). Budget: inside B8's ≤ 12 ms (`26`:682) and SCR-037's ≥ 58 fps (`14`:954), because it is
  the one row that runs during a drag.
- **D9-05, the selection emphasis (BQ-07).** The end state, the `color.drawing.selected` outline and the handles, is
  drawn in frame 0, and the halo only emphasises it: its colour is the end state's own, so the motion adds no meaning
  and no token. TP-11 and TP-13's focus hue stays with the active handle and the snap ring, and R352 BQ-05 keeps
  those two apart: "the 10 px ring + value text vs the 8 px dot keeps the two apart by shape". A press that
  crosses the drag travel threshold (`D02`:291) cuts the halo to rest in that frame (DNA-4). Multi-select (the tree,
  Select area) emphasises nothing on the canvas: the count chip "7 selected" carries it (`D02`:283). More than 20
  objects selected at once means no halo, by HS-1's per-frame cap. Selection from the tree uses the same entry; the
  tree's coupled row is D9-13, a cut.
- **D9-09, the undo restore (BQ-08).** The pair is kept. On the canvas, the D9-05 halo plays on the restored object
  over `motion.duration.slow`, started in the same frame as the tree row's. The restored object is selected and
  focused (`D02`:428), so the static end state carries the answer too. In the tree, D07's row flash (`D07`:216)
  becomes an opacity overlay pre-tinted in `color.surface.selected`, from 1 to 0, so the row looks as D07 drew it at
  the start and no fill colour tweens. **CR-1 is RULED: E05-D03 row 3, restored-row use (RULED #353 BQ-08)**, cited by
  R353's comment id until E05-D03's PR 2 lands it as one more A-row. A bulk undo (`D02`:537's "497 drawings
  deleted") emphasises at most 20 objects per frame, the first 20 in the tree's order, and at most 21 824 px² of halo
  in any 341 × 256 px region (§6); the rest carry D07's "restored" tag and the count announcement. An undone move cuts
  the geometry back to where it was (DNA-1) and then emphasises it at its restored place. Redo uses the same entry.
  D07's word "decorative" gets a one-line delta (§11): the emphasis now carries which object returned.

The cuts that touch persistence (BQ-09): creation (D9-11) and delete (D9-10) never animate (DNA-5), so no motion
implies a server state. Writes are optimistic (`26`:262); persistence is carried by words, the "not saved" tag and
chip and the save-failed path (`D02`:500; `D04`:297-300), which this spec cites and does not change. Delete's undo
affordance is E05-D03 row 4a's toast. A rejected delete puts the drawing back as a cut with the unsaved or conflict
tag (`D02`:500-501). That is T's failure-restore path, and it uses no motion.

## 3. The do-not-animate list

**T's four clauses, quoted byte for byte from `E14.json`:675 (§Scope / Deliverables, third bullet).**

- DNA-1: "price-anchored geometry never eases to a new position (it would misrepresent where the object is)"
- DNA-2: "live VWAP values never count up"
- DNA-3: "drag never has inertia"
- DNA-4: "nothing in the kit animates during an active drag except the snap indicator"

**The additions, each from a parent or T's own text.** The tool pins the bold sentence of each.

- **DNA-5. No drawing animates into existence or away.** Creation and delete are cuts (D9-10, D9-11), because a
  fade would imply a server state the write has not reached (T §Security notes; BQ-09).
- **DNA-6. The tree never scrolls smoothly to a coupled row.** The row gets a mark and a jump control, never an
  auto-scroll (D9-13; `D07`:21).
- **DNA-7. A scale, interval or theme change re-projects every drawing in one frame.** The geometry is never eased
  to its new screen position (T AC 5, "after an undo or a scale change").
- **DNA-8. An anchored VWAP's live update is a cut and not an undo step.** The line is redrawn at its new values in
  one frame, as DNA-2 asks for the numbers (`D02`:506).

**AC 5's rationale, recorded.** A proposal to ease a drawing into a new position, after an undo (DNA-1) or a scale
change (DNA-7), is rejected: every intermediate frame would draw the object at a price and a time it never had, and a
user who trades against a level must see where it is, not where it is going.

**Agreed with the chart-engine engineer.** The list is agreed through the E14-T04 (#359) implementer's
acknowledgement on the engine card, the stand-in R352 BQ-15 set (E14-T04 is "the engine card with the
implementer's acknowledgement"). E14-D11 consumes the list as written here.

## 4. Canvas and DOM: engine motion entries

E05-D03's recipes are DOM recipes and leave the engine to E11 (`E05-D03`:246-250). The canvas rows here are
**engine motion entries, not recipes** (BQ-05):

- **Tokens.** They use the same seven tokens by name, and MR-1 to MR-3 and HS-1 as written. Each animates one
  property: an instance alpha (the GL form of `opacity`) or a scale uniform (the GL form of `transform`).
- **How the durations reach the engine.** As `EngineTheme.metrics`, beside the handle numbers and the magnet radius
  (R352 BQ-04: "the 8 / 10 / 24 px handle numbers and the 12 px magnet radius travel as `EngineTheme.metrics`
  (routed to E14-T04 #359)"). `EngineTheme` carries `colors` only today (`handle.ts`:9-13): G-1.
- **Cost rules per canvas row.** **+0 draw calls**: the ring and the halo are instances in the drawings layer's
  existing batch (`26`:224, :257-263). Only the drawings layer is dirtied (`D02`:553). The entry is time-based
  (`26`:130), so a dropped frame never changes its outcome, and the loop parks again when it ends (`26`:133).
- **DOM rows.** D9-01, D9-12 and D9-13, the tree half of D9-09 and the DOM halves of the cuts never trigger
  layout on the chart container (T §Performance notes): only `opacity` or `transform` animate, and the cuts change
  attributes and text inside the rail, the popover or the tree.

## 5. Reduced motion, focus and announcements

- **The carriers (BQ-10, AC 2).** Every row names its carrier in §2 (MR-3). For the three moving rows: D9-03, the ring
  and its value text at rest and the polite "High 65,400."; D9-05, the selected outline, the handles, the
  surrogate's `aria-pressed` (`D02`:326) and the tree row's `aria-selected`; D9-09, the selected and focused object,
  D07's "restored" tag for 10 s and "Undone: …" (`D02`:535). D02's own reduce row already asks for "static emphasis
  for snap, selection and undo" (`D02`:507).
- **Canvas reduce is `RenderFlags.animate = false`.** As shipped, a flag that is off snaps its effect to the resting
  value (`flags.ts`:34-37). That differs from E05-D03 §6.4, where a running DOM transition completes on its clock
  when the mode flips (`E05-D03`:221-226): C-1, accepted, because the canvas rest state is the reduce end state and
  carries the same information. DOM rows follow E05-D03 §3 and §6.4 unchanged.
- **No flash.** Nothing flashes more than 3 times a second (MR-1, `05`:208); §6 shows the arithmetic for the one
  repeating row (D9-03) and the bulk restore.
- **Announcements and focus never wait on motion.** Each is applied in the frame its state is applied, inside a
  running entry too. Focus moves only on a user action: an undo that restores a drawing focuses it (`D02`:428).

## 6. The frame budget: evidence plan (AC 4)

recorded here. There is no drawings layer to measure yet and no B8 scene (`m0-report.mjs`:733), so the evidence
comes in three layers, each recorded per canvas row (BQ-11). **The prototype is not the engine**: every figure from
it says so.

## 8. The in-motion review, the protocol and the walkthrough (A28)

**BQ-13, RULED (orchestrator, 2026-10-30, #2701 ledger addendum A row A28).** For Done, "reviewed in motion" is met
by the orchestrator's delegated in-motion review on PR 2: the Opus lens plays the three prototypes through the runner
(frame captures at start, middle and end for each entry and its reduce form, plus the measure mode) and records the
verdict on the PR. "3 participants" is met by the protocol below plus the heuristic evaluation. The owner's own run
is a walkthrough item after Done, not a gate: **owner walkthrough: post-Done (#2701)**. No participant, timing or
quote is invented.

**Heuristic evaluation (heuristic; no participants).**

- H-1 (heuristic). Visibility of system status: the snap settle (D9-03) shows the latch while the pointer moves, and
  the value text names it, so the user never has to infer the latch from the pointer's position.
- H-2 (heuristic). Recognition rather than recall: after an undo, the halo and the row overlay (D9-09) answer "which
  one returned" without the user recalling what they deleted; the "restored" tag keeps the answer for 10 s.
- H-3 (heuristic). Error prevention: no geometry eases (DNA-1, DNA-7), so no frame shows a level at a price it does
  not have.
- H-4 (heuristic). Aesthetic and minimal design: ten of thirteen moments are cuts, and the three moving rows each
  animate one property, once.

**Session protocol (3 participants; for the owner to run, not run here).** Setup: the PR 2 prototype at 200
drawings, normal motion, then `?motion=reduce`. Task 1: "select the drawing under the pointer where three overlap;
say which one you picked." Task 2: the facilitator deletes two drawings and presses `Ctrl+Z`; "after an undo, name
which object returned." Task 3: "drag an anchor until it snaps to a High; say the value." Record per participant:
the answer, whether it was right, and the mode. Pass: each participant names the restored object in both modes.

**Owner walkthrough checklist (≤ 10 items; posted on #353 with PR 2).** W1 `?play=snap`: the ring settles once per
new value; W2 the value text appears with no motion; W3 `?play=select`: one halo fade on the picked object; W4 a
drag that starts mid-halo cuts it; W5 `?play=undo`: the halo and the row overlay start together; W6 a bulk undo
emphasises at most 20; W7 every entry again with `?motion=reduce`, the carrier present; W8 no drawing fades in or out
on create or delete.
