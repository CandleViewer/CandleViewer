## 1. Purpose, scope, method, locked inputs, constants

### 1.1 What this spec fixes

The long/short position tool is the one drawing that produces numbers a user acts on with money (ticket Context). This spec fixes its hi-fi anatomy (§2), its read-out and every source of truth behind a number (§2.2), the drag order and the intermediate state (§4), the state matrix with the four acceptance states (§5), the send-to-ticket affordance, its gates and the client-only hand-off payload with the one pre-filled SCR-060 frame (§6), the numbers from one constants block (§7), the keyboard model (§9), the copy deck under the advice boundary (§10), the drawn threat table (§11), the layer and event cards (§12) and the measured contrast and CVD (§13). **The tool plans; the ticket sends.** "Send to ticket" pre-fills SCR-060 and nothing else: no request leaves the client on that press, no arm state changes (§6.4 carries the normative no-order sentence, stated once there and cited from here, §11 and §23; ticket AC 5; memo :28; D02 §13.1 :532; `13` §6 :189) — the only send path is the ticket's own confirm (SCR-076, E30-D03 D3; `14` :1655), after the ticket's validation, confirmation and arming have run. Every plan the tool can hand over carries a native exchange stop (C-2.6; C-4.14): a plan without a protective stop never reaches Send (§6.1, rider (i)).

### 2.3 The DOM / canvas split (ticket Technical notes)

The geometry — lines, zones, handles, the selected outline, the chip and the zone labels' glyphs — is canvas, on `26` §3.1's `drawings` layer (§12). The read-out is **DOM**: selectable, copyable, screen-reader readable and precisely typeset (`type.num.*` tabular, the minus U+2212, thousands separators) — a `role="region"` named "Position plan, long, BTCUSDT" holding a `<dl>` of CMP-036 rows (`dt` / `dd`), a status line with one `role="alert"` node (in the DOM at mount, empty; filled once when the exceeds-cap state is entered — never a role on a `dd`, §9) and the Send to ticket button last, positioned by the overlay layer at most once per frame (CMP-197's data contract :2353). The zone labels' text is also drawn on the canvas for legibility at a glance and mirrored in the `<dl>`, so no number exists only as pixels. Engineering shape: the drawing publishes a plain plan object (prices, side, extent) on every geometry change; the read-out subscribes, computes `(provisional)` numbers and asks the preview at the drag-end cadence (§12) — never per pointer move.

## 7. Numbers (D10, D14; the formulas are the server's — `24` §9.3 quoted, reproduced by the tool, never a third rounding)

**Formulas (the server's, `24` §9.3 :2383–:2438).** stop distance = |entry − stop|; `invalid_stop_distance` when it is 0 (:2402). Risk-based size: `risk_amt = equity × risk_pct_equity`; **fee-aware** `fee_per_unit = ref × (fee.taker × 2)`; `qty = risk_amt / (stop_dist + fee_per_unit)` (:2418–:2419); then the recorded clamps in the fixed order `max_leverage_cap → max_position_pct_equity → max_position_notional → remaining headroom under max_daily_loss → max_order_qty / max_mkt_order_qty → available margin × 0.98` (§9.3.2 :2438), then **"Exchange rounding — ALWAYS floor"** to `qty_step` (:2424), then the viability gates `below_min_notional` (:2429) and `insufficient_margin`. Stops resolve "rounded conservatively (further from entry, never closer)" (§9.3.1 :2436). R is defined on the gross stop distance (E32-D01 R4): R:R = target distance ÷ stop distance. The shared implementation (US-DRAW-007 NFR :1297 "identical sizing maths as US-PROF-002"; US-PROF-002 NFR :559 "server-verified on submit"; US-ORD-004 NFR :2979 "mismatch beyond one lot rejects the order") is E30-T01's `packages/order-ticket-core` (not shipped); the UI never recomputes with a third rounding — the protocol's `divideRoundHalfEven` (`packages/protocol/src/rules/policy.ts` :97–:101, mirroring `exchange/policy.py`) is the one TS / Python pair that already agrees to the tick.
