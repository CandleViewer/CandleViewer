## 1. Purpose and scope

Decisions for the four E39 surfaces so that E39-D02 (#878, SCR-071 + SCR-073 hi-fi) and E39-D03 (#879, SCR-072 +
SCR-134 hi-fi) can start on settled interaction rules:

- **SCR-071 Risk dashboard** — the supervision surface (owner) and the "what are my limits" surface (manager).
- **SCR-072 Kill-switch / freeze confirmation** — the only place where a human engages the kill switch (B18).
- **SCR-073 Lockout notice** — the interruption a manager sees when the server locks their account (B20), and the
  owner's override path.
- **SCR-134 Risk policy (global)** — the admin page whose values become the server's caps.

In scope: the state inventory for all four, the kill-switch flow (disarmed → arm → confirm → engaging → engaged →
release), the lockout flow (breach → locked → override / expiry), the copy deck for the danger wording, keyboard and
live-region rules, degraded / disconnected / demo-vs-live variants, the catalogue and flow amendments the architect
ruling assigned to this ticket, and the acceptance criteria E39-D03 inherits.

Out of scope (unchanged from #829): hi-fi visual design, tokens and motion (E39-D02/D03); the order ticket's inline
cap-headroom chip CMP-232 (E30); the fan-out preview (E34).

Hard constraints the design never relaxes: the UI renders server truth only (C-2.12, C-12.4, C-12.5); the block is a
synchronous server flag, the statecharts record (C-2.21, INV-B18-a, INV-B20-a); every position-opening order carries a
native stop (C-2.6) — so "open positions are NOT closed" is also "open positions stay protected by their exchange-side
stops"; every freeze, release, lockout and override is audited (C-2.9); no client-supplied `until` (#829 Do NOT).

## 2. Method (agent-delivery adaptation; nothing invented)

**What was done.**

1. A **heuristic evaluation** of the four screens as specified in `14-screens-catalogue.md` (SCR-071/072/073/134,
   SCR-010 chrome states, SCR-150..159 global states), against Nielsen's ten heuristics and the trading-specific
   rules in `05-accessibility-standard.md` (§3.1.4 destructive actions, §3.4.3 focus never stolen, §4
   colour-independence, §6.2 live-region politeness, §7 reduced motion).
2. A **contract walk**: `22-api-openapi.yaml` (`RiskSummary`, `RiskCaps`, `KillSwitch`, `SetKillSwitchRequest`,
   `KillSwitchResult`, `getRiskSummary`, `overrideRiskLockout`, `setKillSwitch`), `23-ws-protocol.md` §15.9
   (`SystemUpdate` `kill_switch` frame and its role filtering), `28-statechart-catalogue.md` B17/B18/B20 and the
   E39-T02 (#882) schema text (`risk_lockouts`, `risk_policy`, `kill_switch_state`, their `CHECK` bounds). Every UI
   state below maps to a machine state or to a server-reported condition; none is client-invented.
3. A **public-source review** of how incumbent terminals, exchanges and prop-firm dashboards present cancel-all /
   close-all, risk limits and lockouts (§6). Only pages that were actually fetched on 2026-10-20 are cited; where a
   claim could not be verified it says so.
4. The **architect ruling** on #249 (comment 6163908535, 2026-10-14) is applied in full: R3 (one blast-radius
   confirm, no typed word, no hold, no step-up for engage; step-up + typed reason for release and override; checkbox
   defaults mirror the API), R4 (override reason floor 10, enforced by the server) and the R1 action-class table for
   degraded and disconnected states.

**What was not done, and is not claimed.** No owner or manager session was run; there are no participants, timings,
hit rates or quotes. The ticket's "two scripted sessions" are replaced by the heuristic evaluation plus a session
protocol and owner walkthrough checklist that the owner can run later (§13). Every finding carries its basis:
`(heuristic)`, `(contract)` — stated in an API/WS/statechart/schema document, `(catalogue)` — stated in a plan
document, `(public source)` — fetched vendor page, or `(ruling)`.

**Research questions** (from #829 Scope), answered heuristically in §3.5: RQ1 what the owner expects FREEZE to do;
RQ2 what a manager needs to know the moment a lockout hits; RQ3 which figure each role looks at first on the risk
dashboard.

### 3.4 What the UI may and may not infer (contract)

- A Manager's `kill_switch` frame carries only `engaged`, `scope`, `engaged_at_ms` and the covered account ids
  (`23-ws-protocol.md` §15.9). It never carries `engaged_by`, `reason` or the action counts. So the manager banner
  says _"frozen at 14:02 UTC — only the owner can release it"_; it says _"by the owner"_ only for `scope: global`,
  which only the owner can engage (`04` §7.2 rows 31–32). The action counts the manager sees are their own
  orders/positions from their own private topics, not the kill-switch result. (OD-2 asks whether the covered
  manager should also receive the engaging username.)
- `until` is server-computed and nullable (`RiskSummary.accounts[].lockout.until`); the UI renders it and a relative
  countdown, never computes or submits it (#829 Do NOT).
- The warning band is a server state (B20 `warning`), not a client threshold; the 80 % tick on every meter is a
  reading aid, the escalation comes from the server.

### 3.5 The three research questions — recorded answers (heuristic)

**RQ1 — What does the owner expect FREEZE to do?** `(heuristic)` The plan documents themselves disagree
(F2): the roadmap and the personas say "stop new risk, do not force-close"; flow §20 said "cancel all… flatten ALL";
SCR-010 calls the global control FREEZE while SR-081 calls activation "cancel-all… optionally flatten". A reader who
has met any one of these documents can legitimately expect either outcome — which is exactly the misreading #829
names as the most dangerous. The design therefore stops relying on the word: the Confirm button and the first
sentence of every frozen state say what will happen to working orders _and_ to open positions, every time (D1, D2).
The owner walkthrough (§13) tests whether the expectation matches the label without the facilitator's help.

**RQ2 — What does a manager need the moment a lockout hits?** `(heuristic, personas P2 G3 and pains)` In this
order: (1) that it is a lockout and not a bug — a named reason with threshold vs actual; (2) whether positions were
touched — "1 position was flattened" or "nothing was closed for you"; (3) what still works — close and reduce;
(4) until when — absolute UTC time plus relative; (5) who can lift it and how to ask. The banner anatomy in D5 is
that list in that order; the same five facts appear in the ticket's disabled-with-reason tooltip and the blotter
chip so the answer is the same wherever the manager looks (SCR-073 checklist "consistently").

**RQ3 — Which figure does each role look at first?** `(heuristic)` For the owner in supervision mode the
first question is "is anything about to trip?" — so the per-account **cap-used meter with its %** leads the row,
and the header KPI "positions without native stop" (must be 0) is placed as the last, loudest tile. For the
manager the first question is "how much room do I have?" — the manager variant leads with **their daily-loss
headroom** and repeats the owner-set limits in one line. Public dashboards agree with this ordering: Topstep
replaces the header gauge with the personal daily-loss gauge and ATAS puts a "Reset In" column next to the status
(§6). This is a prediction to verify in the walkthrough, not a measurement.

### 9.4 High contrast and colour independence (05 §4, §5.6)

≥ 4.5:1. `color.text.disabled` is 2.6–3.5:1 and is therefore only ever used with a stated reason beside it, never as
the sole carrier. Non-text borders (`color.border.default` 1.6:1, `strong` 2.0:1) are decorative in these boards; the
state-carrying strokes use `color.text.primary`/`secondary` (≥ 9.9:1). E39-D02 re-runs the matrix
(`docs/design/_tools/contrast_check.py`) when the status colours are added.
