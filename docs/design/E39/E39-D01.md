## 3. Findings (each cited)
- F1 (heuristic): The most dangerous misreading is "FREEZE closed my positions". Release roadmap §7.2 E39: "stops new risk, does not force-close"; B18 has a separate `flattening` step. Source: `30-release-roadmap.md` §7.2, `28-statechart-catalogue.md` B18.2.
- F2: The catalogue and the personas doc contradict each other on confirmation. SCR-072 requires typing `FREEZE` plus hold-to-confirm; `10-personas.md` P4-E says "no typed confirmation… a 15-second typing ritual during a runaway is itself the hazard", with step-up only to undo. `13-user-flows.md` §20 says single click. Sources: `14-screens-catalogue.md` SCR-071/072, `10-personas.md` P4-E table, `13-user-flows.md` §20.
- F3: Step-up (password + TOTP, 5 min) is required to change risk caps and to disable the kill switch, never to engage it. Source: `04-security-program.md` SR-025.
- F4: A lockout only blocks new risk. US-ADMIN-003 "Tighten during an open position": no forced liquidation, entries blocked, reduce-only allowed. Source: `11-user-stories.md` US-ADMIN-003.
- F5: Only the owner with elevation may clear a lockout or release the switch; a denied attempt is audited and never faults the machine. Sources: B20.6 INV-B20-f, B18.7 INV-B18-d/f, `22-api-openapi.yaml` `overrideRiskLockout`.
- F6: Blocking is a synchronous flag consulted by the Validator before any statechart event; the machines record. Sources: CONSTITUTION C-2.21, B18.7 INV-B18-a/b, B20.6 INV-B20-a.
- F7: Revoking an API key does not cancel resting orders, so the kill switch must cancel with the key still valid. Source: `research/12-scope-and-users.md` l.39-40.
- F8: Incumbent pattern: Freqtrade protections (max drawdown, stoploss guard, cooldown) halt new orders; Sierra Chart / Jigsaw expose one-click flatten and cancel-all. Both are separate controls. Source: `research/09-execution-risk-tools.md` l.37-38. No further incumbent claims are made.
- F9: Lockout reasons are the enum `daily_loss | consecutive_losses | max_positions | manual`; `until` is server-computed and nullable. Source: `22-api-openapi.yaml` `RiskSummary.accounts[].lockout`.
- F10: Position size beyond a cap is rejected, not silently clamped. Source: CONSTITUTION C-12.5.

## 4. Decisions
D1 (F1, F4). Every surface that shows a frozen or locked state says in one sentence what was done and what was NOT done. FREEZE never offers flatten by default; flatten is a second, separate action.
D2 (F2, F3). Resolve F2 as: **engage = one deliberate confirm naming the blast radius, no step-up. Typed `FREEZE` is dropped for engage** (needs a catalogue PR, §8 item 1; owner decision). Hold-to-confirm 1 s is retained as a keyboard-operable alternative (Enter on a focused Confirm). **Release and lockout override require step-up.** Rationale: stopping harm must never wait on typing or TOTP.
D3 (F6, F10). UI is a renderer. Cap editor save returns the server-acknowledged value; any rejected order shows the server reason. No client-side enforcement and no client-supplied `until`.
D4 (F5, F3). Owner override: dialog restates the lockout (account, reason, breached cap vs actual), requires a reason of at least 10 chars (catalogue; schema allows 3, so the 10-char rule is a UI floor, flagged in §8), then step-up, then success shows the audit id. A denied attempt shows the server reason. Manager sees "Request override" only.
D5 (F9). Copy deck, lockout reasons:
- `daily_loss`: "Trading locked: daily loss limit reached at {time} UTC. {n} position(s) flattened. Locked until {until} UTC. You can still reduce or close positions. Contact the owner for an override."
- `consecutive_losses`: "Trading locked: {n} losing trades in a row. Locked until {until} UTC. New orders are blocked; closing and reducing still work."
- `max_positions`: "New orders blocked: {n} of {max} positions open. Close a position to trade again. Nothing was closed for you."
- `manual`: "Trading locked by the owner at {time} UTC. It stays locked until the owner releases it; no clock will clear it."
Freeze restatement: "This cancels {n} working orders and blocks new orders on {m} accounts. Open positions are NOT closed." Override helper: "Explain why you're overriding this lockout. It is recorded in the audit log."
D6 (F4). Caps editor (SCR-134 and per-account profile): each limit is a fieldset with unit, current measured value beside it, breach behaviour (warn / block new orders / flatten) and "what happens when breached" text. A cap cannot be disabled entirely. Warning when portfolio cap < sum of the smallest per-account caps. Change summary (old → new) before save, step-up gate on save (SR-025), conflict state shows the other editor's value.
D7 (F1). Kill switch flow: **arm** (Safety control in rail footer + hotkey, reachable from every screen) → **confirm** (SCR-072, alertdialog, focus on Cancel, scope selector, "also cancel working orders", "also flatten positions", both default per `SetKillSwitchRequest`: cancel on, flatten off) → **engaged** (per-account progress; `engaged_incomplete` pages owner and is shown as incomplete, never rounded up) → **release** (step-up, residual acknowledgement for incomplete).
D8 (F6). State encoding: ok = circle, WARN = diamond, LOCK = filled square, FROZEN = two bars, STALE = dashed circle, RECONCILING = ring, each with a text label and a numeric used % beside every meter (greyscale baseline).
D9. Stale/reconciling: FREEZE stays enabled, Override disabled while reconciling.
