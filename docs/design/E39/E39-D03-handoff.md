## B. Accessibility acceptance criteria (`05` §10) — CMP-211, SCR-072, SCR-134

```gherkin
Feature: E39-D03 kill-switch modal, panic cluster and risk policy — accessibility acceptance criteria

  Scenario: Keyboard-only operation
    Given the user has not used a pointing device
    When the user opens the freeze confirmation from the cluster or with Ctrl+Shift+K, changes the scope
      and the options, confirms with Tab then Enter, flattens with the discrete two-press fallback,
      and edits and saves the risk policy using only the keyboard
    Then every control involved is reachable via Tab or arrow-key navigation (Table 2)
    And every action has a documented non-drag keyboard equivalent (the hold has its two-press fallback)
    And focus is never silently moved by a background data update (a kill_switch frame, a measured value)
    And a visible focus indicator meeting >=3:1 contrast is present at every step
      (7.45 / 6.75 / 19.35 on the app chrome; 6.15 / 5.39 / 15.99 on the dialog; 2 px offset on the danger button)

  Scenario: Screen-reader operation
    Given the user is using NVDA with the keyboard
    When the user performs the same tasks
    Then all labels, roles and current values are announced correctly (Table 3): the alertdialog's title and
      consequence, the Confirm label as the last thing read before Enter, the armed name "Press again to ..."
    And live data is announced per 05 §6.2: progress polite and coalesced to 1 per second, the engaged,
      incomplete, not-durable, automatic and released facts assertive once, the hold progress never per tick
    And no canvas-rendered data is involved

  Scenario: Colour-independence
    Given the surfaces display the FROZEN / LOCK / WARN states, DEMO vs LIVE and the danger action
    When the state is rendered
    Then the state is also conveyed via glyph and text, not colour alone (two bars + FROZEN, the badge text,
      the Confirm label naming the effect, the lock glyph + reason sentence on disabled controls)
    And the surfaces pass deuteranopia / protanopia / tritanopia simulation review (planned on the exports)

  Scenario: Contrast
    Given the surfaces are rendered in the dark theme and the high-contrast theme
    Then all text meets >=4.5:1 and all meaningful non-text elements meet >=3:1 per the token contrast
      matrix (E39-D03 §12: 44 rows, 31 gated, 0 FAIL; the on-action label on the danger button 5.05 dark / 4.54 hc)

  Scenario: Reduced motion
    Given the user has prefers-reduced-motion enabled
    When the dialog opens, the hold ring fills or a freeze progresses
    Then the dialog is a cut, the ring is replaced by its percentage text at most twice a second and the
      progress rows step discretely; nothing flashes more than 3 times per second and nothing moves for
      more than 5 s without a pause control

  Scenario: Automated gates
    Given the implementation PR (E39-S05) is opened
    Then axe-core reports zero new serious or critical violations
    And the affected screens' Lighthouse Accessibility score remains >= 95 (SCR-010 with the cluster; SCR-134)
    And the keyboard-only E2E smoke test covering FREEZE... -> SCR-072 -> Tab, Enter passes
    And the hotkey test asserts that Ctrl+Shift+K opens the dialog and sends nothing
    And the test asserts that the request never carries flatten_positions true with cancel_open_orders false
    And the test asserts that a held Enter (key auto-repeat) never confirms a hold button
```
