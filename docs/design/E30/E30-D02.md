## 1. Purpose, scope and method

### 1.1 What this spec fixes

SCR-060, the single-account execution surface: its anatomy and redlines at two densities and three themes; every state the catalogue names plus the ones E30-D01 added (awaiting exchange confirmation, protective stop pending, stale inputs, locked / armed / unknown, the return from a disconnect); every order type and flag; the four sizing modes with the computed result always visible, the preset ladder and the clamp message; the bracket with the non-emptiable native stop; the limits chip; the error-summary pattern and the full-intent submit label; the keyboard path; the copy deck; the measured contrast and CVD evidence. Out of scope, per #850: SCR-076 / 077 / 114 / 158 and the account / trade-group selector (E30-D03), the design-system component specs and the motion spec (E30-D04), chart / DOM trading (E31), the group ticket's layout beyond the selector affordance (E30-D03). The confirmation dialog is drawn only where it is this ticket's own (the LIVE arm step, D15); the order confirmation itself is SCR-076.

### 1.2 Method (honest)

Desk design and heuristic evaluation under the agent-delivery adaptation (owner decision 2026-09-25): no participants, no sessions, no prototype, no critique session — the ticket's "design critique with the E30 engineering lead" becomes the owner walkthrough of §18 and the feasibility notes of §16, recorded as such, not as held. Contrast and CVD are computed programmatically (§15), never eyeballed. Frame: Nielsen's ten heuristics plus the trading heuristics of `05` (keyboard-first §3.1 and §3.3; no hover-only or drag-only interaction §3.1 item 6; colour never alone §4; the contrast bars of §5; live regions §6.2; reduced motion §7). Reference products are cited only where E30-D01 §6 verified them on public pages; nothing new was read from the web for this spec. The bar the ticket sets — Sierra Chart, ATAS, Bookmap, Quantower, TradingView, Jigsaw, Exocharts — is applied as a design standard (density, one glance, keyboard speed, no ornament), not as a claim about any of them beyond E30-D01's cited pages.

### 1.3 Locked inputs (built on, not re-decided)

- **C-2.6 and C-4.14:** every position-opening order carries a native exchange-side stop; no flag, environment or role disables it; `POST /orders` enforces it (`22` placeOrder: `validation_failed` / `native_stop_required`) and `require_native_stop` is `const: true`. This spec draws **no opt-out and no opted-out banner** (E30-D01 §1a SC-4, OQ-4 default).
- **E30-D01 §1a defaults, applied as written:** SC-1 keys (`Ctrl+Shift+T` arm, `B`/`S` set side, presets `1..4` ticket-focused, `Ctrl+Enter` submit, `Esc` clear, `Alt+B`/`Alt+A`/`Alt+M` snap, `R` reduce-only; buy/sell market and cycle-sizing-mode unbound) · SC-2 arm model (server `arm_token`, TTL 300 s default, memory only, six auto-disarm triggers each with its reason, `mm:ss` at ≤1 Hz, `0:05` then the state) · SC-3 (LIVE never skips SCR-076; the LIVE second action is a CMP-044 dialog with SCR-076's gates; `reverse` through SCR-114's `dialog` policy; double-press only for flatten and cancel-all) · SC-5 (the code from `TradeGroup.legs[].error` / WS `trade_groups`; the verbatim `retMsg` inline; `native_stop_required` is 400) · SC-6 (explicit replay, nothing automatic) · SC-8 (stop in `ticks / % / price`; R is a read-out, `24` §9.3.1) · SC-9 (CMP-158, CMP-229 and CMP-139 on the ticket; a positions source on SCR-060's Data line, §21 A-1) · SC-10 (no correction offer for margin or risk-cap rejections).
- **E30-D01 F18–F21:** staleness (one treatment for helpers, wallet-fed fields, preview and the client quantity; the server's `size_leg` is the only authority — the client number's chip word is `(provisional)`, a recorded departure from E30-D01 F18's `(estimated)`, because `14` §0.5 item 2 reserves that word for heuristic proxies; A-20), hotkey safety (the suppression line **inside** the arm indicator; hold-to-confirm with the discrete second press for flatten and cancel-all — not on this screen; digit shadowing: presets act only while the ticket region has focus), re-arm after reconnect (the ticket returns **locked** with the reason; the divergence line stays above the submit control). The reduce-only bracket state and the opens-vs-reduces read-out (F13).
- **E17-D01 §6, D12, D13:** the Read-only overlay is a permission layer, not a feed chip; a keystroke in a blocked state gets inline text at the point of action plus one polite announcement; a gated action is one CMP-044 `standard` confirm; cancel, close and the kill switch are never hidden or blocked by feed state alone; one-click disarms on Disconnected, Read-only or Stale ≥ T1 and is never auto-re-armed. ## 5. Sizing: the hybrid control, presets, clamps, fixture numbers (D7–D9, D21)

### 5.1 The control

One input (CMP-101 on CMP-008) and a unit switch (CMP-003 radiogroup, `aria-describedby` = the active formula, CMP-101 A11y) with four units mapping to `24` §9.2 `sizing_mode` and `22` `Sizing.mode`:

| ------------------ | ----------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `BTC` (base coin)  | `fixed_qty` / `qty`                 | quantity in base units, floored to `qty_step`       | "Quantity as entered, rounded down to the lot step"                                                                          | notional USDT · % of equity · risk USDT (%) · 1 R                    |
| `USDT`             | `fixed_notional` / `notional_usd`   | notional in quote; qty = notional ÷ reference price | "Notional ÷ reference price (limit price, else mid, else last), rounded down to the lot step"                                | qty · % of equity · risk USDT (%) · 1 R                              |

The profile's default unit preselects the switch (`24` §9.2); `% eq` and `risk %` are disabled with the reason "Equity not available — wallet data is 14 s old" while the wallet is stale (US-ORD-014 scenario 3; D21).

Authority (C-2.12): every number on the line is the server's once `/trade-groups/preview` has answered for the current draft (debounced 80 ms, E30-S06); until then the client's own number is drawn under the `(provisional)` hatch and chip — not `(estimated)`, which `14` §0.5 item 2 reserves for heuristic proxies and CMP-130 for slippage (A-20 adds the word to the chip vocabulary); when the server's quantity differs it replaces the client's with the cyan value-change highlight (`color.status.info.subtle` behind the number for `motion.duration.normal`, instant under reduced motion) and a polite announcement "Size set by server: 0.346 BTC". ```text

- **No toggle.** The row is titled "Stop-loss (required)"; there is nothing to untick (the catalogue mock's `[x] Attach SL` is amended, §21 A-4). The field is CMP-100 for `price`, CMP-008 for `ticks` and `%`; the unit switch is the CMP-003 radiogroup `ticks / % / price` (SC-8; `22` `OffsetUnit` has `price`; `r_multiple` is invalid for the stop, `24` §9.3.1), `trigger_by` a CMP-009 select (`MarkPrice` default per the profile; `LastPrice`, `IndexPrice`). A typed stop or take-profit **price** that is not a tick multiple rounds **away from the entry** — a long's stop down and its take-profit up, a short's the reverse — each under its own rule: the stop per `24` §9.3.1 ("rounded conservatively (further from entry, never closer) so the actual risk never exceeds the budget"), which governs the stop only; the take-profit per `24` §1.3 precision rule 1, `round_price(px, side, mode)` with `mode="conservative"`, which rounds a sell limit up and a buy limit down — a long's take-profit is a sell, a short's a buy, so the same direction from its own source — both with the caption "(rounded away from entry to the 0.1 tick)"; a typed 63,899.96 on a long becomes 63,899.9, never the nearer 63,900.0. Only the entry price rounds to the nearest tick (§4; A-5 records both rules for CMP-100); the server's resolved `stop_loss_price` is the authority and a difference is highlighted in the Preview block (§5.5).
- **Source and holder line** (`type.ui.caption`): the distance in ticks and the implied `1 R` in USDT (the R read-out, US-ORD-004), then the source — typed: nothing extra; profile: "from your profile: 200 ticks" with the field pre-filled and editable; fallback: "fallback 2 % — ATR warming up" (`24` §9.3.1 `stop_fallback`, drawn with the attention glyph); then "held by Bybit (exchange)". The holder is stated on every frame because nothing in the mock said it (E30-D01 F13). The line exists only while the field holds a valid stop: an empty or wrong-side field shows the catalogue copy in its place (the blocked-empty state below), and the read-out, the Preview's risk row and the take-profit's R read "—" until a stop exists; a reduce-only draft has no line (D11).
- **Blocked-empty state (drawn, board 10):** an empty stop, or a stop on the wrong side, outlines the field with the 2 px `color.status.danger.default` boundary (3.63 / 3.22 / 3.63:1 — an amber in the light theme until CR-3 gives it `palette.light.red.350`), shows the catalogue copy under it — "This account requires a stop-loss on every order." for empty, "Stop-loss must be below entry for a long." / "Stop-loss must be above entry for a short." for the side — adds the row to the error summary, and the submit is `aria-disabled` with the same reason — still pressable, a press shows the summary (D16); CMP-119's `nativeSlConfirmed` is the gate. The copy says "this account" because the catalogue does; §21 A-5 proposes "Every order requires a stop-loss." since no account can be without it (C-2.6).
- **Reduce-only (D11):** the stop row collapses to a single caption line — "Reduce-only: cannot open a position — no new stop; the position's stop stays" — the note stays; the TP row collapses with it — Bybit's create-order page (read 2026-10-20): "When reduceOnly is true, take profit/stop loss cannot be set" — so the exit carries no bracket and the position's own TP/SL stay (E17-D01 §6's "TP edit on a reduce-only exit" is an amend of an existing exit order, not a new bracket); the line is `color.text.secondary` with no danger styling, so "not applicable" never resembles "missing" or an opt-out.

(mirror of the catalogue's SL copy, proposal §21 A-5).
- **CMP-158 (D12):** `role="note"`, `color.text.primary` on `color.status.info.subtle` with a `status.info.strong` glyph (10.74 / 15.44 / 12.16:1; glyph 7.30 / 4.34 / 7.30), inside the bracket section between the stop and the TP rows, non-dismissible; it widens the catalogue's "inside both rule editors" purpose (SC-9; §21 A-9).

## 11. Limits chip, error summary, full-intent label (D14, D16)

**CMP-232.** One row under the flags: `Limits ⚠ binding: max position 15,000 USDT (profile)` as the attention pill, then `· daily −2 % (480 of 500 USDT used) · lev ≤ 10x · min 0.001 BTC (exchange)` as neutral text with the authority in brackets; a disclosure (`Enter` / click) opens the full list (CMP-036 rows) in a popover. Data: the account profile, `/risk/summary` and `/instruments/{symbol}`; a stale wallet marks the budget rows with their age (D21). A non-binding ticket shows `Limits: none binding` with the same disclosure — the chip never disappears, so its absence can never be read as "no limits".

**Error summary (D16).** Pattern (`05` §10 "Screen-reader operation"; SCR-060 A11y "errors summarised at the top with links to fields"): a CMP-027 box, `role="alert"`, heading `type.ui.heading-sm` "Can't submit — 2 problems", a list of links in document order ("Stop-loss: This account requires a stop-loss on every order." · "Size: Minimum 0.001, step 0.001."); on insertion focus moves to the heading; activating a link moves focus to the field and the field's own message is read via `aria-describedby`; the box is removed when the last error clears and focus is not moved then; no error is shown for a field the user has not yet touched except on a submit attempt. The submit is never natively disabled: while errors stand it is `aria-disabled` with its reason (CMP-001), focusable and pressable, and a press or `Ctrl+Enter` inserts the summary (or re-focuses it if present) — validate on submit, never a dead submit (the GOV.UK error-summary pattern; E17-D01 D13: silence is never the answer).

**Full-intent submit label (D3).** Built from the server's numbers (D21) in one sentence, words then numbers in mono: **BUY 0.250 BTCUSDT limit 64,010.0 · stop 63,900.0** (market: "BUY 0.250 BTCUSDT at market · stop 63,900.0"; conditional: "BUY 0.250 BTCUSDT when Mark rises to 64,100.0 · stop 64,000.0"; reduce-only: "SELL 0.250 BTCUSDT limit 64,300.0 · reduce-only"). ## 15. Themes and densities: measured contrast, CVD and the design-system change requests (D24)

Three themes (dark, light, high-contrast — `themes.json`) × two densities (D2), all on the real tokens at `b936bbaa3ff603c15baee4e3553679afc906c6f5`. Every pair below is produced by `docs/design/_tools/e30_d02_ticket_audit.py` (`python3 -I`, exit 1 on a gated FAIL; it exits 0 at this head): the ratio is `contrast_check.contrast_ratio()`; themes resolve through `verify_tokens.py`'s loader, so `light` and `high-contrast` compose over `semantic-dark` exactly as the build does; `CR:` rows measure a change request on the token or primitive it would alias. Bars: text 4.5:1, non-text 3:1, `hc-text` 7:1 gated in high-contrast and reported elsewhere as the `05` §5 item 3 AAA stretch. Rows marked decorative carry no meaning (`16` §6 rule 7); `exempt` rows are inactive controls (WCAG 1.4.3) whose reason text is gated as text; `rejected-*` rows are pairs the obvious design would have used, kept beside the adopted pair.

## 16. Performance and feasibility notes (D25; the critique the ticket asks for, recorded as desk notes)

- **No full-panel re-render per tick** (ticket Performance notes): the helper region (`ticker`, D6), the wallet-fed read-outs (`wallet`), the preview rows (`/trade-groups/preview`) and the arm pill (`mm:ss`) are four independent subscriptions and four DOM subtrees; the committed fields, the side, the tabs and the submit label re-render only on user input or on a preview answer. Jotai atoms per region with rAF coalescing (`30-frontend-react`); nothing on the ticket subscribes to the whole `ticker` frame.
- **≤8 ms per input** (SCR-060 Performance): the read-out recompute is pure arithmetic over `tick_size`, `qty_step`, equity, leverage and the stop distance; the server's number replaces it asynchronously (≤100 ms preview budget, US-ORD-014 NFR); the full-intent label changes at most once per preview answer.
- **Click → ack ≤500 ms p95** (SCR-060; 14 §0.5 item 7; 06 §5.2 budget #4 <300 ms demo / <500 ms live with ≤50 ms backend-added, each cited to its home per SC-7, E30-K01 measures): the submitting state starts on the press, the 2 s "awaiting" fallback is a timer, not a poll.
- **Feasibility flags for the E30 engineering lead (owner walkthrough item 14):** (a) the `(provisional)` hatch on the greyed preview is a CSS background, not a canvas; (b) the double focus ring is `outline` + `box-shadow`, no extra element; (c) the submit progress bar is the button's own `::before` fill — the width is locked so the label never reflows (CMP-001 `loading`); (d) the error summary's focus move is the only programmatic focus on the panel; (e) the arm pill's second line changes the element's text, never its height in compact (the pill grows to two lines only in comfortable) — in compact the paused line replaces the account · size segment while focus is in a field, so the footer never reflows (normative in D15); (f) nothing here queries a statechart (C-2.20) — the arm state is the plain enum E30-S04 publishes; (g) the footer is `position: sticky; bottom: 0` inside the panel's own scroll container (D2), no portal; (h) the Preview block re-renders only on a preview answer, never on a tick.
