## 3. Why one vocabulary

E12, E13, E14, E18, E19 and E21 all draw inside these nine primitives. The chain that prevents it is already written: `02` §3.1 makes a design-system entry a gate ("any new component has a design-system entry, not an ad hoc one-off"); `16` §1 principle 7 says the chart engine's visual language **is** the design system's visual language; `26` §5 rule 1 says colour comes from tokens in `packages/ui` and the engine holds no hard-coded colours; E11-T04 ingests exactly that token JSON into a frozen `EngineTheme`. This spec is the hinge between the last two: it names the slots the engine will read (§4), the stops it will interpolate (§5), the record it will switch (§6) and the patterns it will register (§7), so that an E18 footprint or an E21 heatmap binds a name that exists rather than a hex that looks right.

The registry is the same chain for honesty. `20` P10 says estimated is labelled; `26` §5 rule 4 renders estimated data with a distinct hatch and the "(estimated)" label; `14` §0.5 item 2 puts the chip on every heuristic-derived value; CMP-227's catalogue-level test asserts every `14` §12.3 screen renders it. A later epic that encodes estimated data without a registered pattern is therefore making **a truthfulness error, not a visual one** (#310 Security note), and routing the encoding through this registry is what makes that error reviewable. The pattern-vocabulary rule itself — "hollow, dashed or hatched = estimated or absent, never a side or direction" — lives in **E25-D01 §9.5** as a PROPOSED `16` §6 rule (LANE-32 ruling, 2026-10-21): this spec registers patterns under it and cites it; it does not re-propose it. Until the owner accepts it, the same clause is binding through `16` §6 rules 1 and 5 and `26` §5 rules 3–4, which is why every registry row in §7 states what the pattern means and that it never carries a side.

The bar is a best-in-class professional terminal (Sierra Chart, ATAS, Bookmap, Quantower, Jigsaw, TradingView, Exocharts — E11-D01's teardown, through E11-D02 §1.3) inside a keyboard-first, WCAG 2.2 AA product where colour comes from tokens and never carries meaning alone (`16` §6 rules 1–3; C-2.13; C-14.1).

### 4.4 Delivery rules (how a slot reaches a pixel)

1. **Engine prefixes, the colour-only export and the shipped adapter.** `build/engine/theme-uniforms.json` carries every token under `ENGINE_CATEGORY_PREFIXES` (`color.chart.*`, `color.grid.*`, `color.axis.*`, `color.crosshair`, `color.candle.*`, `color.footprint.*`, `color.heatmap.*`, `color.buy.*`, `color.sell.*`, …) as `{ hex, rgba }`, flat and resolved, **colour only** (`16` §11.1; `tools/style-dictionary/formats/json-flat-rgba.js`). **Today's host adapter does not load that file:** `apps/web/src/features/appearance/chartColorMode.ts` resolves a six-name list, `ENGINE_TOKENS` (`color.buy.default`, `color.sell.default`, `color.candle.up` / `.down`, `color.footprint.bid` / `.ask`), from the root's CSS custom properties and hands the resulting `EngineTheme.colors` to `setTheme`; loading `theme-uniforms.json` for the active theme is `16` §11.1's contract and the job of E11-T04's `ThemeIngest.ts`. Either way it is the adapter that resolves and the engine that receives a token object — a data swap, not a CSS cascade; the engine never reads `data-theme` or any DOM / CSS state (C-2.16) — and either way a colour reaches the engine only if it is under an engine prefix (the export) or in the adapter's list (today). So every colour the engine draws is under an engine prefix — the §4.1 slots, the §4.2 series / ramp tokens and the §4.1b engine-chrome aliases — **except the ten CVD-safe heatmap stops** `color.cvd.heatmap.{bid,ask}.1..5`, which no prefix, adapter list or remap delivers today (G16 routes them); when E11-T04 lands, the adapter's list becomes the exported set, and E12-D06 §13's request to add `color.surface.canvas`, `color.border.default` and `color.axis.text` to `ENGINE_TOKENS` is met by `color.chart.pane.bg.default`, `color.chart.rule` / `.grid.major` and `color.chart.axis` (C5). `color.text.buy` / `.sell` are not engine tokens and are DOM tokens by design.
2. **What is not a colour travels as a metric.** CR-1's `opacity.grid.minor` / `opacity.grid.major` could never reach the engine through the colour export (an `opacity` token is not a hex, `TOKENS-E003`); the same holds for the density record (§6), `LOD_PROFILE_M0`, `lodBias`, `axisFontSizeClass` and the text-scale factor. They travel as **`EngineTheme.metrics` scalars** (E11-T04 — "a flat, frozen `EngineTheme` of premultiplied `Float32Array` RGBA plus scalar metrics"), set by the host adapter from the token build's TS object or the runtime store, never read from CSS by the engine. Hence the two deliveries for the high-contrast minor grid (§4.1): the opacity token as a metric, or the hc alias as a colour; both are one line in the token PR (Q2).
3. **The `.default` leaf.** `color.chart.pane.bg` is a group with two leaves (`.default`, `.focused`); the ticket's leaf-and-group spelling — E11-D02 CR-3 filed the same pair — is a naming violation `16` §11.1 names and Penpot rejects (C2).

### 5.4 Evaluation at 16 samples (the ticket's number; `data-ink-lib` `DEFAULT_STOPS`), OkLab beside the sRGB lerp

Each ramp is sampled at 16 evenly spaced positions in **OkLab** (piecewise-linear between adjacent stops in L / a / b, the contract of §5.5) and, beside it, in the **sRGB piecewise-linear lerp** `data-ink-lib.mjs` uses today. Per sample the tool prints hex, L / a / b, chroma √(a² + b²), the contrast on `color.surface.canvas`, and per ramp the adjacent-sample ΔE76 (CIE Lab, `cvd_simulate.delta_e76`), its **evenness** (min / max of the adjacent steps over the visible segments; 1.0 is perfectly even) and the adjacent-**stop** ΔE76 under protanopia, deuteranopia and tritanopia (Brettel / Vienot for protanopia and deuteranopia, Machado 2009 for tritanopia, `cvd_simulate.simulate`) against the 5.0 JND floor of `tools/contrast`. Samples with 0 < |t| < ε are the **zero band**: under §5.5's one rule the LUT interpolates them canvas → first visible stop, so they are faint tints below 3:1 that the sign / notch / text channel carries — reported, never gated (the 3:1 gate starts at the first visible stop, as `data-ink-lib`'s does); only t = 0 is the canvas. The tool also prints each half's **dynamic range** — the ΔE76 from the first visible stop to the sign endpoint and the number of 2.3-ΔE76 just-noticeable steps it spans — and the two halves' **symmetry** (min / max) against a PROPOSED ≥ 0.8 gate, which is `16` §6 rule 3's "visually comparable at equal magnitude" as a number (section D2).

### 5.5 The LUT hand-off (E11-T04 `ColorLut.ts`)

- The stops are **tokens**; the 16 samples are evaluation rows, **not** tokens; the LUT has **256 entries** per ramp and palette (`26` §3.8 "256×1 LUT texture"; #310 Performance note) and the engine computes them — a theme switch is one LUT upload (`26` §5 rule 1).
- **Interpolation space = OkLab, piecewise-linear between adjacent stops at the positions of §5.3**, clamped to sRGB after conversion.
- **The one zero-band rule** (`ColorLut.ts` needs exactly one; the tool prints it with every ramp table, section D): the LUT is **continuous through zero** — for 0 < |t| < ε each half interpolates canvas → first visible stop, so a small delta draws a faint tint below 3:1 (1.70 / 1.71:1 at |t| = 0.067 in dark, §5.4) that the sign, the ▲ / ▼ glyph, the L2 corner notch and the mirror text carry (E06-D01 §3; `16` §6 rule 3; `05` §4 item 1); **only t = 0 is the canvas** — a delta of exactly zero has no sign and draws neither ink nor glyph. No entry is clamped to the canvas and no |Δ| threshold hides a value: a −10 % cell must not look like a 0 cell (the ticket's "magnitude readable at a glance"); the 3:1 gate applies from the first visible stop, as `data-ink-lib`'s does. The rejected alternative — entries with |t| < ε are the canvas and |Δ| below 12.5 % of the normaliser renders unfilled — buys nothing the sign channel does not already give and costs the continuity rule 3 asks for.
- **What `t` is:** t is the **post-transfer normalised value** — in [−1, 1] for the delta ramp, [0, 1] for an intensity ramp. The normaliser (per cell, per column max or per visible window — `26` §3.8 "normalise by column max or global scale") and the transfer (`26` §3.8's lin / log; the Bookmap-class intensity control, user-set) run **before** the LUT lookup and are never baked into the LUT, which maps t to colour only. Who owns them is G15: E21-D0x for the heatmap (the user control's home is SCR-050 / SCR-031) and E18-D01 for the footprint delta.
- The CVD-safe palette swaps the five stop tokens (`EngineTheme.palette = "cvd-safe"`; `chart-color-modes.mjs` is the DOM twin) and the convention swap (owner decision #10, `EngineTheme.convention`) swaps the bid and ask LUTs, never their stops. **The ten `color.cvd.heatmap.*` stops have no engine route today (G16):** `color.cvd.` is not in `ENGINE_CATEGORY_PREFIXES`, `ENGINE_TOKENS` holds six directional names and `DIRECTIONAL_PAIRS` remaps buy / sell / candle / footprint only — so `ColorLut.ts` cannot build the CVD-safe delta LUT's ±ε stops or the two CVD-safe intensity LUTs until G16 lands (the `color.cvd.` prefix line); the ±1 ends `color.cvd.buy` / `.sell` arrive today through the shipped adapter's directional remap (`CVD_SOURCE` overrides the six `ENGINE_TOKENS` in CSS) and, under G16's prefix, ride in the export with the stops.
- Whether the five delta stops also become named `color.chart.ramp.delta.*` aliases for Penpot is a PROPOSED question for the token PR, not decided here (Q6).
- The stale state multiplies the LUT and the data-ink uniforms by 0.85 (E11-D02 D16; E11-D06 D13): measured 5.49 / 6.39 / 5.49 (up), 3.55 / 6.24 / 3.55 (down), 4.45 / 7.87 / 4.45 (wick), 7.14 / 5.71 / 7.14 (imbalance outline) — above 3:1 everywhere.
