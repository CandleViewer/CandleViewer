## 3. Why one vocabulary

E12, E13, E14, E18, E19 and E21 all draw inside these nine primitives. If the chart token set were invented in E11 and extended ad hoc in each of those epics, the chart would end up with six palettes (#310 Context). The chain that prevents it is already written: `02` §3.1 makes a design-system entry a gate ("any new component has a design-system entry, not an ad hoc one-off"); `16` §1 principle 7 says the chart engine's visual language **is** the design system's visual language; `26` §5 rule 1 says colour comes from tokens in `packages/ui` and the engine holds no hard-coded colours; E11-T04 ingests exactly that token JSON into a frozen `EngineTheme`. This spec is the hinge between the last two: it names the slots the engine will read (§4), the stops it will interpolate (§5), the record it will switch (§6) and the patterns it will register (§7), so that an E18 footprint or an E21 heatmap binds a name that exists rather than a hex that looks right.

The registry is the same chain for honesty. `20` P10 says estimated is labelled; `26` §5 rule 4 renders estimated data with a distinct hatch and the "(estimated)" label; `14` §0.5 item 2 puts the chip on every heuristic-derived value; CMP-227's catalogue-level test asserts every `14` §12.3 screen renders it. A later epic that encodes estimated data without a registered pattern is therefore making **a truthfulness error, not a visual one** (#310 Security note), and routing the encoding through this registry is what makes that error reviewable. The pattern-vocabulary rule itself — "hollow, dashed or hatched = estimated or absent, never a side or direction" — lives in **E25-D01 §9.5** as a PROPOSED `16` §6 rule (LANE-32 ruling, 2026-10-21): this spec registers patterns under it and cites it; it does not re-propose it. Until the owner accepts it, the same clause is binding through `16` §6 rules 1 and 5 and `26` §5 rules 3–4, which is why every registry row in §7 states what the pattern means and that it never carries a side.

The bar is a best-in-class professional terminal (Sierra Chart, ATAS, Bookmap, Quantower, Jigsaw, TradingView, Exocharts — E11-D01's teardown, through E11-D02 §1.3) inside a keyboard-first, WCAG 2.2 AA product where colour comes from tokens and never carries meaning alone (`16` §6 rules 1–3; C-2.13; C-14.1).

### 4.4 Delivery rules (how a slot reaches a pixel)

1. **Engine prefixes and the colour-only export.** `build/engine/theme-uniforms.json` carries every token under `ENGINE_CATEGORY_PREFIXES` (`color.chart.*`, `color.grid.*`, `color.axis.*`, `color.crosshair`, `color.candle.*`, `color.footprint.*`, `color.heatmap.*`, `color.buy.*`, `color.sell.*`, …) as `{ hex, rgba }`, flat and resolved, **colour only** (`16` §11.1; `tools/style-dictionary/formats/json-flat-rgba.js`). The host adapter loads the file for the active theme and calls `chart.setTheme(ThemeTokens)` (`26` §8): a data swap, not a CSS cascade; the engine never reads `data-theme` or any DOM / CSS state (C-2.16). Every slot in §4.1 and every series / ramp token in §4.2 is under an engine prefix; `color.text.buy` / `.sell` are not and are DOM tokens by design.
2. **What is not a colour travels as a metric.** CR-1's `opacity.grid.minor` / `opacity.grid.major` could never reach the engine through the colour export (an `opacity` token is not a hex, `TOKENS-E003`); the same holds for the density record (§6), `LOD_PROFILE_M0`, `lodBias`, `axisFontSizeClass` and the text-scale factor. They travel as **`EngineTheme.metrics` scalars** (E11-T04 — "a flat, frozen `EngineTheme` of premultiplied `Float32Array` RGBA plus scalar metrics"), set by the host adapter from the token build's TS object or the runtime store, never read from CSS by the engine. Hence the two deliveries for the high-contrast minor grid (§4.1): the opacity token as a metric, or the hc alias as a colour; both are one line in the token PR (Q2).
3. **The `.default` leaf.** `color.chart.pane.bg` is a group with two leaves (`.default`, `.focused`); the ticket's leaf-and-group spelling — E11-D02 CR-3 filed the same pair — is a naming violation `16` §11.1 names and Penpot rejects (C2).
4. **The high-contrast overlay.** No slot needs a `semantic-hc` line except the minor-grid "off" if the alias delivery is chosen; every other hc value arrives through the alias's own hc override (`color.text.tertiary` → `palette.neutral.800`, `color.border.default` → `palette.neutral.500`) or inherits dark (`color.crosshair`, `color.grid.line`, `color.surface.canvas`, the candle, heatmap and cvd tokens). `TOKENS-E001` theme parity is satisfied by `semantic-dark` alone (`16` §11.2 step 4).
5. **The gates' registries (the token PR's consequence, `16` §11.2 step 5).** Registered today on the canvas: `color.grid.line` (exempted), `color.crosshair`, `color.axis.text`, the candle / cvd tokens and, through the `HEATMAP_RAMP` block, every heatmap stop (§10.1 "pairs.mjs" column; `bid.1` / `ask.1` are registered and exempted at once — CR-9). The token PR adds a `pairs.mjs` row per new `color.*` name or `A11Y-C002` fails: `color.chart.axis` at `THRESHOLD.TEXT` on `color.surface.canvas` (and its 7:1 reading holds in hc without a `.hc` variant); `color.chart.crosshair` and `color.chart.replay.border` at `THRESHOLD.NON_TEXT`; **`color.chart.grid.major`, `.grid.minor`, `.watermark`, `.pane.bg.default`, `.pane.bg.focused` are decorative chrome below 3:1 by design** — `16` §11.3 says chart _ink_ gets no new exemption, and these are not ink; the PR therefore proposes five `exemptions.json` entries whose `reason` reads "decorative chrome by design, `16` §6 rule 7; E11-D05 §4" with the owner as `owner`, or a `decorative` entry class in `pairs.mjs` if devsecops prefers a typed exemption (Q4; `tools/` CODEOWNERS; the a11y reviewer confirms the class). 6. **Route and changelog.** The token PR is the first `feat(design-system)` PR of **E11-T04** per `16` §11.3 Runbook B (interface-first, `01` §10): `semantic-dark.tokens.json` gains the eight aliases (one `semantic-hc` line if Q2 chooses the alias), `tools/contrast/pairs.mjs` / `exemptions.json` / `encodings.json` their rows, `packages/ui/tokens/CHANGELOG.md` a `## [0.1.2]` heading with `### Added` — "`color.chart.axis`, `color.chart.grid.major`, `color.chart.grid.minor`, `color.chart.crosshair`, `color.chart.watermark`, `color.chart.pane.bg.default`, `color.chart.pane.bg.focused`, `color.chart.replay.border` — aliases of existing semantic tokens for the chart chassis (engineering, E11-T04; design, E11-D05 §4; E11-D02 CR-1…CR-4)" — the PR that lands it writes "(engineering, E11-T04)" or "(design, E11-D05)" as the case is; local `build:tokens`, `contrast:gate`, `verify_tokens.py` and the `packages/ui` Vitest run; the automatic `security-review` label; after merge the Penpot token sets are brought back to `main` under the next design ticket (`16` §11.3 step 4). ### 5.5 The LUT hand-off (E11-T04 `ColorLut.ts`)

- The stops are **tokens**; the 16 samples are evaluation rows, **not** tokens; the LUT has **256 entries** per ramp and palette (`26` §3.8 "256×1 LUT texture"; #310 Performance note) and the engine computes them — a theme switch is one LUT upload (`26` §5 rule 1).
- **Interpolation space = OkLab, piecewise-linear between adjacent stops at the positions of §5.3**, clamped to sRGB after conversion; the zero stop is the canvas and the half ramps meet there; a delta of exactly zero draws no ink (the sign and the ▲ / ▼ glyph carry it, E06-D01 §3).
