**The save model (BQ-3 RULED).** Save sends one `updateWorkspace` with the whole `WorkspaceInput` (the edited `name` and `is_default`, the loaded `icon_token` and `sort_order`) and `If-Match` set to the loaded token in quotes, a strong validator (`22:8612–8630`). The form is **dirty** while any value differs from the value loaded, field by field, so typing a name back to its saved spelling makes it clean again. A dirty form titles itself `Workspace settings *`, its accessible name "Workspace settings, unsaved changes" (the tab strip's form, `D02:280`), and Save is enabled; a clean form keeps Save in the validity look with "No unsaved changes." under the footer — the tab strip's words for a clean Save (`D02:280`; `ws.save.clean` `D03:611`) as a sentence with its full stop, as merged E15-D03 words its clean Revert to saved… (`D03:626`); never T2 and never a lock (D08-C19) (A1; `D09:224–230`). The autosave switch belongs to the form: Save writes the device's choice after the server's `200`, or at once when it is the only change (then nothing is sent), so a Save applies all of its changes or none.

- **Saving:** Save `loading` (`aria-busy`, its label width locked) and the fields `readOnly`, still focusable (S3 conventions 25, `S3:153`); Cancel, Esc and Close stay T1. Once the request is sent they close the view and cancel nothing (`15:466–468`; H22, `S4:734`). A refusal that arrives after the view has closed raises a persistent CMP-045 `danger` toast, "Couldn't save settings for Scalping.", whose Review reopens SCR-025 with the values that were sent and the refusal in place (`SCR-025/failed`, `SCR-025/invalid-duplicate` or `SCR-025/settings-conflict`), so closing the view never loses an edit in silence (`15:483–490`). A request still unanswered after CMP-001's slow-path delay shows "Still saving…" under the footer, spoken once, politely (`15:48–57`).
- **Saved:** the `200`, or the no-op `200` the server answers when the body changes nothing (`22:8612–8630`). The dialog closes; focus returns to `[⋯]`, the control that opened its menu (`S4:119`); a CMP-045 `success` toast writes "Saved workspace settings." once into CMP-212's polite region after the close (`15:2514–2521`; H34, `S4:881`). The tab and the rail's row show the new name in place, and a moved startup choice moves the rail's default mark.
- **Refused** (T4, at the point of action, never T2, `D02:640–645`): `409 name_taken` → `SCR-025/invalid-duplicate`; `412 version_conflict` → the merge below; `409 concurrent_update`, "a racing write; retry" (`22:8549–8552`) → sent again once with the same body and token, then answered like a first reply, and a second one → `SCR-025/failed` with "Couldn't save — another save of this workspace was in progress. Your changes stay in this dialog."; `503 store_unavailable` or no connection → `SCR-025/failed`; `404`, another window deleted the workspace → `SCR-025/failed` with "Couldn't save — this workspace was deleted in another window."; Save leaves the footer, because an action that no longer applies is replaced by its outcome line, which that banner is (#960 ruling Q13), and Cancel and Esc close without the discard prompt, since nothing is left to save to; a `422` on `name`, where the server counted otherwise than the counter → the matching Name message; a `403` after the session changed → `SCR-025/leg-lost`.
- **The `412` merge:** the client re-reads with `getWorkspace` and compares each field three ways: loaded, yours, saved now. A field only one window changed keeps that window's value, and Save is sent again once with the fresh token and the merged body (D-11's silent re-save, `D02:129`, at field level); a field both windows changed to different values opens `SCR-025/settings-conflict`. A yes-or-no field that both windows changed from the same value ends at the same value, so only Name can conflict (the BQ list's BQ-12 default drew rows for Name and Open at startup; at field level the second never differs); a Move up or Move down in another window, or another workspace made the default there, changes this workspace's token (`22:8549–8552`; every write moves it, `22:19729`) and merges without a dialog.

**What autosave does not cover** (the ticket's Scope, `BL:239`; AD-10 `D01:385`; D-9 `D02:127`). With autosave on, the dirty `*` and the manual save stay: the `*` shows between a change and its write, and the tab strip's Save (`Ctrl+S`) still writes at once. Autosave does not cover (1) these settings, which only Save writes; (2) other workspaces, each with its own switch; (3) other devices, which keep their own switch and their own working copies; (4) a session that cannot save, for autosave sends nothing while Save is T2 (`D02:640`); (5) a layout in conflict, for after an autosave `412` it stops for that layout until the conflict is resolved (`SCR-029/conflict-queued`, §4); (6) history, for each automatic write replaces the saved layout and no earlier version is kept (`FL:85`; `D01:225–238`).

## 3. SCR-029 unsaved dialog and the entry-point matrix

SCR-029 is one component with two variants and a two-verb form: the **unsaved variant**, which stands between a dirty working copy and the one action that would replace it, a preset (D-10 `D02:128`); the **revert form**, the same guard for Revert to saved… (D-9 `D02:127`); and the **conflict variant**, §4. ## 4. SCR-029 conflict dialog

The conflict variant answers one question — this layout changed in another window while mine had unsaved changes: what do I keep? — under the ticket's honesty rule: each choice states what it discards and whether that version can be recovered (`BL:239`; AC 4). **Locked, cited and not re-decided:** D-11's four verbs, the initial focus and `Esc` on Cancel, and the silent re-save of an equal re-read (`D02:129`); E15-D02's table, its lines and its paths, the third racing write and the pending preset included (`D02:417–449`); OQ-E, the fourth verb (`D02:853–855`); A-4 and A-12 (`D02:817`; `D02:825`). Ruled here: BQ-12 (owner-level, held) and BQ-13.

**Scope: one layout (BQ-12 RULED).** The concurrency token is per layout: a layout's `updated_at` versions the whole layout with its panes (`22:8863–8873`), while the workspace's covers its metadata only (`22:19729`). So the conflict is "This layout changed in another window.", E15-D02's words, and never `14`'s "This workspace changed elsewhere. [Keep mine] [Load theirs]" (`14:514–516`; A-4 `D02:817`; D08-A20, §10). No other layout of the workspace is named or touched. The workspace's own `412`, on SCR-025's Save (`22:8629`), is `SCR-025/settings-conflict` — the same grammar at field level, three verbs and no save-as (§2) — never this dialog.

**Detection: two producers, one dialog (BQ-13 RULED).**

1. **A save the user makes** — `Ctrl+S`, `[Save]`, the palette's Save layout, Save layout in the unsaved variant, Replace saved version in the overwrite confirm — answered `412 version_conflict` (`22:664`; `22:8872`). The `412` carries no copy of the other version, so the client re-reads it with `getLayout`; a re-read equal to the copy's base (another window only moved the token) re-saves with the fresh token and shows nothing (D-11 `D02:129`); a different one opens the dialog at once, on Cancel: the user's own action moves focus (`05:96–97`).
2. **An autosave write** — opted in on this device (AD-10 `D01:385`; D-9 `D02:127`) — answered the same way. It arrives while the user is doing something else, so it takes the queue rule below.

The catalogue's detection "over WS … within 300 ms" (`14:668`) cannot be built in R1: `23`'s private topics carry no workspace or layout revision (`23:818`), and E15-S03 puts server-pushed conflict notification out of scope, "R1 detects conflicts on write only" (`BL:783`; A-12 `D02:825`). The 300 <!-- audit:contract.conflict_ms=300 --> ms budget stays, measured from the re-read's answer — the moment the difference is known — to the dialog on screen, or from the moment the queue lets it open. A revision topic in `23` is D08-G6, to `23`'s owner, contract first (C-6.1; §11), and `14`'s Performance line D08-A17 (§10); were one added, a revision pushed for a layout with unsaved changes would enter by producer 2's queued path, the dialog unchanged.

**The queue rule (the ticket's Technical notes, `BL:239`; BQ-13 RULED).** The dialog never opens while focus is in an order-capable panel — the panels D-7 badges, an order ticket among them (`D02:125`) — so it never takes focus from a trading control (`05:96–97`); PROPOSED (D08-D22): nor in the middle of a drag or a keyboard move, which first end as their one mutation. While it waits (`SCR-029/conflict-queued`):

- the tab shows `Scalping *` and a conflict marker — a glyph with the words in the tab's accessible name, "Scalping, unsaved changes, changed in another window", never colour alone; the marker is D08-A21, to E15-D03, which owns the tab strip and names a dirty tab "Scalping, unsaved changes" (`ws.tab.dirty.name`, `D03:602`; merged text; §11);
- autosave stops for Layout 1 until the conflict is settled, and every other layout keeps autosaving;
- one polite announcement, once, "Layout 1 changed in another window." — a status message that takes no focus (WCAG 2.2's 4.1.3, under C-14.1), never the assertive channel `05` keeps for trading events (`05:148`).

It opens when focus leaves the order-capable panel, or on the next `Ctrl+S` or `[Save]`, within 300 <!-- audit:contract.conflict_ms=300 --> ms of that moment, as the explicit modal alert, read by its role, title and description as focus enters it (`05:96–97`; `S4:119`). A Cancel later leaves the marker and the stopped autosave in place: the next save meets the same `412` and opens the dialog again.

## 5. T2 — stated once

**T2 — disabled with a visible reason, one rule for both screens (every gated row of §2–§4 cites "§5").** E09-D09's decision rule decides every control here, the first "yes" winning (`D09:36–42`): a server refusal is T4 at the point of action (step 2); then the session's legs, in the server's own order — **view-as first**: while `GET /auth/session/view-as` reports a context, every server write of this surface is T2 with `rbac.view_as`, "Read-only while viewing as {user}.", because the server refuses a view-as write before it authorises (`D09:85–95`); otherwise a write whose permission the session lacks is T2 with `rbac.permission` and `workspaces:write`'s verb, "Your role can't save workspaces." (`D09:114`); a workspace write is scope `self`, so the account and environment legs never apply (`D02:639`) — and then a state the client knows (step 4) takes its key: `workspace.limit.last`, "You need at least one workspace.", the words of `22:8663`, and `layout.limit.count`, "This workspace has the most layouts it can hold.", E15's PROPOSED state keys (`D02:675`; `D02:670`). Every reason is one sentence of at most 60 <!-- audit:contract.reason_max=60 --> characters with a full stop that names a capability, never data, and a screen never writes its own (`D09:85–95`); the first missing leg is the one named, so a view-as session reads `rbac.view_as` on the last workspace too.
