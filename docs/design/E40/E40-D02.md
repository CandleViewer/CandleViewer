## 1. The notify-only boundary and the SCR-081 → SCR-091 reuse map

Alerts notify; rules act. The server makes it a property, not a promise: every alert write runs `AlertCompiler`'s
structural allow-list before anything is stored (`api/alerts.py:3-5`, `:214-216`; `alerts/compiler.py:56-68`), so an
action-bearing body is a 422 ("Alerts only notify: an action is not allowed in a root node.", `compiler.py:133-136`), the
route never imports the OMS, and the evaluator's only side effects are delivery and outbox rows, counters, audit records
and metrics (`alerts/evaluator.py:10-11`).

**D-1 (the boundary is drawn, not implied).** SCR-091 has no Actions section and no control, menu item or key path that
adds one: E40-S01 passes `mode: "alert"` and the action vocabulary is empty. Where SCR-081 draws Actions (`14:1679`),
SCR-091 draws **Delivery**, whose section description is the persistent line **"Alerts notify; to act automatically,
create a rule."**, "create a rule" being a CMP-021 link to `/rules` (R-160; a Viewer's press lands on R-160's 403, the
route being Owner and Manager only, `apps/web/src/routes/manifest.ts:66`). The line is the CMP-065 FormSection
`description` (`aria-describedby` of the fieldset), with `icon/info`, in `color.text.secondary`: not a tooltip, and not
CMP-028, whose `info` tone is a `role="status"` live region (`15:296-305`), wrong for a static sentence. Board A13 draws
SCR-081 and SCR-091 side by side with the instance map below, so the reuse reads at a glance. The detail drawer's

### 2.4 Tabs, groups and the row model (D-3)

The catalogue's tabs stay — **Active · Triggered · Snoozed** (CMP-042, `role="tablist"`) — with one rule each, so every
alert has a home and nothing silently leaves the list (D01 F6):

- **Active** lists the alert definitions that are not snoozed, in three `<tbody>` row groups with header rows: **Needs
  attention** (disarmed alerts, and armed alerts whose latest firing had a failed or blocked channel) first, open;
  **Armed**; **Not armed** (disabled by the user, expired, a fired one-shot), collapsed by default with its count and a
  `Show` toggle remembered per user. A trader who believes an alert is watching sees at once the ones that are not.
- **Triggered** lists the alerts that have fired (`fire_count` ≥ 1), newest last-fired first, a fired one-shot included,
  so the catalogue's "expired one-shot alerts moved to Triggered" reads "a fired one-shot" (X-1). Each row expands to its
  firing history (§2.6). The tab's count badge (CMP-012) counts alerts with unacknowledged firings, from the `alerts`
  topic's items (`23:842-853`).
- **Snoozed** lists the snoozed alerts with the remaining time as text (T-6), the soonest to wake first.

The list API filters only `enabled` and `symbol` (`api/alerts.py:48`), so tabs, groups and the status filter are
derived on the client over every page (`limit` ≤ 500, `:247`); pages after the first load in the background and a count
reads "500+" until `has_more` is false.

### 2.6 Firing history, row actions and snooze

**Firing history** (the Triggered row's expansion, and `View history` from any row menu): rows from
`GET /alerts/deliveries?alert_id=` (`api/alert_deliveries.py:60-62`), grouped per firing by `alert_id` and `fired_at`
(one transaction stamps every channel row of a firing with the same `queued_at`, `21:2521`), newest first, 20 at a time
with `Load older`. A firing row reads its time, its per-channel status words ("In app sent · Desktop blocked by the OS")
and, once CC-2 lands, the values at fire time. Status words: `sent` / `acked` "Delivered" (and "Read" when acked),
`queued` "Waiting for the desktop app" for a desktop row (`23:847`), `failed` "Failed" with the mapped reason,
`suppressed` "Suppressed" with its reason: `storm` "(storm)", `owner_inactive` "(account inactive)", `recipient_deleted`
"(recipient removed)", and for channels this UI never offers, `email_relay_off`, `webhook_disabled`, `push_unavailable`,
`unknown_channel`, "(channel unavailable)". The history's `Export CSV` is drawn disabled with the reason "Export waits for
the values at fire time." until CC-2, because US-ALRT-004 sc. 3 exports "the values at fire time" (RULED Q13).

**Row menu** (CMP-041; the same actions, in this order, on `Shift+F10` and the menu key): `Edit` · `Duplicate` ·
`Snooze ▸` · `Enable` / `Disable` · `Show on chart` · `View history` · `Delete…` (danger, CMP-044). `Enable` / `Disable`
is also the row's CMP-004 toggle, where the row has room; `PUT /alerts/{id}/enabled` (`api/alerts.py:321-338`).
`Duplicate` opens SCR-091 with every field copied and the name suffixed " (copy)", which must stay unique (§3.7).
`Show on chart` focuses a chart pane already showing the symbol, or opens a new chart panel, never retargeting the focused

### 2.7 Bulk actions (D-6)

Selecting rows (`Space` on a row, CMP-005 in the first column, `Shift+click` for a range) replaces the filter row with
the bulk bar: "3 selected · `Enable` · `Disable` · `Delete…` · `Clear`". Every bulk action confirms with CMP-044 naming
the count and the consequence (the ticket asks confirmation for all three):

| Action  | Confirm title / body                                                                                                          | Confirm button |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------- |
| Enable  | "Enable 3 alerts?" · "They will fire again when their conditions are met. 1 was disarmed by the server and may disarm again." | `Enable 3`     |
| Disable | "Disable 3 alerts?" · "They stop firing until you enable them. Their history is kept."                                        | `Disable 3`    |

There is no bulk endpoint, so requests go one per alert with bounded concurrency (E40-S01 technical note), and the bar

LR-8 announces the result once ("4 alerts disabled, 1 failed"); focus stays on the first selected row (KM-7). Bulk
snooze waits for CC-4 and bulk mute for symbol-mute storage (G5): neither is drawn.

### 2.8 Filters, live updates and performance

The filter row (CMP-055): **Symbol** (CMP-219 with "All symbols"), **Status** (All · Needs attention · Armed · Not armed

cursor-paginated; live changes repaint at most once a second and only mutate text in place (E40-S01 performance
notes); a delivery for an alert invalidates that alert's row, never the page.

### 2.9 Roles (D-8; RULED Q8)

### 3.3 Evaluate on, firing mode and cooldown (D-10)

US-ALRT-002 asks for bar close by default with an intrabar option and wants every alert to say which it uses (sc. 1, 3;
`11:4449`). The IR already carries it: the evaluator runs a subscription only on ticks of its trigger type
(`evaluator.py:320`), so CMP-143 is the control and no new field is asked for (D01 G15 is answered by the existing
`trigger.type`; X-23; CC-11 asks E40-T05 to confirm). CMP-143 offers the four triggers an alert can use:

| Option (words)                | `trigger`                             | Notes                                                                                                                             |
| ----------------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Every price update (intrabar) | `on_price_update`                     | the default when every metric in the condition is a price-feed value (last, mark, bid, ask, index): US-ALRT-001's 1 s cross       |
| Bar close + interval          | `on_bar_close`, `timeframe` (CMP-220) | the default otherwise (US-ALRT-002 sc. 1); 1m 3m 5m 15m 30m 1h 2h 4h 6h 12h 1d 1w only (`compiler.py:71`), no bar modes (E12-D02) |
| When a metric changes         | `on_metric_change`, `metric`          | offered for detector and order-flow metrics                                                                                       |
| On a schedule (UTC)           | `on_schedule`, `cron`                 | a 5-field UTC cron with a plain-words echo ("Weekdays at 09:00 UTC")                                                              |

**Firing modes** (`trigger_mode`): **Once** — fires, then disarms (`evaluator.py:408-410`); **Every time** — fires on
every evaluation that holds, at most once per cooldown; **Once per bar** — at most once per bar of the interval, a late
revision of a fired bar never re-opening it (`gating.py:149-152`). With intrabar evaluation the bar is the trigger's
`timeframe`, and the gate falls back to 1m when none is sent (`gating.py:150`), so the editor always sends the CMP-220
interval with Once per bar and shows it ("Once per 5m bar"); CC-11 confirms an intrabar trigger may carry it.

**Cooldown** applies to Every time only (`gating.py:153-159`) and is hidden for the other modes. Drawn: CMP-008
"Repeat at most every [60] s", minimum 5 s (`14` SCR-091 Validation; the column allows 0–86400, `21:2500`), step 5 s.
**Interim:** `AlertInput` has no cooldown (G12) and an update keeps the stored value (`api/alerts.py:237-238`), so until
CC-5 the field is read-only text: "Repeats at most once a minute." (the column default, `21:2487`).

### 3.4 Delivery: channels, sound and the boundary (D-11; RULED Q6)

- **In app — toast and notification centre — always.** A checked CMP-005 with `aria-disabled` and the description
  "Every alert is recorded in the app." The centre is never a channel choice (D01 §4) and `in_app` is always sent.
- **Sound** is a line under In app, not a channel (D01 C10, F8): the tone the Alerts category plays (§6.2; Error and
  Critical alerts use the Urgent tone, §9), a `Play Alert tone` button (a text label, never icon-only) and a link
  "Change sounds in Notification settings". In the browser build the line reads **"Sound requires the desktop shell."**
  and the play button still previews (`14` SCR-091 Validation). Because In app is always on, a sound-only alert cannot be
  composed here; SCR-115 prevents it per category (§6.3).
- **Desktop notification** — a CMP-005 checked by default on a new alert (DN-A per alert, RULED Q2), with the OS state
  on its line: "Allowed by the OS" · "Blocked by the OS — fix in Notification settings" (link) · "Not asked yet — you'll
  be asked when you save" · "Not supported here". Saving with Desktop checked and the permission not asked raises the OS
  prompt once, in context. Severity Error or Critical checks Desktop when the user has not touched it (D01 K2), with the
  note "Desktop is on by default for Error and Critical alerts."
- **Not drawn:** email, webhook, push. The API refuses push and webhook (`api/alerts.py:202-209`); email waits for a
  relay capability on the wire (DF-6).
