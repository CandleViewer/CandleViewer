## 1. The notify-only boundary and the SCR-081 → SCR-091 reuse map

Alerts notify; rules act. The server makes it a property, not a promise: every alert write runs `AlertCompiler`'s
structural allow-list before anything is stored (`api/alerts.py:3-5`, `:214-216`; `alerts/compiler.py:56-68`): an
action inside the condition is a 422 ("Alerts only notify: an action is not allowed in a root node.",
`compiler.py:133-136`), an `actions` key beside it fails `AlertInput`'s `extra="forbid"` (`api/alerts.py:61-64`), the
route never imports the OMS, and the evaluator's only side effects are delivery and outbox rows, counters, audit records
and metrics (`alerts/evaluator.py:10-11`).

**D-1 (the boundary is drawn, not implied).** SCR-091 has no Actions section and no control, menu item or key path that
adds one: E40-S01 passes `mode: "alert"` and the action vocabulary is empty. Where SCR-081 draws Actions (`14:1679`),
SCR-091 draws **Delivery**, whose section description is the persistent line **"Alerts notify; to act automatically,
create a rule."** The line is the CMP-065 FormSection `description` (`aria-describedby` of the fieldset), with
`icon/info`, in `color.text.secondary`: not a tooltip, and not CMP-028, whose `info` tone is a `role="status"` live
region (`15:296-305`), wrong for a static sentence. Board A13 draws SCR-081 and SCR-091 side by side with the instance
map below, so the reuse reads at a glance. **The link-out pattern** (here and in §4.6's "Create a rule from this alert",
the only other crossing): "create a rule" is a CMP-021 link to `/rules/new` (R-163, Owner and Manager only,
`apps/web/src/routes/manifest.ts:74`) that opens the rule editor with the condition copied as a draft, never a binding;
with unsaved changes it first asks "Discard changes to this alert?" (CMP-044); for a session without `rules:write` it is
disabled with E09-D09's "Your role can't change rules." (`14` §0.5 rule 5), never a route to a 403.

**The reads behind it.** No field carries an alert's latest delivery (`Alert` has none, and the topic's snapshot holds
only `sent` unacknowledged rows, `23:847`), so until CC-3 the client reads, per page of alerts: the newest rows of each
disabled alert, `GET /alerts/deliveries?alert_id={id}&limit=10` (`api/alert_deliveries.py:347-378`), for its disarm
notice; and one `GET /alerts/deliveries?status=failed&from={the oldest last_fired_at on the page}` for D-7's chips, a
`failed` row within 5 s of its alert's `last_fired_at` marking that alert's latest firing. The topic's deltas keep both
current afterwards.

A one-shot whose only firing was held by the storm gate also reads Fired, its history row saying "Suppressed (storm)" (a
suppressed `once` still disarms, `evaluator.py:431-434`). US-ALRT-004 sc. 1 words the three classes "armed / fired /
disarmed" (`11:4495`): the table uses those words and splits the catalogue's "active / disabled" into the reasons a
trader acts on (X-29). A recurring alert that has fired stays "Armed" and shows its fires in Last fired. "Disarmed" uses
`color.text.secondary`, never `color.text.disabled` (NC-5, CR-17), and its own glyph, so it never reads as a user's
Disabled.

### 2.4 Tabs, groups and the row model (D-3)

The catalogue's three tabs keep their roles under one word set, **All · Fired · Snoozed** (CMP-042, `role="tablist"`;
X-29), with one rule each, so every alert has a home and nothing silently leaves the list (D01 F6):

- **All** lists every alert in four `<tbody>` row groups with header rows: **Needs attention** (disarmed alerts, and
  armed alerts whose latest firing had a failed or blocked channel) first, open; **Armed**; **Snoozed**; **Not armed**
  (disabled by the user, expired, a fired one-shot), collapsed by default with its count and a `Show` toggle remembered
  per user. A trader who believes an alert is watching sees at once the ones that are not.
- **Fired** lists the alerts that have fired (`fire_count` ≥ 1), newest last-fired first, a fired one-shot included, so
  the catalogue's "expired one-shot alerts moved to Triggered" reads "a fired one-shot" (X-1). Each row expands to its
  firing history (§2.6). The tab's count badge (CMP-012) counts alerts with unacknowledged firings, from the `alerts`
  topic's items (`23:842-853`).
- **Snoozed** lists the snoozed alerts with the remaining time as text (T-6), the soonest to wake first.

The list API filters only `enabled` and `symbol` (`api/alerts.py:48`), so tabs, groups and the status filter are
derived on the client over every page (`limit` ≤ 500, `:247`); pages after the first load in the background and a count
reads "500+" until `has_more` is false.

### 2.6 Firing history, row actions and snooze

### 3.3 Evaluate on, firing mode and cooldown (D-10)

US-ALRT-002 asks for bar close by default with an intrabar option and wants every alert to say which it uses (sc. 1, 3;
`11:4449`). The IR already carries it: the evaluator runs a subscription only on ticks of its trigger type
(`evaluator.py:320`), so CMP-143, the Select SCR-081 draws (`14:1672`; `15:1633`; X-33), is the control and no new field
is asked for (D01 G15 is answered by the existing `trigger.type`; X-23; CC-11 asks E40-T05 to confirm). CMP-143 offers
the four triggers an alert can use, each with the words SCR-090's condition cell prints (§2.2):

| Option (words)                | `trigger`                             | SCR-090 words | Notes                                                                                                                                                                                  |
| ----------------------------- | ------------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Every price update (intrabar) | `on_price_update`                     | intrabar      | the default when every metric in the condition is `price` (its `source` last, mark or index; there is no bid or ask metric, `rules/vocabulary/metrics.py:74`): US-ALRT-001's 1 s cross |
| Bar close + interval          | `on_bar_close`, `timeframe` (CMP-220) | 5m close      | the default otherwise (US-ALRT-002 sc. 1); 1m 3m 5m 15m 30m 1h 2h 4h 6h 12h 1d 1w only (`compiler.py:71`), no bar modes (E12-D02)                                                      |

**Firing modes** (`trigger_mode`): **Once** — fires, then disarms (`evaluator.py:408-410`); **Every time** — fires on
every evaluation that holds, at most once per cooldown; **Once per bar** — at most once per bar of the interval, a late

interval with Once per bar and shows it ("Once per 5m bar"); CC-11 confirms an intrabar trigger may carry it.

**Cooldown** applies to Every time only (`gating.py:153-159`) and is hidden for the other modes. Drawn: CMP-008

## 4. SCR-092 fired toast and detail drawer

### 4.1 What arrives, and what each item becomes (D-39, D-17)

A firing writes one delivery row per channel of the alert, in one transaction
(`storage/repositories/alert_firing_sqlalchemy.py:137-150`), whose `title` is the raw template, or the alert's name when
the template is empty, and whose `body` is empty (`alerts/evaluator.py:379-380`, `:386-390`); there is no renderer yet
("the future renderer", `compiler.py:81`). The `alerts` topic sends a row again on every change to it: the dispatcher's
settle, an acknowledgement, a desktop report (`23:848`). Its items carry no kind, value, interval or context
(`alerts/ws_topic.py:187-200`; `23:3913-3955`), and the API never returns `context` nor reads one delivery
(`api/alert_deliveries.py:30-31`, `:248-259`). The AC's "actual metric value" and the drawer's snapshot therefore wait
for CC-1 and CC-2: the frames draw the target and are labelled "waits for CC-1" / "waits for CC-2"; the interim
behaviour is stated with each rule.

**D-39 (items to surfaces).** The client classifies each item, then routes it. Until CC-7 puts a `kind` on the wire, the
class is read from the server's own title:

1. **What makes a toast:** a delta item (never a snapshot) on `in_app`, `sent`, with an id not seen before, of class
   firing, disarm notice or storm summary.
2. **A snapshot** (`sub_ok` or a resync: up to 500 unacknowledged `sent` rows, `23:847`) seeds the bell, the badges and
   the rows; it never toasts, sounds or announces (AR-7). §4.5 step 5 counts what it brings that is newer than the gap.
3. **A known id** updates its row (acknowledged, failed) and never toasts again.
4. **`desktop` items** drive only the shell (§4.7) and D-7's chip; `queued`, `failed`, `suppressed` and `acked` items
   never toast.
5. **A firing** is (`alert_id`, `fired_at_ms`): one transaction stamps every row of a firing with the same `queued_at`
   (`21:2521`). Repeat, batch and overflow count firings, never rows, and no notice joins a repeat group or a batch.
6. **Severity** is the alert's current one, read with each row (`alert_deliveries_sqlalchemy.py:31`): history shows
   today's severity on past firings.

**D-17 (toast content).** **Title:** the alert's name, from the client's alert list by `alert_id`; when the alert is
gone, the delivery's title if it holds no `{{`, else "Alert" with the time. **Body:** the message rendered at firing
(CC-1); an empty template renders the condition with its values, "Last price 65,012.5 crossed above 65,000". **Meta:**
symbol · interval when the alert has one · the fire time to the second in UTC, so a late toast reads as late, not as now
(D01 §8). **Interim:** the body is the delivery's title when it differs from the name and holds no `{{` (the message as
written), else the condition restatement without a value. No surface shows a raw `{{`: the toast, an SCR-014 row and the
OS text all take this rule, and the failure notice reads "Desktop notification not shown: {name}".

### 4.3 Lifetime, politeness and focus (D-18; RULED Q2)

- **Lifetime.** Info and Warning close after the SCR-115 duration, 20 s by default (T-1); Error and Critical stay until
  dismissed (T-2), and so do the toasts that stand for more than one item or ask for a decision: a disarm notice, a
  symbol batch, the counted toast, the storm summary and the digest after a gap (T-3). Hover or focus on any toast
  pauses the whole stack (CMP-212 `pauseOnHover`). No countdown bar: the E10-D02 wireframe's thin progress bar
  (`E10-D02.md:123`) would be motion lasting over 5 s with no pause control for a keyboard user who never focuses the
  toast (`16` §7; B-F12; X-17).
- **Politeness.** Every user alert of any severity is `role="status"` in CMP-212's polite region (UA-A; LR-1, LR-2),
  never `role="alert"`; CMP-045's `tone="danger"` gets `role="status"` through the `role` prop (AM-11). The announcer
  speaks D01's sentence, "Alert: {name}, {symbol}, {metric} {value}, {time}" (LR-1), with "Error alert" or "Critical
  alert" in place of "Alert" for the two persistent severities (LR-2's prefix, split by severity, X-30), once per AR-1;
  it digests per AR-2 and AR-3 and writes nothing per WS frame (AR-5); the toast itself never writes.
- **Focus.** A toast never takes focus (05 §3.4.3; CMP-212): it is reached by `Tab` or by the palette's "Focus toasts"
  and "Snooze last alert" (KM-5); `Esc` on a focused toast dismisses it. Dismissing acknowledges the firing (dismiss =
  acknowledge, RULED Q2): one `POST /alerts/deliveries/{id}/ack` for each of its `sent` rows, the in-app row and, once
  shown, the desktop row, because `unacked_count` counts every channel (`alert_deliveries_sqlalchemy.py:106-109`); after
  CC-18 only the in-app row. A timeout never acknowledges (D01 §2). Without `alerts:write` (a Viewer, view-as) `Dismiss`
  closes the toast and acknowledges nothing (`api/alert_deliveries.py:332-336`): the row stays unread.
- **Modals.** Toasts render above a modal's scrim but outside its focus trap and never over its footer (D-20): an open
  SCR-091 keeps focus, the toast is seen and announced, its actions are reached after the dialog closes, and its record
  is in SCR-014.

### 4.5 Stacking, grouping, overflow and the storm summary (D-19)

## 9. Sounds (D-36; RULED Q7)

### 9.1 The set (four tones, labels as text everywhere)

| Tone          | Default use                                                       | Pattern                                  | Length | File size    |
| ------------- | ----------------------------------------------------------------- | ---------------------------------------- | ------ | ------------ |
| Alert tone    | alerts of severity Info and Warning                               | two notes rising                         | 310 ms | 13,712 bytes |
| Urgent tone   | alerts of severity Error and Critical; the risk warning band (K7) | two quick repeats, then a higher note    | 420 ms | 18,564 bytes |
| Reject tone   | ordinary order rejects (K6a)                                      | two notes falling                        | 350 ms | 15,478 bytes |
| Critical tone | every locked override kind (CO-1..CO-12)                          | four alternating notes, then a high note | 740 ms | 32,674 bytes |

80,428 bytes in all, under the 200 KB budget (`14` SCR-115 Performance) and each under 100 KB (RULED Q7). Rule actions,
system health and the recorder's start and stop play nothing by default (D01 K4, K9, K10). One play per firing, never
per channel row; one per repeat group or symbol batch (T-8); none for a storm-held firing (SR-3) or a snapshot item
(D-39); a tone never loops.

### 9.2 The recipe (the generator's input)

PCM WAV, mono, 16-bit signed little-endian, 22,050 Hz, a canonical 44-byte RIFF header and no other chunk. A tone is a
sequence of segments; a segment of `ms` milliseconds has `22050 × ms // 1000` samples (integer division). A note at `f`
Hz is `sin(2πft) + 0.2 · sin(4πft)`, shaped by a 5 ms linear onset, an exponential decay `exp(−t/τ)` and a 10 ms
linear release to zero at its end; a gap is silence. Each tone is scaled so its peak is 0.708 of full scale (−3 dBFS)
and rounded to the nearest integer. Nothing is random, so the bytes are deterministic.

| Tone          | Segments (Hz, ms; a gap is "—")                                                                        | τ     |
| ------------- | ------------------------------------------------------------------------------------------------------ | ----- |
| Alert tone    | 880.00, 110 · —, 30 · 1318.51, 170                                                                     | 60 ms |
| Urgent tone   | 987.77, 90 · —, 40 · 987.77, 90 · —, 40 · 1318.51, 160                                                 | 50 ms |
| Reject tone   | 659.26, 120 · —, 30 · 440.00, 200                                                                      | 80 ms |
| Critical tone | 783.99, 100 · —, 30 · 1046.50, 100 · —, 30 · 783.99, 100 · —, 30 · 1046.50, 100 · —, 30 · 1567.98, 220 | 70 ms |

### 9.3 Generator and manifest (with the boards step)

Per the ruling the WAVs ship only with a committed generator: `docs/design/_tools/e40_d02_tones.py`, Python standard
library only (`wave`, `struct`, `math`, `hashlib`, `json`), writes the four files to `docs/design/E40/sounds/` and
`manifest.json` with each file's label, default use, length, sample rate, bytes and sha256; `--check` regenerates in
memory and fails on any difference. The tones are synthesized here, so no third-party licence applies. If the generator
does not land, the recipe and the manifest ship without audio (RULED Q7).

### 9.4 Preload and the audio-blocked fallback

The four tones are fetched and decoded once at start (≤200 KB, `14` SCR-115 Performance), so a firing plays without a
fetch. In the browser build SCR-091 and SCR-115 read "Sound requires the desktop shell." and previews still play. In the
shell, when a play fails (no output device, the OS muting the app), the toast and the centre carry the event as always;
SCR-115's Sounds section shows "The last sound couldn't play on this device (14:02 UTC). Alerts still show as toasts."
with `Play a test sound`. No toast or announcement of its own: sound is never the only channel.
