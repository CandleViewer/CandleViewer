## 1. Live regions per surface (LR; PROPOSED)

**Architecture (LR-0).** One **announcer** owns every alert-system announcement and lives in CMP-212 ToastHost, which already specifies "one `aria-live="polite"` region for informational toasts and a separate `role="alert"` region for errors/rejections". Both regions are pre-rendered empty at load and only their text is swapped (05 §6.2 region hygiene). Every discrete event is announced **once, app-wide, by this announcer**; no other surface re-announces it (a drawer that repeats the toast's sentence double-speaks). The announcer never runs inside the WS message handler (§4 AR-5).

## 4. The announcement-throttling rule (AR; the a11y counterpart of Part A §6; PROPOSED)

| AR   | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AR-1 | **Single-alert path.** A fired alert (LR-1 class) with no alert announcement in the previous **60 s** (`DIGEST_WINDOW`) is announced at once, in full (one sentence, ~10 words, 2–3 s of speech — E06-D03 D5).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| AR-2 | **Digest path.** Any further LR-1 firing within 60 s of the last alert announcement is **not announced**: it increments a pending count and updates the latest title; the toast still appears visually; the unread count updates with `aria-live="off"`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| AR-3 | **One digest.** The pending count is announced **once**, politely, when the 60 s window closes — or, once G13 puts the summary marker on the wire, at once when the server's SR-5 summary arrives, whichever comes first; until G13 lands the client timer alone fires it (the summary row is indistinguishable from a delivery: 23 §15.7 is `additionalProperties: false`, 22 `AlertDelivery` and the deliveries API carry no `context`): "{n} alerts fired in the last minute; newest: {title}. Open Notifications to read them." If the user opens SCR-014 before then, the pending digest is dropped (they are reading the list).                                                                                                                                                                           |
| AR-4 | **Never digested:** LR-5 (rejects, lockout, kill switch, disconnect, the K12 protection banner) — each once, assertive, in full (05 §6.2); rule fires per OQ-13 (LR-12). **Bounded:** LR-2 (user alerts of severity error / critical) — `gating.py` runs the storm gate for every alert, so up to 20 can reach the client in 60 s, and 20 assertive interrupts a minute is a flood where 05 §6.2 reserves assertive for "discrete, low-frequency" events: the first **3** in any 60 s are announced at once, assertive, in full; from the 4th they are counted into one assertive critical digest at the window end ("{n} more critical alerts in the last minute; newest: {title}"), the toasts persisting regardless (T-2) — the client-side cap until the Owner answers OQ-4 (server-side exemption or cap). |
| AR-5 | **Cadence independence.** The announcer samples the delivery store (Jotai atom fed by the RxJS WS stream) on its own timer; a live-region write happens only on AR-1, AR-3 and AR-4 events — at most **2 polite writes per 60 s** and **4 LR-2 writes per 60 s** (3 + the critical digest), plus one per LR-5 event, never per WS frame (the `alerts` topic is throttled at 250 ms = 4 Hz, 23 §6.2; frames may carry several deliveries). Zero DOM live-region writes in the message handler.                                                                                                                                                                                                                                                                                                                   |
| AR-6 | **Readable on demand.** Every item — announced, digested or storm-suppressed — is a row in SCR-014 (LR-6) and SCR-090 Triggered, with the `suppressed` word (SR-4); the drawer's `log` reads them at the user's pace; the bell's name carries the count.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

**The AC's edge case, 25 firings in one minute (evenly ~2.4 s apart):** t = 0 firing 1 → one full announcement (AR-1); firings 2–25 → counted, not announced (AR-2); at t = 60 s (the SR-5 summary arrives at the same window end and is not a second write, LR-3) → **one summary announcement**: "24 alerts fired in the last minute; newest: …" (AR-3). Total speech: one item sentence + one summary. **Honest note (OQ-B1):** the AC says "one summary announcement" — exactly one summary is produced; the first item's announcement is the unavoidable causal lead (at t = 0 nothing predicts a storm). The strict alternative — a 2 s lead delay on every alert announcement, cancelled when a second firing arrives — would make 25 firings produce one announcement, at the cost of every single alert being spoken 2 s late for screen-reader users (against the SCR-092 2 s budget, C3); **not recommended (heuristic)**; the Owner chooses (Part A §9.4). Visual users see 20 toasts and the summary (Part A §6); the screen-reader user hears 2 sentences.

Feature: Alert surfaces (SCR-014, SCR-090, SCR-091, SCR-092, SCR-115) — accessibility acceptance criteria

  Scenario: Keyboard-only operation
    Given the user has not used a pointing device
    When the user opens the notification centre, reads the newest item, snoozes an alert from its toast,
      creates an alert with a sound and previews the sound, and changes one cell of the SCR-115 matrix
    Then every control involved is reachable via Tab/arrow-key navigation (KM-1..KM-10)
    And every action has a documented non-drag keyboard equivalent (none is drag-based)
    And focus is never silently moved by a firing, a WS push or a count change
    And a visible focus indicator meeting >=3:1 contrast is present at every step (CR-30..CR-33, the double ring on fills)

  Scenario: Screen-reader operation
    Given the user is using NVDA (or VoiceOver) with the keyboard
    When 25 alerts fire in one minute while an order is rejected
    Then the rejection is announced once, assertively, from the role="alert" region (LR-5, AR-4)
    And the alerts produce one item announcement and one summary (AR-1, AR-3), without flooding,
      with no live-region write per WS frame (AR-5)
    And every item is readable on demand in the role="log" list (LR-6, AR-6)

  Scenario: Colour-independence
    Given a row shows severity, kind, snoozed, disabled, muted, suppressed or delivery-failed state
    When the state is rendered
    Then the state is also conveyed via a word and a glyph, not colour alone (NC-1..NC-11)
    And the surfaces pass deuteranopia/protanopia/tritanopia simulation review (docs/design/_tools/cvd_sim.py, E40-D02)

  Scenario: Contrast
    Given the surfaces are rendered in the dark, light and high-contrast themes
    Then all text meets >=4.5:1 (7:1 in high-contrast) and all meaningful non-text elements meet >=3:1,
      per CR-1..CR-36, after DS-CR-1..DS-CR-3 land

  Scenario: Reduced motion
    Given the user has prefers-reduced-motion enabled (OS or in-app override)
    When a toast enters or leaves, or a count changes
    Then the toast uses the instant variant (16 §7), counts swap instantly, nothing flashes above 3 per second
      and no sound or badge loops (T-8, B-F12)

  Scenario: Automated gates
    Given the E40-S02 PR is opened
    Then axe-core reports zero new serious/critical violations (dual live-region separation test, CMP-212)
    And the affected screens' Lighthouse Accessibility score remains >= 95
    And the keyboard-only E2E smoke test covering KM-1, KM-5 and KM-9 passes
