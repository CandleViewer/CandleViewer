## 1. Purpose

Decide, once, what the contributor surface captures **at creation** (the issue/PR forms) versus
**at Ready** (Refinement) versus **at Done** (sign-off), so that:

- the board automation in E01-T07 has stable, parsable gate-section headings to guard on;
- the forms implemented in E01-T05 stay short enough that contributors fill them honestly instead
  of fabricating an answer to get past validation (this is the single biggest risk this design
  exists to manage — see §6 Writing-style spec and the `(heuristic)` findings in §2);
- every checklist item in `02-definition-of-ready-done.md` (§§2–7) is accounted for: mapped to a
  field, or explicitly deferred to Ready/Done with a stated reason — no silent drops (AC1).

Out of scope (owned elsewhere): implementing the YAML/template files (E01-T05), the backlog JSON
schema (E01-T06), design-system tokens/components (E05), GitHub Projects field/column layout
(E01-K01, repo admin config), any product `SCR-*` screen.

## 2. Research findings (heuristic evaluation, not moderated sessions)

Per the Agent-delivery adaptations, "4–6 interviews across disciplines" is replaced by a
**documented heuristic evaluation** against Nielsen's 10 heuristics plus the trading-specific
heuristics in `05-accessibility-standard.md`, applied to: (a) the _current_ six-Kind DoR/DoD
checklists in `02-definition-of-ready-done.md`, (b) the _current_ generic issue forms
(`bug_report.yml`, `feature_request.yml`, `epic.yml`) as a baseline of what a naive transcription
looks like, and (c) this repo's own `.claude/rules/*` and `CLAUDE.md`, which already encode what
a Task/Story/Bug/Chore/Spike ticket needs to carry to be actionable by an agent. No participants,
timings, or quotes are fabricated; every finding below is labelled `(heuristic)`.

### Top-5 friction points

1. **`(heuristic)` Naive DoR transcription produces a 40-field form.** Walking
   `02-definition-of-ready-done.md` §3–§7 line by line and turning every checkbox into a form
   field yields 10–14 fields for a Story alone (INVEST, Gherkin, design-ready x4, security-ready
   x2, test-ready x2, dependencies, estimate, scope note). A contributor facing that many required
   fields either abandons the form or fills fields with placeholder text ("TBD") to get past
   `validations: required` — the exact failure mode the ticket names as the primary risk.
   _Design decision this drove:_ split "captured at creation" from "verified at Ready" (§4) —
   only ~40% of each Kind's DoR items become a creation-time field; the rest are confirmed during
   Refinement against a linked checklist, not re-typed into the issue body.
2. **`(heuristic)` Checkboxes a contributor ticks about their own work are a weak control** — the
   ticket body itself makes this finding explicit for QA/security sign-off, and the heuristic
   evaluation confirms it generalizes: a self-ticked "tests written" checkbox has no evidentiary
   value. _Design decision:_ sign-off sections (QA/security/a11y) are **never** author-fillable
   checkboxes; they are actor-attributed PR-template subsections the reviewer/owner completes
   (§5), matching Nielsen's "error prevention" heuristic (make the wrong action impossible, not
   just discouraged).
3. **`(heuristic)` Free-text on closed-vocabulary fields drifts from the label taxonomy.** The
   repo's `area/*` (17 values), `priority/*` (4), Kind (6), Component, Perspective, Risk (R1–R15 +
   None), Estimate (1/2/3/5/8) are all closed sets defined in
   `01-sdlc-and-branching.md` §5.1–§5.2 and consumed by E01-T06's schema validator. A textarea for
   any of these will drift (typos, synonyms, casing) and silently break the schema/board sync.
   _Design decision:_ every closed-vocabulary item is a `dropdown` with options copied verbatim
   from §5.2, never a free-text field (matches the ticket's own Field-type guidance).
4. **`(heuristic)` Placeholder-as-label and colour-only required-state fail a11y and clarity at
   the same time.** GitHub Issue Forms render `placeholder` text that disappears on focus/fill —
   using it as the only label violates WCAG 2.2 AA (name available on inspection) and also just
   makes the form worse to use once filled in, since the field's meaning vanishes. _Design
   decision:_ every field always has `attributes.label` set to a real, persistent string;
   `placeholder` is used only for a short _example_, never as the label; `validations.required`
   (a programmatic flag GitHub renders as `*Required`) is the only required-state signal — no
   ad hoc "(required)" text duplicated in the label.
5. **`(heuristic)` A vulnerability report filed as a public Bug is a security incident, not a
   triage inconvenience.** The current `bug_report.yml` has no routing away from security issues;
   a contributor who doesn't know `SECURITY.md` exists will just file a public bug with exploit
   detail. _Design decision:_ the issue chooser (`config.yml`) gets an explicit contact link to
   `SECURITY.md`'s private reporting channel, positioned above the template list, and every form's
   top-of-body warning names "vulnerability details" alongside "secrets" as things that never go
   in a public issue (§7 Security notes).

### Rejected findings (recorded per AC4)

- **`(heuristic, rejected)` Add a single "Definition of Ready checklist" free-text/checkbox block
  duplicating all of §2–§7 verbatim into every form.** Rejected: duplicates a single-source list
  into a second location, which `CLAUDE.md` §11 and `CONSTITUTION.md` C-16.5 explicitly forbid for
  _this repo's own docs_, and the same anti-pattern degrades a contributor form — a wall of
  checkboxes nobody reads. The form links to the DoR doc instead of restating it (§4, §6).
  Reason for rejection: single-source-of-truth violation + reintroduces friction point #1.
  applies to every reintroduces friction point #1.
- **`(heuristic, rejected)` Make `priority/*` and `area/*` multi-select checkboxes instead of a
  single dropdown, to save a second form submission when a ticket spans two areas.** Rejected:
  `01-sdlc-and-branching.md` §5.2 defines "exactly one primary `area/*`... secondary areas may be
  added" as a **label**, applied post-creation during triage, not a creation-time multi-select;
  keeping the form single-select for the primary and letting a maintainer add secondary labels
  keeps the Task-form time budget (§8) intact.

## 4. Field-set specification per Kind

Convention used in every table: **Field** (control type) — help text summary — **DoR item satisfied**
(from `02-definition-of-ready-done.md`) or **Verified later** (stage + reason it isn't a creation field).
All closed-vocabulary fields are `dropdown` with options copied verbatim from
`01-sdlc-and-branching.md` §5.1/§5.2 (never free text — finding #3). Every form's body opens with a
persistent (non-dismissible, non-collapsible) markdown block: _"Never paste API keys, session
tokens, passwords, or real account/user identifiers into this issue. Found a vulnerability? Do not
file it here — see SECURITY.md."_ (§7).

## 5. Gate-section heading contract (agreed with the E01-T07 owner)

E01-T07 parses the **PR body**, not the issue body, for sign-off gates (issues capture intent at
creation; PRs carry verification evidence). The contract below is the exact, stable heading text
the parser matches — case-sensitive, exactly this markdown heading level (`###`), no trailing
punctuation. This is the artefact AC3 requires the E01-T07 owner to confirm; until that
confirmation is recorded on this issue, treat headings as **proposed**, not final.

| Heading                   | Appears when                                                                                                                                                       | Absent vs. empty                                                                                                                                                                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `### Acceptance criteria` | Always (every PR)                                                                                                                                                  | **Absent** = parser error, blocks merge. Never legitimately empty — content is the AC→evidence table (§ existing PR template, already present, kept as-is).                                                                                                             |
| `### Test plan`           | Always                                                                                                                                                             | **Absent** = parser error. **Empty** (heading present, no rows/content below it before the next heading) = treated as "no tests" — legal only for `docs`/`chore` with a stated "N/A — no user-facing effect" line; parser requires that literal `N/A` token when empty. |
| `### QA sign-off`         | Story, Bug always; Task/Chore only if labelled `qa`                                                                                                                | **Absent** on a Story/Bug = parser blocks merge (§8 cross-kind rule). **Present but empty** = blocks merge — the section must contain an actor-attributed line (`Signed off by @<handle>` or the literal string `QA capacity deviation` per DoD §8).                    |
| `### Security review`     | Any PR labelled `security`, or touching the paths C-10.2/§8 always-security list names (auth-rbac, oms-execution order paths, key storage, withdrawal, fan-out SL) | **Absent** when the label/path rule applies = parser blocks merge, auto-adds the `security-review` label as a nudge. **Empty** = blocks; needs `Reviewed by @<security-handle>` line or `N/A — <reason>`.                                                               |
| `### a11y evidence`       | Any PR labelled `a11y`, or touching `apps/web/**`, `packages/ui/**`, `packages/chart-engine/**` UI surfaces                                                        | **Absent** when the path rule applies = parser blocks, auto-adds `a11y` label as a nudge. **Empty** = blocks; needs an axe-core CI run URL or `N/A — no UI surface changed` (must be literal, not silently blank).                                                      |

Design decision (finding #2, applied again here): none of these are checkboxes for the PR author
to self-tick. They are markdown sections the parser scans for an **actor-attributed statement**
(a `@handle` or an explicit `N/A`/`QA capacity deviation` token) — ticking a box proves nothing;
a scanned reviewer handle plus a stated reason is at least falsifiable and auditable.

**Proposed for owner/E01-T07-owner confirmation:** the parser should treat "N/A" case-sensitively
(`N/A`, not `n/a` or `NA`) to avoid false negatives — flagged as an open question in the PR
description of this ticket's implementation.

## 6. PR template wireframe

The existing `.github/PULL_REQUEST_TEMPLATE.md` (228 lines, reviewed in full above) is close to
the target shape already — this design **keeps its section order and content**, and adds only the
two things missing per this ticket's scope: (1) inline HTML comments naming which of §5's gate
headings map to which existing checklist block, so the mapping is visible to whoever edits the
template next, not just tribal knowledge; (2) a stated checklist-line ceiling.

- **Section order (kept, confirmed correct):** Summary → Related issues (`Closes #`) → Ticket
  brief checklist → Type of change → How this was tested → Constitution gates (Process →
  Architecture → Statechart [conditional] → Data → Security → Testing → A11y/perf → Observability
  & docs → Reviews required) → Risk & rollout → Self-review.
- **Checklist ceiling:** the current template is ~110 checklist lines across all sections
  (excluding the conditional statechart block, which is deleted when unused per its own
  instruction). The ticket's "~60 lines" budget is a **per-PR-type** budget, not a hard cap on the
  template file: a `docs`-scope PR like this one only touches Process, Architecture (partially),
  Security, Testing, Observability & docs, and Self-review — the Data, Statechart, and
  a11y/perf-heavy items are marked `[~]` N/A with a one-line reason, landing this PR's _filled_
  checklist at ~35 lines. **Design requirement for E01-T05:** no new section is added to the
  template by this ticket; if a future ticket wants to add one, it must state which existing
  section it replaces to hold the ceiling.
- **Gate-heading mapping (to add as inline comments in E01-T05's implementation):**
  `### Acceptance criteria` ↔ existing "How this was tested" section context;
  `### Test plan` ↔ same section, made explicit as its own heading;
  `### QA sign-off` ↔ new subheading under "Reviews required";
  `### Security review` ↔ existing "Security (§12)" block, retitled with the exact heading text;
  `### a11y evidence` ↔ existing "Accessibility & performance (§14)" block, split so a11y gets its
  own heading distinct from perf (perf stays a checklist, a11y becomes the actor-attributed
  section per §5).
- **States:** _empty_ (template as scaffolded by GitHub, all boxes unchecked) → _in progress_
  (author checks items as done, marks `[~]` for N/A with reason) → _submitted_ (all applicable
  items `[x]`/`[~]`, gate headings from §5 present with real content) → _changes requested_
  (reviewer leaves a specific checklist line unchecked with a comment) → _ready to merge_ (all
  green, 2 approvals incl. 1 CODEOWNER).

## 7. Writing-style spec (help text)

- Imperative voice: "State the exact steps", not "Steps should be stated."
- Specific over vague: "≤8 points" not "small enough"; "e.g. C-4.7" not "a rule id."
- Every constraint is stated in words, never conveyed by colour, icon, or emoji alone (WCAG 2.2 AA,
  `05-accessibility-standard.md`).
- No unexplained jargon: any rule id, doc name, or internal term gets inline context or a link on
  first use per field (e.g. "INVEST form (Independent, Negotiable, Valuable...)" not bare "INVEST").
- Every form opens with the same two-line security warning (§4 preamble) verbatim — consistency
  matters more than local wordsmithing for a warning users must recognize instantly.
- Dropdown option text is self-describing out of context (a11y requirement, §8): e.g.
  `priority/p0-critical — drop everything`, not a bare `p0-critical`.
